## 0. Контекст и обоснование (вступление)

### Что делаем

Объединяем два трека в одну фазу:

1. **Component-aware narrowing для топ-5 фиксов (Ф.17.1).** Sandbox при сканировании прокидывает имя компонента (или ближайшего инстанса) до детектора. Детектор формирует **топ-5** кандидатов в `Violation.candidates`, фильтруя по индексу `componentName → Set<tokenId>` (только токены, реально используемые в этом компоненте). AI получает выбранный из этого списка токен + контекст компонента и **объясняет** выбор в 1–2 предложениях. AI не генерирует список — он работает в текущем формате `callGemini()`-в-UI.
2. **Unified search в дропдауне фиксов (Ф.17.2).** В том же дропдауне ReportView добавляется search-input, ищущий по всему `snapshot.tokens` (variables + styles вместе, бейдж VAR/STYLE текстом). Только local-режим (current file + active library из Ф.16.6.5).

### Почему вместе

UI-точка одна — дропдаун выбора фикса в `ReportView.tsx`. Делать двумя фазами означает дважды трогать один и тот же компонент с разной семантикой и удваивать QA-регрессию. PO зафиксировал объединение 2026-05-09.

### Зафиксированные решения PO (8 решений, 2026-05-09) — В СИЛЕ

**Ф.17.1 (component-aware):**
- Q1.edge — вложенные инстансы: ближайший снизу (Card → Avatar → Image ⇒ компонент = Avatar).
- Q2.edge — master с хардкодом: использовать master, брать чистые поля, грязные игнорировать.
- Q5.scope — только narrowing, без текстового бейджа «Used in <Component>».
- **Топ-5 ранжированный список** (формирует детектор в `Violation.candidates`, не AI).
- Если в палитре эталона < 5 подходящих токенов — показываем сколько есть, не дополняем общими.
- Веса confidence — внутренние (если сохраняются на уровне детектора), в UI не выводим.

**Ф.17.2 (unified search):**
- Q1 — индекс: только local (current file + active library из Ф.16.6.5).
- Q2 — бейдж VAR/STYLE текстом, переиспользуем существующий из SelectField.
- Q4 — ранжирование смешанное: exact → prefix → contains, внутри группы алфавит.
- R5 — в library-режиме hint: «Library styles aren't searchable. Use file styles for full search.» (плейсхолдер, финализация @release-scribe).

**Связь треков:**
- Один дропдаун в ReportView: сверху топ-5 кандидатов (`Violation.candidates`), search-input как 6-й пункт ниже, search ищет по всему `snapshot.tokens`. AI-объяснение появляется при выборе любого токена (из топ-5 или из search) — текущий поток `callGemini()` сохраняется.

### Шаг 17.1 — Прокинуть component context через walkNode

**Цель:** В `walkNode` передавать имя ближайшего компонента/инстанса вниз по обходу дерева.

**Зачем:** Без знания, в каком компоненте найдено нарушение, детектор вынужден работать на полной палитре. На крупных эталонах (500+ токенов) релевантность падает, релевантные суггестии теряются среди шума. Это блокер качества фиксов на v1.0.

**Действие:** `@backend`: в `src/sandbox/scanner.ts` (функция обхода дерева) добавить параметр `componentContext?: string`. При входе в `INSTANCE` или `COMPONENT`/`COMPONENT_SET` обновлять контекст. Для вложенных инстансов брать ближайший снизу (решение Q1.edge PO). Узлы внутри MASTER с грязными полями — поля игнорируются на уровне детектора (см. шаг 17.4), но контекст master прокидывается (решение Q2.edge).

**Затрагиваемые файлы:** `src/sandbox/scanner.ts`.

**Acceptance criteria:** На фикстуре с вложенными инстансами Card→Avatar→Image для нарушения внутри Image поле `componentContext` равно `'Avatar'` (ближайший снизу). `tsc --noEmit` чисто. Размер `dist/code.js` Δ ≤ 0.5 KB.

**Зависимости:** нет (стартовый шаг backend-трека). Может стартовать сразу — 17.2 уже закрыт частично, тип `componentName?` существует.

**Размер:** S.

**Среда:** Claude Code в терминале.

**Исполнитель:** @backend → @qa (точечная проверка фикстурой)

### Шаг 17.3 — Построить индекс componentName → Set<tokenId> в sandbox

**Цель:** В sandbox-снапшоте строить мапу «имя компонента → набор tokenId, реально использованных в этом компоненте».

**Зачем:** Этот индекс — основа narrowing на стадии детектора. Без него детектор не знает, какие токены релевантны для конкретного компонента. Считается один раз за скан.

**Действие:** `@backend`: в `src/sandbox/scanner.ts` (или в новой функции `buildComponentTokenIndex`) во время обхода накапливать мапу `Map<string, Set<string>>`. Ключ — `componentName` (правила выбора те же, что в 17.1 — ближайший instance/component, master с чистыми полями). Значение — id токенов, привязанных к узлам внутри. Индекс прикрепляется к snapshot или передаётся в `runDetection` отдельным параметром (выбор `@backend` по чистоте API). При прокидывании в UI (для prompt в 17.5) — формат уточняется в 17.5 (см. «Открытый вопрос реализации» в разделе 1).

**Затрагиваемые файлы:** `src/sandbox/scanner.ts` (+ возможный новый модуль `src/sandbox/componentIndex.ts`).

**Acceptance criteria:** На фикстуре с 3 компонентами (A, B, C) и 10 токенами индекс корректно различает токены каждого. Индекс собирается за один проход (без второго walk дерева). `tsc --noEmit` чисто.

**Зависимости:** 17.1 (нужен component context в обходе).

**Размер:** S.

**Среда:** Claude Code в терминале.

**Исполнитель:** @backend → @qa (фикстурная проверка)

### Шаг 17.4 — Детектор: топ-5 кандидатов с component-aware narrowing

**Цель:** Расширить `Violation.candidates` с топ-3 до топ-5; для violation в компоненте X фильтровать кандидатов через индекс `index[X]`.

**Зачем:** Это и есть точка, где narrowing превращается в результат: пользователь видит в дропдауне 5 максимально релевантных токенов компонента, а не 3 произвольных по дистанции из всей палитры.

**Действие:** `@backend`: в `src/sandbox/detector.ts` функция `runDetection`:
1. Принимает индекс из 17.3 (через параметр или через snapshot).
2. Логика отбора кандидатов: текущая (по дистанции/имени) расширяется до топ-5.
3. **Component-aware narrowing:** если у violation есть `componentName` — кандидаты берутся только из пересечения «топ-N по дистанции» ∩ `index[componentName]`. Берётся 5 наиболее близких из этого пересечения.
4. **Fallback:** если `componentName` отсутствует (узел вне компонента) → топ-5 без narrowing (по полной палитре). Текущее поведение детектора фактически сохраняется, только границу 3 → 5.
5. **Недобор:** если в `index[componentName]` < 5 подходящих — возвращаем сколько есть, **не дополняем общими** (per PO).
6. Грязные поля master игнорируются: на этом уровне (через 17.3) candidate из узла master с hardcoded value не попадает в индекс, но другие чистые поля master — да.

**Затрагиваемые файлы:** `src/sandbox/detector.ts`.

**Acceptance criteria:** На фикстуре «компонент Avatar использует только цвета `--text-primary` и `--bg-surface`» violation внутри Avatar получает `candidates` ровно из этого набора (длина 2, не дополняется общими). На фикстуре с богатой палитрой компонента (≥5 подходящих) — `candidates.length === 5`. Fallback для узла вне компонента — топ-5 как раньше (длина до 5). Регрессия Ф.16.x не падает: existing fix scenarios работают (старый код, читавший `candidates[0]`, продолжает работать). `tsc --noEmit` чисто.

**Зависимости:** 17.2 (закрыт), 17.3.

**Размер:** M.

**Среда:** Claude Code в терминале.

**Исполнитель:** @backend → @qa (чекпоинт после backend-трека)

### Шаг 17.5 — Обогатить AI prompt контекстом компонента

**Цель:** В UI (`ReportView.tsx`, useEffect формирования prompt) добавить в Gemini-prompt секцию с контекстом компонента — `componentName` + список tokenId, реально используемых в этом компоненте, — чтобы объяснение выбранного токена было более релевантным.

**Зачем:** AI остаётся «объяснителем выбранного токена» (строка 1–2 предложения), а не генератором списка. Топ-5 уже сформирован детектором в 17.4. Но качество объяснения растёт, если AI понимает, что токен выбран в контексте конкретного компонента и видит палитру этого компонента (например, AI может явно сказать «в Avatar компоненте используется только text-primary и bg-surface, поэтому text-primary — естественный выбор для текста»).

**Действие:** `@ui-engineer`:
1. В `src/ui/components/ReportView.tsx` (useEffect на строках 158–212, где формируется prompt и вызывается `callGemini`) расширить prompt-шаблоны:
   - Если у `current` violation есть `componentName` (опциональное поле) — добавить в prompt секцию `Component context: "<componentName>". Tokens used in this component: <componentPalette comma-separated>.`
   - Если `componentName` отсутствует — prompt без этой секции, текущее поведение сохраняется (backward compat).
2. Источник `componentPalette` — индекс из 17.3, проброшенный через `snapshot` (17.6) или через новое опциональное поле `Violation.componentPalette?: string[]` (детальность реализации, см. «Открытый вопрос реализации» в разделе 1; решает `@ui-engineer` + `@backend` совместно).
3. **Контракт ответа AI не меняется** — остаётся `Promise<string>` от `callGemini()`, объяснение в 1–2 предложения. Никакого парсинга массивов, никаких новых `PluginMessage`.
4. **Лимит длины prompt:** componentPalette ограничивается до N=20 tokenId (или 30 — на усмотрение реализации) — чтобы prompt не раздувал latency и стоимость Gemini-запроса (см. Риск 7).

**Затрагиваемые файлы:** `src/ui/components/ReportView.tsx`. Возможно `src/shared/types.ts` (если `componentPalette?` добавляется в `Violation` — тогда совместная правка с @backend).

**Acceptance criteria:**
1. На тестовом сценарии с двумя компонентами (Avatar и Card), использующими разные палитры, для одного и того же выбранного токена AI даёт **разные объяснения**, отражающие контекст каждого компонента (проверка PO в Figma desktop, скриншот приложен).
2. Если `componentName` отсутствует — prompt без componentContext-секции, существующее объяснение работает как раньше (backward compat).
3. Длина prompt не превышает разумного предела (componentPalette обрезается до N токенов).
4. `tsc --noEmit` чисто. Размер `dist/ui.js` Δ ≤ 0.8 KB (только prompt-строка + lookup в индексе, без новых React-компонентов).
5. Симметрия `PluginMessage` не затрагивается (AI не использует sandbox-канал).

**Зависимости:** 17.4 (детектор отдаёт `Violation.candidates` топ-5), 17.6 (snapshot или индекс прокинут в ReportView).

**Размер:** S (упростилось vs revision 1, где было M из-за миграции AI в sandbox и валидатора JSON).

**Среда:** Claude Code в терминале + Figma desktop (PO для проверки реального ответа Gemini на двух компонентах).

**Исполнитель:** @ui-engineer → @qa (чекпоинт в 17.10/17.11)

### Шаг 17.6 — Проброс snapshot из App.tsx в ReportView

**Цель:** Передать `snapshot` (или `snapshot.tokens` + componentTokenIndex) в `<ReportView />` как prop, чтобы search мог искать по всему `snapshot.tokens` и AI prompt в 17.5 мог получить componentPalette.

## 6. Риски и точки эскалации к PO (revision 2)

### Удалённые риски vs revision 1

- ❌ **Риск 1 (rev.1) — AI возвращает не топ-5 в стабильном формате.** Неактуально: AI не возвращает топ-5, контракт — строка-объяснение.

### Активные риски с маркерами

🔴 **Риск 1 (бывший Риск 2 rev.1) — narrowing даёт пустое множество и UX ломается.** На реальных ДС возможно: компонент использует только variables, а нарушение — на style. После narrowing кандидатов 0, пользователь видит пустой топ-5 в дропдауне. **Митигация:** при <2 narrowed-кандидатах детектор fallback'ится на полную палитру (топ-5 без narrowing); либо UI явно показывает «No suggestions for this component, use search». Эскалация к PO: какой из вариантов он выбирает (предлагается fallback на полную палитру по умолчанию — пользователь увидит хоть что-то).

🟡 **Риск 2 (был Риск 3 rev.1) — размер бандла превысит лимит.** Поиск с substring + ранжирование + новый компонент дизайн-системы + расширенный prompt. **Митигация:** замер на каждом UI-шаге, лимит Δ ≤ 4 KB на `dist/ui.js` в сумме. Если превышаем — упрощаем (нет fuzzy, нет debounce).

🟡 **Риск 3 (был Риск 4 rev.1) — регрессия Ф.16.6.5 single-select.** Изменения в `snapshot.tokens` могут косвенно затронуть library-режим. **Митигация:** явный регрессионный пункт в 17.10 и 17.11.

🟡 **Риск 4 (был Риск 5 rev.1) — производительность walkNode на крупных файлах.** Дополнительный параметр componentContext + сборка индекса на проходе. На файлах 5000+ узлов может прибавить заметные мс. **Митигация:** замер времени скана на одной фикстуре до/после в 17.10. Если рост >15% — оптимизация (или эскалация).

🟡 **Риск 5 (переформулирован из Риска 7 rev.1) — конфликт между narrowed-кандидатами и search-результатами.** Пользователь видит топ-5 от детектора (narrowed) и ищет токен, который не вошёл в narrowed-список. Search возвращает результат, но непонятно, почему его не было в топ-5. **Митигация:** UI-разделение чёткое («Suggested tokens» vs «Search all tokens»). Если в QA жалобы на UX путаницы — эскалация к PO с предложением текстовой подсказки («Showing tokens used in this component»).

🟡 **Риск 6 (был Риск 8 rev.1) — backward compatibility старого snapshot.** Поле `componentName?` опциональное (закрыто), но другие неявные допущения детектора могут зависеть от его наличия. **Митигация:** явный регрессионный сценарий в 17.10 — парсинг старого снапшота из фикстуры до Ф.17.

🟡 **Риск 7 (новый, специфичный для revision 2) — AI prompt становится длиннее из-за componentPalette → больше токенов на запрос Gemini, выше latency и стоимость.** componentPalette может содержать десятки tokenId. **Митигация:** ограничить `componentPalette` в prompt до N=20 (или 30) токенов в 17.5; замер latency в 17.11 (приемлемо до 1.5x от baseline). Если рост >2x — обрезать N или эскалировать к PO.

3. **После 17.7,** если SearchableSelectField требует значительной переработки SelectField — расширять или дублировать (но если выходит за S/M — на PO).
4. **На 17.9,** финализация текста library-hint — чисто текстовое решение, либо @release-scribe, либо PO.
5. **На 17.11,** если бандл превышает Δ 4 KB на `dist/ui.js` — упрощение или принять рост?
6. **На 17.11,** если время скана растёт >15% — упрощение индекса или принять?

### Известные edge-cases

- **Узел в master без componentName fallback'ится на full palette** — желаемое поведение, не баг.
- **Component без узлов с токенами** не попадает в индекс — детектор для violations внутри корректно fallback'ится на полную палитру.
- **Async library published instances** (Q2.b в исходной разведке) — out of scope, отложено в v1.1.
- **Один и тот же компонент в нескольких файлах:** имена могут совпасть. Индекс по имени, не id, — на v1.0 принимаем (PO зафиксировал «only local»).
