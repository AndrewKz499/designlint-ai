### Шаг 17.12.6 — Создать helper `loadPrompts` с `throw on missing section` [S]

**Цель:** Создать `src/ui/prompts/loadPrompts.ts` с функцией парсинга `.md`-файла и helper'ом подстановки `{{name}}`-плейсхолдеров с явной ошибкой при отсутствии секции или placeholder'а.

**Зачем:** Решение PO Р3 — парсер обязан **бросать ошибку при отсутствии любой ожидаемой секции**, не возвращать undefined / пустую строку. Это страховка от рассинхронизации `.md`-файла и кода: переименовали секцию в `.md`, забыли в `.ts` — падение в dev сразу, не молчаливый «Hello undefined» в Gemini API. Аналогично — при опечатке в имени placeholder'а (Р4 → 4.1, разведка п.4.2 вариант 1).

**Действие:** `@ui-engineer`: создать `src/ui/prompts/loadPrompts.ts` со следующим API:
- `parseSections(raw: string): Record<string, string>` — парсер `## SECTION` секций. Использовать `split(/^## (\w+)\s*$/m)` или эквивалент. Собранный объект содержит ключи всех найденных секций.
- `getSection(parsed: Record<string,string>, name: string): string` — `throw new Error('Missing prompt section: ' + name)` при отсутствии. Ожидаемые имена: `'SYSTEM'`, `'USER_TEMPLATE_A'`, `'USER_TEMPLATE_B'`, `'COMPONENT_CONTEXT_SUFFIX'`.
- `fillTemplate(template: string, vars: Record<string,string>): string` — `replace(/\{\{(\w+)\}\}/g, ...)` с `throw new Error('Missing prompt placeholder: ' + key)` для отсутствующих в `vars` ключей. Пустая строка — валидное значение, не повод для throw.

Функцию для удобства экспортировать одну: `loadAiPrompts(raw: string): { system, templateA, templateB, componentContextSuffix }`, которая вызывает `parseSections` + 4×`getSection` и возвращает строго-типизированный объект (никаких optional полей).

**Критерий успеха:** Файл `src/ui/prompts/loadPrompts.ts` создан, экспортирует `loadAiPrompts(raw: string)` с возвращаемым типом `{ system: string; templateA: string; templateB: string; componentContextSuffix: string }`. `tsc --noEmit` чисто. Helper не используется ещё (это шаг 17.12.7) — `dist/ui.js` не растёт. Размер helper'а после минификации (визуальная оценка из исходника) — не более 400 B.

### Шаг 17.12.9 — Создать `ADR-002 — Library styles limitation in Plugin API` [S]

**Цель:** Зафиксировать ADR-002 о фундаментальном ограничении Figma Plugin API: Plugin API в режиме library отдаёт только Variables, не Styles, поэтому `LIBRARY_HINT` остаётся в UI, и search-режим для library Styles в v1.0 не доступен.

**Зачем:** Долг Ф.17 — этот факт упоминается в комментарии `LIBRARY_HINT` (`ReportView.tsx:18–22`) и в snapshot AI-контракта неявно. Без зафиксированного ADR в будущем кто-то попытается «починить» search для library Styles, не понимая, что это упор в API. ADR закрывает вопрос «почему так навсегда».

**Действие:** `@release-scribe`: создать `context/architecture/adr-002-library-styles-limitation.md` по шаблону ADR (Статус / Дата / Контекст / Решение / Альтернативы / Последствия / Прецеденты). Включить:
- Контекст: при scan-режиме `library` Plugin API возвращает только Variables (`teamLibrary.getAvailableLibraryVariableCollectionsAsync` и т.п.); Styles из библиотеки не listing-ятся API'ем — это подтверждено probe в `designSystemParser.ts:89–171` (Ф.16.6.5).
- Решение: в `ReportView` показывать `LIBRARY_HINT` placeholder при `snapshot.source === 'library'` (или эквивалентный признак); search-режим работает только для file-styles + variables.

## 6. Риски и митигации (по нетривиальным шагам)

### 17.12.1 — search-filter

- **Риск:** для типов нарушений, которые не покрыты явно (например, будущий `effect`-нарушитель), фильтр случайно отбросит все токены. **Митигация:** локальная `isCategoryCompatible` имеет default-ветку `return true` (не фильтровать, если тип неизвестен) — fail-open, не fail-closed. Это явное архитектурное решение, фиксируется комментарием в коде.
- **Регрессия для Ф.17.5 / 17.8:** componentContext-логика и search-search-input не зависят от категории, фильтрация по category не должна их трогать. **Проверка @qa:** scenario «detached_style → выбрать токен из search → AI отвечает» работает как раньше.

### 17.12.7 — миграция AI-промпта (центральный шаг)

**Главный риск — не идентичный prompt после миграции.** Решение PO Р6 → 6.1 явно требует байт-в-байт идентичности.

**Рекомендуемый способ проверки QA — baseline-перехват через `console.log`** (вариант (а) из снимка п.6.4). Аргументы за этот вариант, против остальных:
- **Юнит-тест fillTemplate** — корректно, но в проекте сейчас тестов нет. Введение jest/vitest = новая инфраструктура, расширение scope, отдельный шаг.
- **Mock callGemini** — работает, но требует моковой инфраструктуры в `aiClient.ts`, которой тоже нет; тоже расширение scope.
- **Ручной side-by-side diff в редакторе** — работает для 4-х констант, но не покрывает живой prompt с подставленными значениями (componentName с пробелом, паллетой с запятыми и т.п.).
- **Console.log baseline** — реальный prompt в реальной dev-сессии, side-by-side через `diff` файла baseline и after. Минимальная инфраструктура (один `console.log`), снимается в этом же шаге, не остаётся в production. Это **рекомендация**.

Конкретный рецепт для @qa:
1. До миграции (ветка `main` без шага 17.12.7): открыть Figma desktop → запустить плагин → scan → ReportView → выбрать violation типа `hardcoded_color` с `current.candidates.length > 0` → выбрать токен → DevTools → Console → скопировать строку `[F17.12.7-MIGRATION-CHECK] prompt: "..."` → сохранить в `/tmp/prompt-baseline-A.txt`.
2. То же для `detached_style` с непустым `componentName` и `paletteNames` → сохранить в `/tmp/prompt-baseline-B.txt`.
3. После миграции (применён шаг 17.12.7, без удаления `console.log`): повторить оба сценария → сохранить `/tmp/prompt-after-A.txt`, `/tmp/prompt-after-B.txt`.
4. `diff /tmp/prompt-baseline-A.txt /tmp/prompt-after-A.txt` и `diff /tmp/prompt-baseline-B.txt /tmp/prompt-after-B.txt` → оба должны вернуть пустой результат.
5. После подтверждения @qa — удалить `console.log` из ReportView в этом же шаге, не отдельным.

Если diff не пустой — миграция не идентична, шаг возвращается на доработку.

### 17.12.12 — атомарные коммиты

- **Риск:** при `git add -p` случайно попадает кусок из другого логического блока. **Митигация:** после каждого коммита @release-scribe запускает `git diff --stat HEAD~1..HEAD` и проверяет, что список файлов соответствует логическому блоку. Если файл не на месте — `git reset HEAD~1` и пересобрать коммит.
- **Риск:** `tsc --noEmit` ломается на промежуточном коммите (например, коммит N добавляет use, коммит N+1 — определение). **Митигация:** заранее определить порядок коммитов так, чтобы каждый промежуточный был самодостаточным. Для коммитов 5 (большой UI-редизайн) — приемлемо, что определения и use идут вместе.

### 17.12.14 — push

- **Риск:** force-push случайно. **Митигация:** Принцип проекта запрещает force-push на main. `@release-scribe` использует только `git push origin main`, без флагов `-f` / `--force`.

## 7. Scope-cap: что НЕ делается в Ф.17.12

Зафиксировано здесь для дисциплины — если в ходе выполнения возникает соблазн «заодно» добавить пункт ниже, он откладывается в **отдельный шаг после Ф.17.12** или в **v1.1**.

**Не делается:**
- **Slot-aware ranking** в search dropdown (приоритезация токенов по slot-пути). Откладывается в v1.1.
- **Theme-aware matching** (учёт light/dark при подборе кандидатов). Откладывается в v1.1.
- **Pre-release tuning текста промптов.** Перевод `## SYSTEM` или `## USER_TEMPLATE_*` на русский, изменение тона, добавление severity/slot/theme в текст — **отдельная задача после Ф.17.12** (решение PO Р6 → 6.1).
- **Health-check externalization.** Inline в `Settings.tsx:54` остаётся (решение PO Р5 → 5.2). Возможно в v1.1 если появится потребность редактировать.
- **Async / library-styles изменения.** `LIBRARY_HINT` остаётся плейсхолдером с финализированным текстом; подгрузка library Styles через async API — упор в Plugin API (см. ADR-002), не делается до v1.1+.
- **Введение тестового фреймворка** (jest/vitest). Юнит-тесты для `fillTemplate` / `parseSections` — отдельный шаг после Ф.17.12, не часть его. Baseline-перехват prompt'а заменяет тесты на этот этап.
- **Правка `tsconfig.json`.** Решение РО-3: используется `src/vite-env.d.ts`, `tsconfig.json` не трогаем.
- **Рефакторинг IIFE `suggestionOptions`** в отдельную утилиту. Шаг 17.12.1 правит фильтр на месте, не выносит логику.
- **Submission-артефакты** (скриншоты для Figma Community, README для submission, обновление manifest для marketplace). Это **отдельная фаза после Ф.17.12** (Ф.17.13 «Submission prep», вне скоупа этого документа).
- **`figma plugin publish`.** Требует явного `✅ публикуем` от PO; после push'а `main` v0.14.13 отдельным актом, не частью Ф.17.12.

## 8. Рекомендуемая версия релиза: v0.14.13 (НЕ v1.0.0)

### Аргументы за v0.14.13

1. **v1.0.0 — это не «следующий патч после 0.14.12», это публичная заявка о готовности к Figma Community.** Submission в Community ещё не подан, скриншоты не сделаны, README-tester ещё не финализирован, тестирование на реальных ДС клиентов вне команды не проводилось. Ставить v1.0.0 «авансом» — формирует ожидание стабильности, которое продукт не подтвердил.
2. **История проекта показывает паттерн `0.14.X`:** последняя зафиксированная в коммитах версия — `v0.14.19` (коммит `78e111e`), потом регресс до `0.14.12` в `package.json` (drift при редизайне). v0.14.13 продолжает этот паттерн, фиксирует «всё, что накопилось после 0.14.12 + Ф.17.12 cleanup».
3. **Ф.17.12 — cleanup + миграция promp'та + долги Ф.16.7 + library-hint финал.** Это патч-уровень изменений (нет нового функционала с точки зрения пользователя, кроме исправленного search-фильтра). По semver — это `PATCH`, не `MAJOR`.
4. **v1.0.0 имеет смысл резервировать за моментом submission в Figma Community** — когда есть реальные скриншоты, проверка на N разных ДС, README, фидбек от внешних тестеров. Это **отдельная фаза после Ф.17.12**.
5. **Откатить v0.14.13 → v0.14.14 проще, чем откатить v1.0.0 → v1.1.0.** Версионирование в патч-диапазоне даёт пространство для итераций, не создавая ложных обещаний.

### Аргументы за v1.0.0 (почему НЕ выбрано)

- Психологическая фиксация «продукт готов к публике» — но фиксируется в реальности submission'ом, не номером.
- «Уже долго на 0.14.X» — но это не аргумент для семантической версии, это аргумент для нового **MINOR** (`0.15.0`) если у нас есть нефункциональные подвижки. У нас они есть (миграция промпта — внутренняя архитектура), но не пользовательские.
- **Возможный гибрид: v0.15.0** — если PO считает, что cleanup + externalization тянет на minor (по сути — внутреннее архитектурное изменение видимое разработчику, но не пользователю). Допустимый компромисс. **Моя рекомендация по гибриду:** v0.15.0 имеет смысл только если PO планирует submission в Figma Community в течение 1-2 ближайших фаз (v1.0.0 после v0.15.0 — естественный шаг). Если submission далеко (3+ фазы) — оставить v0.14.13.

### Финальная рекомендация

**v0.14.13** — основная рекомендация (минимальный риск, соответствие истории проекта).
**v0.15.0** — допустимый компромисс, если PO планирует submission в ближайшие 1–2 фазы.
**v1.0.0** — **не рекомендую** до submission и проверки на реальных ДС.

Решение — РО-1, за PO. План шага 17.12.13 написан под v0.14.13; замена значения тривиальна.
