Принцип «derived state вместо дублирования» из CLAUDE.md.

## 2. Концепция шага в одном абзаце

Текущая Ф.18.10 находит **первый слот эталона по `slotKind`** и подставляет его как `suggestedToken`. На простой кнопке (1 background-fill, 1 text-style) этого достаточно, но на ContextMenu (8 background-fills под разные состояния default/hover/pressed/...) детектор всегда подставляет первый встреченный fill эталона — что ломает сценарий «нарушение background → нужен background-токен из эталона». Шаг 18.13 вводит понятие **семантической роли слота** (`SlotRole = 'background' | 'text' | 'icon' | 'border' | 'shadow' | 'unknown'`), которую парсер вычисляет статически (`inferRole` по `node.type` primary, `tokenName` secondary), а детектор вычисляет для нарушения (`inferViolationRole` по `violation.type` + `scannedNode`). Матчинг сначала ищет слоты с совпадением `slotKind + role`, объединяет их с top-N от старой логики (`pickTopCandidates`), дедуплицирует по `tokenId` и отдаёт **до 10 кандидатов** в `Violation.candidates`. Если матча по role нет — fallback на старую логику без изменений.

### Шаг 18.13.2 — Helper `inferRole` в парсере + проставление `role` во всех `collect*Slot*`

**Цель:** Создать в `src/sandbox/exampleParser.ts` функцию `inferRole(node, slotKind, tokenName): SlotRole` и вызвать её в каждом месте, где формируется `ExampleSlot` (`collectFillSlots`, `collectStrokeSlots`, `collectTextStyleSlot`, `collectRadiusSlots`, `collectLayoutSlots`).

**Зачем:** R-13.1 — `role` живёт на стороне парсера, не вычисляется налету в детекторе. Это упрощает дальнейшую логику matching (детектор только сравнивает) и делает данные эталона самодостаточными для AI prompt в 18.13.6.

**Действие:** `@backend`: в `src/sandbox/exampleParser.ts`:
- Импортировать `SlotRole` из `../shared/types`.
- Добавить helper:
  ```ts
  function inferRole(
    nodeType: SceneNode['type'],
    slotKind: ExampleSlot['slotKind'],
    paintTarget: 'fill' | 'stroke' | null,
    tokenName: string,
  ): SlotRole { ... }
  ```
  Логика по приоритету (R-13.2):
  1. `slotKind === 'text-style'` → `'text'` (textStyle всегда = текст).
  2. `nodeType === 'TEXT'` → `'text'` (включает `slotKind === 'fill'` на TextNode — E2).
  3. `paintTarget === 'stroke'` → `'border'` (Q-microsoft).
  4. Имя токена (case-insensitive substring match): contains `'background'` → `'background'`; contains `'icon'` → `'icon'`; contains `'shadow'` → `'shadow'`; contains `'border'` → `'border'`.
  5. Default для shape-узлов с fill → `'background'` (E3).
  6. Иначе → `'unknown'`.
- В `collectFillSlots` (строка 74) и `collectStrokeSlots` (строка 128): передавать `node.type` и соответствующий `paintTarget` (`'fill'` / `'stroke'`) в `inferRole`, проставлять `role` в собираемом `ExampleSlot`.
- В `collectTextStyleSlot` (строка 181): `paintTarget = null`, `nodeType = 'TEXT'` (helper вызывается только для TextNode). Результат `inferRole` всегда `'text'` по правилу (1).
- В `collectRadiusSlots` (строка 212) и `collectLayoutSlots` (строка 247, spacing): `paintTarget = null`. Для radius/spacing inferRole в большинстве случаев вернёт `'unknown'` (если только `tokenName` не содержит подсказок). Это допустимо — multi-slot для spacing/radius **не входит в 18.13** (anti-case), но проставление `role` обязательно для консистентности типа.

**Критерий успеха:** `tsc --noEmit` чисто после правок. На синтетическом эталоне ContextMenu (если PO запустит локальный prebuild и посмотрит лог парсинга через `console.log` — debug-логи не остаются в финальном коммите) видны `role` со значениями `'background'`, `'text'`, без `'unknown'` для известных tokenName-шаблонов. Размер `dist/code.js` Δ ≈ +0.8–1.2 KB на этом шаге.

**Среда:** Claude Code в терминале + Figma desktop (для опциональной debug-проверки PO).

**Исполнитель:** @backend → @qa.

**Размер:** S.

**Acceptance «Готово, когда…»:** `inferRole` экспортируется (или приватный — на усмотрение backend, главное вызывается во всех 5 collect-функциях). На эталоне Button + ContextMenu все собираемые слоты имеют корректную `role`. `tsc --noEmit` чисто.

**Зависимости:** 18.13.1 (тип `SlotRole` существует).

**Риски:** Эвристика по имени токена (правило 4) может давать ложные срабатывания на нестандартных design system'ах — например, токен `Shadow/Card` будет распознан как `role:'shadow'`, что корректно, но `Border/Subtle` на background-узле — как `'border'` (если правило 4 сработает раньше правила 5). Mitigation: правила 1–3 (по `nodeType` / `slotKind` / `paintTarget`) **имеют приоритет над правилом 4**, что покрывает ContextMenu-случай. На редких ДС с конфликтными именами получим `role:'unknown'` или формально неправильную роль — это попадает в раздел «Known limitations» вместе с E3 и не блокирует шаг.

### Шаг 18.13.4 — `inferViolationRole` + расширение `findExampleSlot` и `applyExampleOverride` в детекторе

**Цель:** В `src/sandbox/detector.ts` создать helper `inferViolationRole(violation, scannedColor): SlotRole`. Расширить `findExampleSlot` для возврата **массива слотов** с матчем `slotKind + role`. Переписать `applyExampleOverride` для объединения слотов role + top-N от `pickTopCandidates`, дедупликации по `tokenId`, лимита 10. Сохранить fallback на старую логику при пустом матче role (R-13.4 b).

**Зачем:** Это **ядро шага 18.13**. Без этой правки парсер уже умеет собирать `role`, scanner умеет различать TextNode/stroke, но детектор всё ещё работает по «первый по slotKind». Сценарии S2/S3/S4 пройдут только после этого шага.

**Действие:** `@backend`: в `src/sandbox/detector.ts`:

- **Helper `inferViolationRole`** (новый, ~25 строк):
  ```ts
  function inferViolationRole(
    violation: Violation,
    scannedColor: ScannedColor | null, // для color-нарушений; null для text-style/spacing
  ): SlotRole { ... }
  ```
  Логика:
  - `violation.type === 'missing_text_style'` → `'text'` (всегда, без scannedColor).
  - `violation.type === 'hardcoded_color'`:
    - `scannedColor?.nodeType === 'TEXT'` → `'text'` (E2 для color на TextNode).
    - `scannedColor?.paintTarget === 'stroke'` → `'border'` (Q-microsoft).
    - default → `'background'` (E3).
  - `violation.type === 'detached_style'` / `'similar_to_token'` / `'nonstandard_font_size'`: применить ту же логику что и для соответствующего основного типа (`detached_style` для color → как `hardcoded_color`; `nonstandard_font_size` → `'text'`).
  - `violation.type === 'spacing_off_scale'` → `'unknown'` (явно, multi-slot для spacing — anti-case 18.13).

- **`findExampleSlot` (строки 90–99) → переписать в `findExampleSlotsByRole`:**
  ```ts
  function findExampleSlotsByRole(
    example: Example | null,
    kind: ExampleSlot['slotKind'],
    role: SlotRole,
  ): ExampleSlot[] { ... }
  ```
  Возвращает **массив** слотов с матчем `slotKind === kind && (slot.role === role || slot.role === 'unknown' || role === 'unknown')` (E5: `'unknown'` матчит любую role с обеих сторон). Если массив пуст — пустой массив (не undefined).

- **`applyExampleOverride` (строки 161–185) — переписать:**
  ```ts
  function applyExampleOverride(
    violation: Violation,
    example: Example | null,
    snapshot: ReferenceSnapshot | null,
    scannedColor: ScannedColor | null,
  ): void { ... }
  ```
  Логика:
  1. Вычислить `role = inferViolationRole(violation, scannedColor)`.
  2. Получить `roleSlots = findExampleSlotsByRole(example, kind, role)`.
  3. Если `roleSlots.length === 0` (R-13.4 b — fallback): оставить `violation.candidates` как есть (top-N от старой логики из `pickTopCandidates`, который уже отработал в `runDetection`). `violation.exampleSlot` не проставляется.
  4. Если `roleSlots.length > 0`:
     - `roleCandidates = roleSlots.map(slot => ({ id: slot.tokenId, name: slot.tokenName, value: slot.hexInTheme, kind: tokenKindFromSlot(slot) }))`.
     - `oldCandidates = violation.candidates ?? []` (top-N от `pickTopCandidates`).
     - Объединение: `merged = [...roleCandidates, ...oldCandidates]`, дедупликация по `id` (через `Set`/`filter`), **лимит 10** (E4).
     - `violation.candidates = merged`.
     - `violation.suggestedToken = roleCandidates[0].name`; `violation.suggestedTokenId = roleCandidates[0].id`.
     - `violation.exampleSlot = roleSlots[0]` (первый по порядку обхода парсера).

- **Вызов `applyExampleOverride`** в `runDetection` (строка 475): передать `scannedColor` из текущего scanResult (для color-нарушений: найти запись по `nodeId === violation.nodeId && paintTarget === ...`; для text-style/spacing: `null`).

- **`tokenKindFromSlot`** — вынести из существующего `tokenFromSlot` (строки 112–127) или повторно использовать. Не дублировать логику.

**Критерий успеха:**
- `tsc --noEmit` чисто.
- Сценарий S1 (простая кнопка) не регрессирует: один background-fill в эталоне → `roleCandidates.length === 1` → `merged` длиной 1+top-N (как раньше). Поведение визуально не отличается.
- Сценарий S2 (ContextMenu, color на background): `roleCandidates.length === 5` → `merged` длиной до 10, видны все 5 background-токенов в SelectField.
- Сценарий S3 (color на text): `roleCandidates` содержит только text-color-токены, не background.
- Сценарий S4 (typography multi-slot): `roleCandidates` содержит все 3 text-style-токена.
- Размер `dist/code.js` Δ ≈ +0.8–1.5 KB на этом шаге. **Кумулятивно за 18.13.1–18.13.4 на code.js: +2.3–3.7 KB.**

**Среда:** Claude Code в терминале + Figma desktop (PO для прогона S1–S4).

**Исполнитель:** @backend → @qa (тест-матрица S1–S4 + регрессия baseline 18.10).

**Размер:** M.

**Acceptance «Готово, когда…»:** Все 4 сценария S1–S4 проходят как описано в разделе 3. `tsc --noEmit` чисто. Регрессия baseline 18.10 (поведение simple-кнопки) подтверждена `@qa`.

**Зависимости:** 18.13.2 (парсер проставляет `role`), 18.13.3 (scanner проставляет `nodeType`/`paintTarget`).

**Риски:**
- **Риск-A (вычисление scannedColor для violation):** связь `Violation` ↔ `ScannedColor` — по `nodeId`, но при наличии и fill, и stroke на одном узле существует **две** `ScannedColor`-записи. Mitigation: для нарушения по hex искать `scannedColor` по `nodeId + currentValue === scannedColor.hex` (что уже фактически и есть, т.к. nodeId+hex уникальны). Для `missing_text_style` — `scannedColor = null`, эта ветка inferViolationRole не использует scannedColor.
- **Риск-B (лимит 10 vs текущий 5):** старый `pickTopCandidates` отдаёт top-5. Если `roleCandidates.length === 5`, в merged уже 5 от role + ≤5 от старой логики (часть будет отсеяна дедупом) — итого ≤10. Лимит 10 соответствует E4 и не превышается.
- **Риск-C (производительность):** на огромных ДС (1000+ violations × 8 slots в эталоне) `findExampleSlotsByRole` вызывается N×M раз. Mitigation: эталон обычно содержит ≤20 слотов; для v1.0 это допустимо. Если QA увидит замедление >500ms на 1000+ violations — кешируем результат `findExampleSlotsByRole` по ключу `kind+role`.

### Шаг 18.13.5 — Миграция старых `Example` из `clientStorage` через `??`

**Цель:** В handler `get-example` в `src/sandbox/code.ts` (или там, где десериализуется persisted `Example`) при чтении старого формата подставлять `slot.role ?? 'unknown'` для каждого слота, чтобы старые persisted `Example` без `role` не приводили к runtime-ошибке и матчились с любой role нарушения.

**Зачем:** E5 явно требует graceful fallback. Без этого пользователь, у которого в `clientStorage` сохранён `Example` от Ф.18.10 (без `role`), при первом запуске v0.18.x с шагом 18.13 получит `slot.role === undefined`, и `findExampleSlotsByRole` будет всегда возвращать пустой массив — multi-slot не заработает до перепарсинга.

**Действие:** `@backend`: в handler `get-example` в `src/sandbox/code.ts` после `JSON.parse(stored)`:
- Пройти по `parsed.slots` и для каждого `slot` без `role` подставить `slot.role = 'unknown'`. Это можно сделать одним `.map(slot => ({ ...slot, role: slot.role ?? 'unknown' }))`.
- Альтернатива (более явная): при парсинге проверить `parsed.slots.some(s => s.role === undefined)` — если да, залогировать warning «migrating example without slot.role to 'unknown'» и применить map. Это даёт видимый сигнал в console при разработке/QA.
- НЕ делать перепарсинг (это потребовало бы доступа к узлу) — `'unknown'` достаточно: оно матчит любую role нарушения по правилу E5, и пользователь получит fallback-поведение «как в 18.10», а после первого нового парсинга эталона в UI данные обновятся.

**Критерий успеха:** На синтетическом тесте: записать в `clientStorage` под ключ `'example-current'` JSON старого формата (без `role` в слотах), запустить плагин — `get-example` отдаёт `Example` с `slot.role === 'unknown'` для всех слотов, runtime-ошибки нет. `tsc --noEmit` чисто. Размер `dist/code.js` Δ ≤ +0.2 KB.

**Среда:** Claude Code в терминале + Figma desktop (QA для синтетического теста миграции).

**Исполнитель:** @backend → @qa.

**Размер:** XS.

**Acceptance «Готово, когда…»:** Сценарий миграции (старый persisted `Example` без `role`) → `get-example` корректно читает, проставляет `'unknown'`, фильтрация в детекторе работает (любая role нарушения матчится).

**Зависимости:** 18.13.4 (логика `findExampleSlotsByRole` уже работает с `'unknown'` — иначе миграцию проверять не на чем).

**Риски:** Если в будущих фазах появятся другие поля `ExampleSlot`, требующие миграции, паттерн `?? defaultValue` придётся повторить. Mitigation: при добавлении нового обязательного поля `@lead-architect` обязан проверять этот handler и расширять map. Документируется комментарием в коде.

### Шаг 18.13.6 — AI prompt enrichment в `ReportView.tsx`

**Цель:** Расширить фразу AI prompt про эталон в `src/ui/components/ReportView.tsx` (строка 257): добавить упоминание `role` в дополнение к существующему `slotKind`.

**Зачем:** AI-объяснение должно знать роль слота, чтобы лучше комментировать «почему именно этот токен». Без этого LLM видит только slotKind (который слабо различает background-fill vs icon-fill vs border-fill — все они `'fill'`) и теряет контекст. Это финальный визуальный артефакт шага, который PO проверяет в сценариях S2–S4.

**Действие:** `@ui-engineer`: в `src/ui/components/ReportView.tsx` строка 257:
- Текущая фраза:
  ```ts
  prompt += ' This token was taken from the user-selected example reference (slot: ' + violation.exampleSlot.slotKind + ').';
  ```
- Новая (если `violation.exampleSlot.role` существует и не `'unknown'`):
  ```ts
  prompt += ' This token was taken from the user-selected example reference (slot: ' +
    violation.exampleSlot.slotKind +
    (violation.exampleSlot.role && violation.exampleSlot.role !== 'unknown'
      ? ', role: ' + violation.exampleSlot.role
      : '') +
    ').';
  ```
- Если `role === 'unknown'` (случай миграции старого persisted `Example`) — не добавлять в prompt, чтобы не путать AI шумом.
- **Лимит правок: ≤20 строк.** Если по ходу обнаружится, что нужно править больше (например, добавить новый отдельный сегмент prompt с указанием всех слотов role) — **эскалировать через `ask_user_input_v0` к PO**, не делать самовольно.

**Критерий успеха:** В сценариях S2–S4 AI-объяснение упоминает роль (например, «role: background»). В сценарии S1 AI-объяснение либо упоминает роль (если простая кнопка имеет background-fill — да), либо нет (для `'unknown'`-слота — нет). `tsc --noEmit` чисто. Размер `dist/ui.js` Δ ≈ +0.15–0.25 KB. Скриншот AI-объяснения для S2 приложен.

**Среда:** Claude Code в терминале + Figma desktop (для скриншота AI ответа).

**Исполнитель:** @ui-engineer → @qa.

**Размер:** XS.

**Acceptance «Готово, когда…»:** В AI prompt для нарушения с известной role видно `role: <value>`. Скриншот S2 приложен. Регрессия S1 (простая кнопка) — AI-prompt не сломан.

**Зависимости:** 18.13.4 (поле `exampleSlot.role` фактически проставляется детектором).

**Риски:** Если `violation.exampleSlot.role` оказывается `undefined` из-за бага в 18.13.4 — `prompt` получит `role: undefined` буквально. Mitigation: проверка `&& violation.exampleSlot.role !== 'unknown'` в условии (логически если undefined — оператор `&&` отсекает на первом операнде, prompt получит чистую старую фразу). Это безопаснее, чем optional chaining без проверки.

## 7. Anti-cases — что НЕ делается в 18.13

Явно отложено в Ф.18b или v1.x:

- **Multi-slot для spacing.** `inferViolationRole` для `'spacing_off_scale'` возвращает `'unknown'`. Это означает, что любые spacing-слоты эталона матчатся как fallback — но это эквивалентно текущему поведению Ф.18.10 (первый подходящий по slotKind). Полноценная multi-slot логика для spacing — Ф.18b или v1.x.
- **Эвристика по имени узла для Frame-as-icon.** Если PO выбирает Frame с одной заливкой как иконку, парсер всё равно ставит `role:'background'`. Это known limitation, фиксируется `@release-scribe` в ADR-002 раздел «Открытые вопросы». Эвристика по имени (`'icon'` в node.name) **НЕ вводится** в 18.13.
- **AI-определение роли.** `inferRole` остаётся **статической эвристикой**. AI-классификатор для роли — антипаттерн (вносит latency на парсинге, AI недоступен без ключа).
- **Переписывание `pickTopCandidates`.** Ф.17.4 (component-aware narrowing) и старая логика hex-расстояния остаются как есть. Шаг 18.13 только **дополняет** через `applyExampleOverride`.
- **Тема-aware подбор.** `hexInTheme` всё ещё берётся из первого mode (по решению Ф.18a). Поддержка светлой/тёмной темы — R4, Ф.18b.
- **`Violation.suggestedRole`** как отдельное поле. Role доступна через `violation.exampleSlot?.role`.
- **Изменение лимита `pickTopCandidates`** с 5 до чего-то другого. В шаге 18.13 финальный лимит `Violation.candidates` — 10 (E4), но это **на стороне `applyExampleOverride`** (после объединения), а не в `pickTopCandidates`.
- **Severity-градация нарушений** (v1.1).
- **DTCG-импорт** (v1.1).
- **Bump версии** в шаге 18.13. Это **рабочий шаг внутри Ф.18b**. Финальный bump до `v0.18.0` — после закрытия всех шагов Ф.18b в финальном релизном шаге `@release-scribe`.
