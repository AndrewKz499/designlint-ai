## 1. Как сейчас собирается plugin

### 1.1 Билд-скрипты и инструмент

`package.json`, строки 5–11:

```json
"scripts": {
  "build:sandbox": "vite build --mode sandbox",
  "build:ui": "vite build && node scripts/build-ui.mjs",
  "build": "npm run build:sandbox && npm run build:ui",
  "watch:sandbox": "vite build --mode sandbox --watch",
  "watch:ui": "vite build --watch"
}
```

- Сборщик **один и тот же — Vite** в двух режимах (`mode sandbox` для `dist/code.js` и default для `dist/ui.js`).
- Никакого esbuild/webpack отдельно.
- Финальный шаг — `scripts/build-ui.mjs` инлайнит скомпилированный `dist/ui.js` целиком в `dist/ui.html` через `<script>${js}</script>`. То есть **всё, что попадает в `ui.js`, попадает и в `ui.html`** — вес UI-бандла удваивается (на момент снимка `ui.js = 690 628 B`, `ui.html = 690 947 B`).

### 1.2 Версии (фактически установленные, не declared)

`package.json` declared:

```json
"devDependencies": {
  "@figma/plugin-typings": "^1.0.0",
  "@types/react": "^19.0.0",
  "@types/react-dom": "^19.0.0",
  "react": "^19.0.0",
  "react-dom": "^19.0.0",
  "typescript": "^5.0.0",
  "vite": "^6.0.0"
}
```

Фактически установлен `vite@8.0.3` (см. `node_modules/vite/package.json`). Это **расхождение** между declared `^6.0.0` и installed `8.x`, но для разведки важно: `?raw`-импорты поддерживаются и в Vite 6, и в Vite 8.

### 1.3 Конфигурация Vite

`vite.config.ts` (полный файл, 44 строки):

- **Sandbox-режим:** entry `src/sandbox/code.ts`, формат `iife`, target `es2017`, `minify: false`. Внешним помечен только `@figma/plugin-typings`.
- **UI-режим:** entry `src/ui/main.tsx`, формат `iife`, fileName `ui.js`. Минификация — по дефолту Vite (`esbuild`, включена). `define` подменяет `process.env.NODE_ENV` на `"production"`.
- **Никаких пользовательских loader / plugin / `assetsInclude`** в конфиге нет. Используется только то, что Vite даёт из коробки.

### 1.4 Что попадает в финальные `code.js` / `ui.js`

- `code.js` (55 216 B) — только `src/sandbox/*` + `src/shared/*`, что импортируется из sandbox.
- `ui.js` (690 628 B) — `src/ui/*` (включая React 19, ReactDOM, всю дизайн-систему `components/ui/*`, `aiClient.ts`, `App.tsx`, все экраны) + `src/shared/*`, что импортируется из UI. Импорта между UI и sandbox нет — это два независимых бандла.
- `ui.html` (690 947 B) = шаблон + инлайн `ui.js`.

### 1.5 Поддерживает ли текущая конфигурация import текстовых файлов «из коробки»

**Да, через `?raw`-suffix.** Это нативный механизм Vite, доступный без плагинов. Проверено:

- `node_modules/vite/client.d.ts:243` декларирует:

```ts
declare module '*?raw' {
  const src: string
  export default src
}
```

- Никаких дополнительных plugin/loader/assetsInclude в `vite.config.ts` не требуется.

**Однако в `tsconfig.json`** нет `"types": ["vite/client"]` (см. полный файл в первоисточнике). Чтобы TypeScript увидел декларацию `'*?raw'`, потребуется либо добавить `"types": ["vite/client"]` в `compilerOptions`, либо создать `src/vite-env.d.ts` с `/// <reference types="vite/client" />`. Без этого `import x from './foo.md?raw'` будет компилироваться (Vite обработает на этапе сборки), но IDE и `tsc --noEmit` будут ругаться.

### 1.6 Текущее использование raw-импортов в проекте

Поиск `?raw` / `assetsInclude` / loader-конфигов по `src/`: **результатов нет**. Никаких raw-импортов в проекте на момент снимка не используется. То есть это новый механизм для проекта.

## 2. Как импортировать текстовый файл как строку

### 2.1 Текущее состояние

В `ReportView.tsx:185–194` промпты — это inline TS string-literals, склеенные через `+ ... +`. В `ReportView.tsx:252` system-prompt — также inline-литерал. В `Settings.tsx:54` health-check user-prompt — inline-литерал на русском (`'Ответь одним словом: работает.'`).

Нет никакого внешнего источника, нет ни constant-модуля, ни json/md-файла.

### 2.2 Варианты

#### Вариант (1) — Vite `?raw`-импорт

```ts
// .md или .txt
import promptTemplate from './prompts/ai-suggestion-a.md?raw';
```

- **Работает в нашей сборке без доп. конфигурации сборщика?** Да — `?raw` нативный для Vite (и для sandbox, и для UI бандла).
- **Требует ли правок tsconfig?** Да: либо `"types": ["vite/client"]` в `tsconfig.json`, либо `src/vite-env.d.ts` с `/// <reference types="vite/client" />`. Это однократная настройка.
- **Содержимое:** обычный `.md` или `.txt`, любые символы, без необходимости escape-ить кавычки и `\n` — переводы строк остаются как есть.
- **Плюсы:** PO редактирует чистый markdown; нет JS-синтаксиса; никакой случайной интерполяции; файл пригоден для diff-review без шумa от TS-операторов.
- **Минусы:** placeholder-ы — кастомный формат (см. п.4), требуется helper-подстановка; нужна правка tsconfig.
- **Объём прироста бандла:** длина файла попадает в `ui.js` как строковая константа (Vite превращает её в `export default "..."`). На момент снимка длина текущих литералов суммарно ~960 B (см. п.5), плюс структурная разметка markdown ~50–100 B → итого +1.0–1.1 KB сырого текста. После `esbuild`-минификации экономии нет (литералы уже минимальны).
- **Применимо к sandbox?** Да, но в sandbox prompt-ы не используются — все вызовы `callGemini` идут из UI (`ReportView.tsx`, `Settings.tsx`). Для нашей задачи это только UI-бандл.

#### Вариант (2) — TS-модуль с экспортом строки

```ts
// src/ui/prompts/ai-suggestion.ts
export const PROMPT_A = `Violation: {{currentValue}} on node "{{nodeName}}". Suggested token: ...`;
export const PROMPT_B = `On node "{{nodeName}}" the value {{currentValue}} ...`;
export const SYSTEM_PROMPT = `You are a designer assistant ...`;
export const COMPONENT_CONTEXT_SUFFIX = ` Component context: "{{componentName}}". Tokens used in this component: {{componentPalette}}.`;
```

- **Работает в сборке?** Да — это просто обычный TS-импорт, ничего не нужно.
- **Требует tsconfig?** Нет.
- **Содержимое:** TS-литералы. Если использовать template literals (backticks), placeholders можно делать как `${componentName}` (нативная JS-интерполяция) — но тогда подстановка происходит **в момент чтения константы**, что разрушает идею «файл с готовым шаблоном». Поэтому placeholder-ы всё равно остаются текстовыми (`{{...}}`), а template literals нужны только ради удобства многострочности.
- **Плюсы:** ноль изменений в тулчейне; типизация имеется автоматически; легко делать частичный refactor; PO видит код, но строки изолированы в отдельном файле.
- **Минусы:** PO работает с `.ts`-файлом — нужно помнить про backticks, escape для `\``, риск случайно сломать TS-синтаксис; diff-review хуже, чем по чистому `.md`; цель PO «редактировать промпт отдельно от TS-кода» формально нарушена (это всё ещё TS).
- **Объём прироста бандла:** идентичен варианту (1) — Vite инлайнит литералы. Может быть **немного меньше**, потому что нет накладных расходов на «default export» обёртку (но это байты единицы).

#### Вариант (3) — copy в `manifest.json` + `fetch()` в рантайме

- В Figma plugin sandbox/iframe работает обычный `fetch` (используется для Gemini API). Технически читать `prompt.md` через `fetch('./prompts/ai-suggestion.md')` теоретически возможно, **если файл разместить в `dist/`** и манифест Figma его подхватит.
- **Но:** `manifest.json` Figma-плагина (наш файл, 9 строк) поддерживает только `main` (sandbox JS) и `ui` (UI HTML). Других относительных путей плагину сделать недоступно — UI рендерится в iframe с `srcdoc`, отдельные файлы не сервится.
- На практике уже сейчас весь UI инлайнится в `ui.html` через `scripts/build-ui.mjs` — это вынужденная мера именно потому, что Figma не сервит дополнительные файлы.
- **Подтверждение ограничения:** Figma plugin iframe — это `srcdoc` без origin, у `fetch` относительных путей нет, а внешние URL заблокированы (CORS + manifest `networkAccess` — у нас `networkAccess` не задан вовсе).
- **Вывод:** **не подходит**. Runtime-fetch промпта изнутри плагина невозможен без изменения архитектуры (это и есть отвергнутый PO «уровень Г»).

#### Вариант (4) — esbuild loader / Vite custom plugin

Альтернативные механизмы, которые имеет смысл назвать ради полноты:

- **Vite `assetsInclude` + `import.meta.glob`** — для загрузки нескольких файлов одной директивой. Полезно при N≥3 промптов; для 2-х шаблонов overkill.
- **`fs.readFileSync` на этапе сборки через custom Vite plugin** — даёт ту же семантику, что `?raw`, но с лишним кодом. Не нужно.
- **Импорт как JSON (`.json`)** — Vite поддерживает из коробки, типизация работает. Допустим как промежуточный вариант: `prompt.json` со структурой `{ "templateA": "...", "templateB": "...", "system": "...", "componentSuffix": "..." }`. Минус: JSON требует escape `\n` и кавычек — теряется главное преимущество externalization (читабельность для PO).

### 2.3 Рекомендация по разделу

**Вариант (1) — `?raw`-импорт `.md`-файла** — закрывает цель PO «редактировать отдельно от TS-кода» с минимальной ценой: одна правка tsconfig + новая директория. Вариант (2) — приемлемый запасной, если PO решит, что новый суффикс импорта в проекте не нужен и достаточно изоляции в TS-модуле.

## 4. Формат placeholder-ов

### 4.1 Текущее состояние

Шаблон сшивается через **JS string concatenation**, без какого-либо placeholder-формата (`ReportView.tsx:185–194, 238–239`):

```ts
prompt = 'Violation: ' + current.currentValue + ' on node "' + current.nodeName +
  '". Suggested token: "' + tokenInfo.name + '" with value ' + tokenInfo.value +
  '. Explain in 1-2 short sentences why this token fits. ' +
  'No preamble, get straight to the point. Reply in English.';
```

После externalization этот код заменится на чтение шаблона + подстановку. Формат placeholder-а определяет, как именно будет выглядеть `.md`-файл и helper подстановки.

### 4.2 Варианты

#### Вариант (1) — `{{name}}` (mustache-style)

`.md`:

```markdown
Violation: {{currentValue}} on node "{{nodeName}}". Suggested token: "{{tokenName}}" with value {{tokenValue}}. Explain in 1-2 short sentences why this token fits. No preamble, get straight to the point. Reply in English.
```

Helper:

```ts
function fillTemplate(tpl: string, vars: Record<string, string>): string {
  return tpl.replace(/\{\{(\w+)\}\}/g, (_, key) => {
    if (!(key in vars)) throw new Error('Missing prompt placeholder: ' + key);
    return vars[key];
  });
}
```

- **Плюсы:** работает в `.md` без TS-обёртки; PO видит знакомый mustache-синтаксис; helper тривиальный (одна regex-замена); **безопасность по умолчанию**: `throw on missing` ловит опечатки в имени плейсхолдера и не уходят в API сообщения вроде `Hello {{componentName}}`.
- **Минусы:** новый микро-DSL в проекте. Никаких других DSL для шаблонов сейчас нет.
- **Объём:** helper ~150–200 B минифицированных в `ui.js`.

#### Вариант (2) — `${name}` (нативный TS template literal)

```ts
// файл должен быть .ts:
export const PROMPT_A = `Violation: ${currentValue} on node "${nodeName}". ...`;
```

- **Главная проблема:** `${...}` интерполируется **на месте определения константы**. Чтобы отложить подстановку, нужно делать функцию-фабрику: `(vars) => \`Violation: ${vars.currentValue} ...\``. Это уже не «декларативный шаблон», а код. Цель externalization (PO правит шаблон без TS) **не достигается**.
- **Плюсы:** zero-runtime cost (вычисление строки — нативный JS).
- **Минусы:** требует, чтобы файл был `.ts` (вариант 2 из п.2); PO правит TS-функцию; «забыл переменную» = `undefined` в строке без явной ошибки → текст «Hello undefined» уйдёт в Gemini API.
- **Безопасность:** **низкая.** `undefined` подставляется молча.

#### Вариант (3) — именованные плейсхолдеры через `String.replace` (та же идея, что (1), но синтаксис плейсхолдера другой)

Например, `${name}` (в `.md`-файле, не TS), `<name>`, `[[name]]`.

- Различия с (1) только косметические. Любой кастомный синтаксис работает одинаково.
- Рекомендую **не выбирать `${name}` в `.md`-файле**: это дезориентирует читателя — выглядит как template literal, но обрабатывается иначе.

#### Безопасность подстановки (общее требование)

Независимо от формата, helper должен:

1. **Бросать ошибку**, если в шаблоне есть placeholder, для которого нет значения. Тогда баг ловится при разработке/тестировании, а не утекает в API.
2. **Не падать**, если значение — пустая строка (это валидный кейс: `componentName` иногда отсутствует, но в нашей логике это решается на уровне ветвления, а не подстановки).
3. **Не делать html-escape / json-escape** — Gemini принимает plain text, любая дополнительная обработка только испортит prompt.

### 4.3 Рекомендация по разделу

**Вариант (1) — `{{name}}` + helper с `throw on missing`.** Это единственный вариант, который одновременно: (а) даёт PO чистый `.md`-файл без TS, (б) обеспечивает явную ошибку при опечатке/рассинхроне, (в) тривиален в реализации (~5 строк helper).

## 5. Размер прироста бандла

### 5.1 Текущие литералы (база для подсчёта)

Длины (через `wc -c` по диапазонам строк `ReportView.tsx`):

| Что | Строки | Длина (байт, включая JS-операторы и кавычки) |
|---|---|---|
| User-prompt шаблон A | 185–188 | 974 |
| User-prompt шаблон B | 191–194 | (~520, аналогично шаблону A) |
| Component context suffix | 237–240 | 193 |
| System-prompt | 252 | 126 |

Чистый текст промптов (без TS-операторов `'... ' + var + '...'`) — **порядка 700–750 B** для шаблона A, **~430 B** для шаблона B, **~140 B** для component-suffix, **~100 B** для system. Итого: **~1370–1420 B** чистого текста.

В TS-коде сейчас на эти промпты тратится **~1815 B** (с учётом операторов конкатенации, кавычек, переменных). После externalization этот код **сокращается до ~50 B на promptа** (одна функция `fill(template, { ... })`).

### 5.2 Рост от externalization

После переноса в `.md` (вариант 1, `{{name}}`):

| Компонент | Δ |
|---|---|
| Промпты в виде строк (попадают в `ui.js` как один константный экспорт) | +~1420 B чистого текста |
| Helper `fillTemplate` минифицированный | +~150–200 B |
| Удаление inline-конкатенации в `ReportView.tsx` | −~1500 B (исходник; в минифицированном бандле литералы и сейчас компактны, но операторы `+` и переменные занимают место) |
| Импорт `?raw` (один `import x from '...?raw'`) | +~30 B (ESM-обёртка) |

**Чистый прирост в `ui.js`:** **+50…+200 B** — фактически близко к нулю, может быть **отрицательным** (бандл уменьшится), потому что чистая строка минифицируется лучше, чем последовательность `'a' + b + 'c' + d`. Точная оценка возможна только после реальной сборки.

В `code.js` — **+0 B** (sandbox prompt-ы не использует).

### 5.3 Бюджет

Контекст из задачи: «текущий бюджет `code.js` +3.10 KB уже превышен». Этот snapshot подтверждает: бюджет относится к **`code.js`**, не к `ui.js`. Externalization промпта **не трогает `code.js`** — мера не пересекается с действующим бюджетом.

`ui.js` сейчас 690 628 B (~675 KB). +200 B в худшем случае = +0.03 % — пренебрежимо.

### 5.4 Рекомендация по разделу

Прирост **в пределах шума**. Бандл — не блокер для решения. Аргументы за/против externalization строятся на UX/процессе, не на байтах.

## 6. Риски миграции

### 6.1 Точность переноса литералов

`'...' + var + '...'` → `{{var}}`-подстановка может незаметно изменить prompt из-за **escape-символов и пробелов**. Конкретные точки риска:

- **Перенос строк.** Сейчас в коде нет `\n` — все промпты однострочные (склейка `+ ` сохраняет один пробел между словами). При переносе в `.md` редактор может вставить trailing newline, который отдастся в Gemini как лишний `\n`. Риск низкий, но требует diff-сравнения после миграции.
- **Кавычки.** В шаблонах есть `"{{nodeName}}"` (двойные внутри). В `.md` это рендерится как `"…"` без проблем, но при переключении PO на JSON-формат потребуется escape — лишний аргумент против JSON.
- **Component context suffix начинается с пробела** (`' Component context:...'`). Сейчас это работает корректно: `prompt += ' Component context...'` склеивается без двойного пробела. После externalization суффикс должен либо начинаться с пробела в файле, либо helper должен вставлять separator. **Рекомендация:** склейка через `'\n'` или `' '` в коде, не в файле — иначе PO случайно потеряет ведущий пробел при редактировании.

### 6.2 Health-check API-ключа в `Settings.tsx:54`

```ts
const text = await callGemini([{ role: 'user', content: 'Ответь одним словом: работает.' }], undefined, 32);
```

- Это **отдельный prompt**, на русском, без placeholders, без componentContext. Переносить ли его во внешний файл — отдельная развилка (см. п.7).
- Если переносить вместе — нужен второй файл или раздел в общем файле.
- Если **не переносить** — после миграции остаётся одна inline-строка в `Settings.tsx`. Это нарушает принцип «все промпты во внешнем файле», но допустимо как осознанное исключение (health-check — не product prompt, а служебная проверка коннекта).
- **Риск регрессии:** если PO решит перенести и health-check, нужно убедиться, что тестовый текст остаётся коротким (32 maxTokens — это мало) и на русском (если англ. — Gemini может ответить длиннее).

### 6.3 Tone и стилистика промпта

Текущие тексты — английский, императив, явный запрет на преамбулу. После выноса в файл PO теоретически сможет:

- Поменять язык (русский → утечка локализации в API без UI-локализации остального плагина).
- Удалить «No preamble, get straight to the point» → ответы Gemini станут длиннее, могут не уместиться в 200 maxTokens → обрыв ответа.
- Удалить «in 1-2 short sentences» → то же самое.

**Это не баг externalization** — это естественное последствие того, что промпт стал редактируемым. Но **должно быть зафиксировано** в комментарии в самом `.md` или в `README` каталога prompts: «не меняй maxTokens=200 в коде без проверки длины ответа».

Ответ на вопрос задачи «оставлять ли английский» — **это решает PO в момент применения шага, не разведка**. `@release-scribe` участвует только при коммите финальной версии; решение по содержанию — за PO. Snapshot-минимум: **сохранить текст идентичным**, иначе изменение поведения AI попадает в зону, исключённую из задачи («поведение AI не меняется»).

### 6.4 Тестируемость: гарантия идентичности до/после

Способы убедиться, что после миграции prompt **идентичен** старому:

1. **Побайтовое сравнение (offline).** Перед миграцией: запустить плагин в режиме разработки, перехватить prompt в момент `callGemini(...)` через `console.log(prompt)` и сохранить как baseline. После миграции: тот же сценарий → новый prompt. `diff` файлов должен быть пустым.
2. **Юнит-тест helper-а.** Прогнать `fillTemplate(template, fixtures)` и сравнить с захардкоженным `expected` (равным результату текущей конкатенации). Не требует Figma. Тестов в проекте сейчас нет — это создаёт прецедент. Не обязательно делать частью шага миграции.
3. **Ручной diff.** Side-by-side в редакторе: текущий код — новый шаблон с подставленными значениями. Достаточно для нашего объёма (4 константы).

**Рекомендация:** способ 1 (баseline-перехват) минимально достаточен. Способ 2 хорош, но шаг F17.12 не должен раздуваться до «введём тесты». Способ 3 — fallback при отсутствии возможности запустить плагин.

### 6.5 Регрессии в acceptance criteria закрытых фаз

- **Ф.17.5** (`componentContext`): изменение должно сохранить условия добавления суффикса (`result !== null && componentName !== undefined && tokenIds && tokenIds.length > 0 && snapshot && paletteNames.length > 0`). Эта логика — в TS-коде, она не уходит в `.md`. Риск низкий.
- **Ф.17.x** (acceptance: «Gemini отвечает 1–2 предложениями, без преамбулы»): зависит от текста промпта. Если PO в момент применения шага меняет текст → возможна регрессия. Если текст идентичен — регрессии нет.
- **Ф.12.5** (Health Score, отвергнут): не затрагивается.
- **Ф.7 / Ф.8** (детектор): не затрагивается, prompt — UI-only.

### 6.6 Рекомендация по разделу

Главные риски: **(а) случайное изменение текста промпта при copy-paste** (особенно ведущие/trailing whitespace) и **(б) расширение scope шага** (если PO решит «заодно поправить тон»). Оба риска снимаются явным AC: «после миграции prompt-строка для двух канонических кейсов байт-в-байт совпадает с baseline до миграции» и отдельным шагом «изменение текста промпта» — если и когда PO захочет.

## 7. System vs User prompt: один файл или разные

### 7.1 Текущее состояние

Четыре отдельных литерала, разной природы:

| Литерал | Где | Природа |
|---|---|---|
| System-prompt | `ReportView.tsx:252` | константный, без переменных |
| User-prompt шаблон A | `ReportView.tsx:185–188` | с переменными, ветка `current.candidates` |
| User-prompt шаблон B | `ReportView.tsx:191–194` | с переменными, ветка `suggestedToken`-fallback |
| Component context suffix | `ReportView.tsx:237–240` | с переменными, опциональный |
| Health-check user-prompt | `Settings.tsx:54` | константный, на русском |

### 7.2 Варианты

#### (а) Один файл с явными секциями

Например, `src/ui/prompts/ai-suggestion.md`:

```markdown
## SYSTEM
You are a designer assistant who explains design system token choices. Reply concisely and to the point, in English.

## USER_TEMPLATE_A
Violation: {{currentValue}} on node "{{nodeName}}". Suggested token: "{{tokenName}}" with value {{tokenValue}}. Explain in 1-2 short sentences why this token fits. No preamble, get straight to the point. Reply in English.

## USER_TEMPLATE_B
On node "{{nodeName}}" the value {{currentValue}} was previously linked to design system token "{{suggestedToken}}" but the link was detached. Explain in 1-2 short sentences why re-linking restores design system consistency. No preamble, get straight to the point. Reply in English.

## COMPONENT_CONTEXT_SUFFIX
 Component context: "{{componentName}}". Tokens used in this component: {{componentPalette}}.
```

- **Плюсы:** PO видит все промпты в одном месте; легко сравнивать тон и стиль; один import, один helper-парсер секций.
- **Минусы:** требует мини-парсера секций (`## SECTION` → раздел). Это второй микро-DSL поверх `{{name}}`. Helper становится сложнее (~30–40 строк вместо 5).
- **Альтернатива внутри (а):** хранить как **JSON** (`{ "system": "...", "templateA": "...", ... }`). Тогда парсер не нужен, но возвращаются проблемы JSON: escape `\n`, кавычки, читабельность ниже.

#### (б) Разные файлы по типу

```
src/ui/prompts/
├── system.md
├── user-template-a.md
├── user-template-b.md
└── component-context.md
```

- **Плюсы:** каждый файл — одна цель, без парсера; импорты независимые (`?raw` каждый); легко менять права/структуру в будущем.
- **Минусы:** N файлов на одну фичу; PO нужно открывать 4 разных файла чтобы понять полный prompt.

#### (в) Гибрид: один файл для всех user-template, system inline

- System-prompt — константа, без переменных, **48 слов**. Можно оставить inline (`SYSTEM_PROMPT = '...'` в новом `prompts.ts`), а в `.md` вынести только три user-шаблона.
- **Плюсы:** уменьшает scope миграции; system меняется крайне редко (не менялся с Ф.6).
- **Минусы:** непоследовательно — «часть промптов внешняя, часть нет». Усложняет ментальную модель «где лежит prompt».

#### (г) Health-check (`Settings.tsx:54`) — отдельный вопрос

Health-check — это **не product prompt**, а служебный echo-test. Кандидаты:

- Оставить inline в `Settings.tsx` — как «исключение, потому что не для AI-объяснений».
- Вынести в общий файл секцией `## HEALTH_CHECK` — для последовательности.
- Вынести в отдельный файл — overkill.

### 7.3 Рекомендация по разделу

**Вариант (а) — один файл с секциями `## SYSTEM` / `## USER_TEMPLATE_A` / `## USER_TEMPLATE_B` / `## COMPONENT_CONTEXT_SUFFIX` для product-prompt; health-check инлайн оставить в `Settings.tsx`** (с TODO-комментарием, что в v1.1 можно тоже вынести). Аргументы:

- PO видит весь product prompt одним взглядом.
- Парсер секций тривиален (`split(/^## (\w+)$/m)`).
- Health-check — другая природа (служебный, не для пользователя), его externalization не даёт ценности.

Альтернатива (б) — оправдана, если PO ожидает, что в будущем (v1.1+) появится несколько персонализированных промптов под разные типы нарушений (slot-aware ranking, severity-aware). Тогда «много файлов» масштабируется лучше «много секций».
