# Глоссарий

Раздел определяет язык продукта DesignLint AI. Он помогает дизайнерам, разработчикам и продакт-менеджерам говорить об одних и тех же сущностях одинаково, а команде — снимать неоднозначности на ревью спецификации, в коде и в UI плагина.

## Структура документа

Глоссарий разделён на две части по аудитории:

**Глоссарий продукта** — язык, который видит и понимает пользователь плагина. Используется в UI, копирайте, маркетинговых материалах, спецификациях для продакт-менеджера.

**Глоссарий реализации** — язык кода и архитектуры. Используется в отчётах сессий, code review, обсуждениях с разработчиком.

Спорные термины (например, `Token`) размещены в продуктовой части, в реализационной — короткая ссылка.

## Маркеры стабильности

Каждый термин имеет маркер, отражающий его статус:

🟢 **Стабильный** — реализован, проверен, не меняется. ⠀ 🟡 **Уточняется** — введён недавно, формулировка может меняться по результатам QA. ⠀ 🔵 **Запланирован** — заявлен в дорожной карте, в коде ещё нет. ⠀ ⚫ **Устаревший** — оставлен для совместимости с прошлыми отчётами, в новой работе не использовать.

## Правила оформления

**Один термин — одно определение.** Если у понятия два значения (Style как механизм Figma и Style как имя в коде), термины разделяются по контексту с пометкой в скобках.

**Похожие понятия различаются явно.** Skip vs Hide, Style vs Variable, Primitive vs Semantic — в каждом определении явно указано, чем отличаются от соседей. См. также раздел «Антипаттерны и ложные синонимы».

**Стиль формулировок зафиксирован.** Существительные — «X — это Y, который…». Действия — «X — это операция, при которой…». Состояния — «X — это состояние, в котором…».

**Англоязычный эквивалент в скобках,** если термин используется в Figma API, документации или UI плагина в английском написании.

**Реализация в курсиве** под определением, для технических терминов, где важна точка входа в код.

## Дизайн-система и токены

🟢 **Design system** — это единый источник дизайн-токенов и компонентов, на который опирается продукт. В контексте плагина может быть локальной (опубликованной в текущем файле Figma) или подключённой (из team library через механизм Figma Libraries). ⠀ _См. также: Local design system, Connected design system._

🟢 **Local design system** — это дизайн-система, токены и компоненты которой хранятся в текущем файле Figma и доступны без подключения внешних библиотек. ⠀ _См. также: Connected design system._

🟢 **Connected design system** — это дизайн-система, подключённая к файлу через team library. Её токены доступны для использования, но управляются в исходном файле-библиотеке. ⠀ _См. также: Local design system._

🟢 **Token** — это переиспользуемое значение из дизайн-системы (цвет, шрифт, отступ, радиус). Классифицируется по способу хранения (Style или Variable) и по уровню абстракции (Primitive или Semantic). ⠀ _См. также: Style, Variable, Primitive token, Semantic token._

🟢 **Style** — это исторический механизм Figma для хранения токена (PaintStyle, TextStyle, EffectStyle). Всегда обладает именем и потому считается семантичным по природе. ⠀ _Реализация: Figma API → `PaintStyle`, `TextStyle`._ ⠀ _См. также: Variable, Token source._

🟢 **Variable** — это современный механизм Figma для хранения токена. В отличие от Style поддерживает режимы (modes) и алиасы между переменными. Может быть primitive или semantic. ⠀ _Реализация: Figma API → `Variable`, `VARIABLE_ALIAS`._ ⠀ _См. также: Style, Bound variable, Primitive token, Semantic token._

🟢 **Primitive token** — это токен, хранящий «сырое» значение, например `#36499A` или `16px`. Базовый уровень абстракции, обычно не предназначен для прямого использования в продуктовых компонентах. ⠀ _См. также: Semantic token, Token policy._

🟢 **Semantic token** — это токен, выражающий назначение, а не значение (например, `color/brand/primary`). В Variable реализуется через алиас на другой переменной, в Style — через осмысленное имя. ⠀ _См. также: Primitive token, Token policy, Two-tier design system._

🟡 **Two-tier design system** — это архитектура дизайн-системы, в которой явно разделены два уровня токенов: примитивы (значения) и семантика (назначения). Плагин учитывает это разделение при выборе кандидатов для рекомендаций. ⠀ _См. также: Token policy, Semantic token._

🟢 **Bound variable** — это нода, у которой свойство (например, `fills[i].boundVariables.color`) уже ссылается на Variable. Такая нода не считается нарушением, так как использует токен корректно. ⠀ _Реализация: проверка в `detector.ts` при обходе нод._ ⠀ _См. также: Variable, Violation._

## Источники и политики выбора токенов

🟢 **Token source** — это пользовательская настройка, определяющая, какие хранилища токенов детектор рассматривает как пул кандидатов: только Variables, только Styles или оба источника (Both). ⠀ _См. также: Token policy, Candidate pool._

🟢 **Token policy** — это пользовательская настройка для two-tier ДС, определяющая уровень абстракции рекомендуемых токенов: только семантические (Semantic only) или все доступные (All tokens). ⠀ _См. также: Token source, Semantic token, Two-tier design system._

🟢 **Candidate pool** — это итоговый набор токенов, среди которых детектор ищет ближайшие совпадения. Формируется на пересечении Token source, Token policy и подключённых дизайн-систем. ⠀ _См. также: Candidates (в разделе AI), Token source, Token policy._

🟢 **Scope** — это область сканирования, выбираемая пользователем перед запуском проверки (например, выделенный фрейм, секция, страница). Ограничивает множество нод, по которым работает детектор. ⠀ _Реализация: `ScopeSelector.tsx`, передаётся в sandbox при `start-scan`._ ⠀ _См. также: Rescan._

## Нарушения и фильтрация

🟢 **Violation** — это нарушение использования токенов, найденное детектором. Описывается типом, категорией и привязкой к конкретной ноде. ⠀ _Реализация: `shared/types.ts → Violation`, поле `candidates: Array<{id, name, value}>`._ ⠀ _См. также: Violation type, Category, Active pool._

🟢 **Violation type** — это конкретная разновидность нарушения, определяющая логику детектора и формулировку рекомендации. Примеры: `hardcoded_color`, `detached_style`, `missing_text_style`. ⠀ _Реализация: `sandbox/detector.ts`._ ⠀ _См. также: Category, Hide._

🟢 **Category** — это группа типов нарушений, объединённых по смыслу для фильтрации на Dashboard (Colors, Typography, Layout). Используется в UI для тогглов с чекбоксами. ⠀ _См. также: Violation type, Active pool._

🟢 **Active pool** (активный пул) — это подмножество всех найденных нарушений, попадающее под текущий выбор категорий пользователя. Именно по нему считаются счётчики и формируется Review. ⠀ _Реализация: `App.tsx → selectedCategories`._ ⠀ _См. также: Filtered violations, Category._

🟢 **Filtered violations** — это производное (derived) значение в UI, представляющее активный пул. Является единым источником истины для Review-экрана и счётчиков, что предотвращает рассинхронизацию между фильтрами и отображением. ⠀ _Реализация: `App.tsx → filteredViolations` (derived, не state)._ ⠀ _См. также: Active pool. Антипаттерн: дублирование в state — см. раздел «Антипаттерны»._

🟢 **Ignored set** — это множество идентификаторов нарушений, пропущенных пользователем через действие Skip. Сохраняется в рамках сессии до Rescan. ⠀ _Реализация: `App.tsx → ignoredIds: Set<string>`._ ⠀ _См. также: Skip, Rescan._

🔵 **Hidden types** — это набор типов нарушений, скрытых пользователем через действие Hide на текущую сессию. ⠀ _См. также: Hide, Violation type._

## Действия пользователя

🟢 **Fix** — это операция применения выбранного токена-кандидата к ноде. После успешного выполнения нарушение удаляется из активного пула. ⠀ _Реализация: `sandbox/fixer.ts → fixViolation`, протокол `fix-violation` / `fix-complete`._ ⠀ _См. также: Bulk Fix, Undo, Skip._

🟢 **Skip** — это операция пропуска конкретного нарушения без применения токена. Нарушение остаётся в данных, но помещается в ignored set и не показывается в текущей сессии Review. ⠀ _См. также: Hide, Ignored set, Fix. Антипаттерн: путать со словом «Ignore» — см. раздел «Антипаттерны»._

🔵 **Hide** — это операция скрытия целого типа нарушений на сессию (например, отключить показ всех `similar_to_token`). Действует шире, чем Skip, и применяется к группе, а не к отдельной ноде. ⠀ _См. также: Skip, Hidden types, Violation type._

🔵 **Bulk Fix** — это операция пакетного применения Fix к нескольким нарушениям сразу. Использует тот же протокол, что и одиночный Fix, но проходит по активному пулу. ⠀ _Реализация: запланирована как `fixBatch` (шаг 10.C.2 в дорожной карте)._ ⠀ _См. также: Fix, Active pool._

🟢 **Undo** — это операция отката последнего применённого Fix через нативный Cmd+Z. Корректность отката обеспечивается вызовом `figma.commitUndo()` перед мутацией, что изолирует каждый Fix в отдельной undo-группе. ⠀ _Реализация: `sandbox/code.ts`, `commitUndo` ДО `fixViolation`._ ⠀ _См. также: Fix. Антипаттерн: вызов commitUndo после мутации — см. раздел «Антипаттерны»._

🟢 **Rescan** — это операция повторного запуска сканирования. Сбрасывает метрики сессии (`scoreBefore`, `sessionStartMs`, `fixedCount`), ignored set, hidden types и обновляет список нарушений. ⠀ _См. также: Detection, Report metrics._

## AI-рекомендации

🟢 **AI suggestion** — это рекомендация конкретного токена-кандидата, формируемая детектором по эвристике (топ-3 ближайших по дистанции в RGB или по разнице fontSize). Не требует обращения к внешнему AI. ⠀ _Реализация: `sandbox/detector.ts → candidates`._ ⠀ _См. также: Candidates, AI explanation._

🟢 **Candidates** — это массив топ-N кандидатов на исправление, прикреплённый к нарушению. Отображается в Combobox SelectField и используется как вход для Fix. ⠀ _Реализация: поле `candidates` в `Violation`, тип `Array<{id, name, value}>`._ ⠀ _См. также: AI suggestion, Candidate pool, SelectField._

🟢 **AI explanation** — это текстовое объяснение от внешней модели Gemini 2.5 Flash, почему выбранный кандидат подходит для конкретного нарушения. Кэшируется по паре `(violationId, tokenId)`. ⠀ _Реализация: `aiClient.ts → callGemini`, кэш в `ReviewFix.tsx → useRef<Map>`._ ⠀ _См. также: AI toggle, AI key._

🟢 **AI toggle** — это пользовательская настройка «Использовать AI» в Settings. При выключении AI-объяснения не запрашиваются и не отображаются, но эвристические AI suggestions продолжают работать. ⠀ _Реализация: ключ `ai-enabled` в `figma.clientStorage`._ ⠀ _См. также: AI explanation, AI suggestion. Антипаттерн: тоггл не удаляет ключ — см. раздел «Антипаттерны»._

🟢 **AI key** — это Google API key пользователя для доступа к Gemini, хранящийся в `figma.clientStorage` под ключом `google-api-key`. Вводится в Settings, может быть проверен через диагностический вызов. ⠀ _Реализация: `Settings.tsx`, миграция со старого `anthropic-api-key` в `sandbox/code.ts`._ ⠀ _См. также: AI toggle, AI explanation._

# Часть 2. Глоссарий реализации

## Технические состояния и протокол

🟢 **Detection** — это результат работы детектора: набор найденных нарушений с метаданными. На основе этой структуры строится UI Review. ⠀ _Реализация: `App.tsx → detection.violations`, событие `detection-complete`._ ⠀ _См. также: Violation, Rescan._

🟢 **Preview** — это изображение PNG в base64 текущего состояния ноды, экспортированное через `node.exportAsync` для отображения в карточке нарушения. Кэшируется по `nodeId`. ⠀ _Реализация: протокол `request-preview` / `preview-ready`, кэш в `ReviewFix.tsx → previewCacheRef`._ ⠀ _См. также: Plugin message._

🟢 **Report metrics** — это набор метрик финального экрана сессии (исправлено N из M, область проверки). Собираются в корневом компоненте App, чтобы пережить переходы между экранами. ⠀ _Реализация: `shared/types.ts → ReportMetrics`, рендер в `ReportView.tsx`._ ⠀ _См. также: Rescan._

🟢 **Scan error code** — это код критической ошибки сканирования (нет выделения, нет токенов в файле). При наличии кода UI показывает ErrorCard вместо обычного Dashboard-контента. ⠀ _Реализация: `App.tsx → scanErrorCode`, рендер `ErrorCard.tsx`._ ⠀ _См. также: Plugin message._

🟢 **Dashboard** — это агрегатор нарушений по категориям с тремя CTA: Fix all, Review one by one, Rescan. Показывается на Экране 2 после успешного скана (`status === 'done'`, `detection !== null`). В коде — `Dashboard.tsx`; в макете — фрейм 148:12219 с именем `ReviewFix`. Расхождение имени принято PO в Ф.16.4 (2026-05-08), фиксируется здесь во избежание путаницы с архивным фреймом макета `Dashboard` (148:12084, hidden). ⠀ _Реализация: `src/ui/components/Dashboard.tsx`._ ⠀ _См. также: Detection, Filtered violations._

🟢 **Sandbox** — это изолированная среда исполнения кода плагина в Figma, имеющая прямой доступ к API документа. Обменивается сообщениями с UI-слоем через `postMessage`. ⠀ _Реализация: точка входа `sandbox/code.ts`._ ⠀ _См. также: Plugin message._

🟢 **Plugin message** — это типизированное сообщение между UI и sandbox. Симметричность протокола (на каждый запрос гарантирован ответ, в том числе из catch-ветки) — архитектурное требование. ⠀ _Реализация: `shared/types.ts → PluginMessage`. Примеры: `start-scan`, `request-preview`, `preview-ready`, `fix-violation`, `fix-complete`, `get-ai-enabled`, `set-ai-enabled`._ ⠀ _См. также: Sandbox._

# Антипаттерны и ложные синонимы

Этот раздел фиксирует выученные уроки сессий разработки. Он отвечает на вопрос «чем термин _не является_ и с чем его _путают_».

**«Стиль» ≠ «Токен».** Style — это конкретный механизм Figma. Token — обобщающее понятие продукта, включающее и Style, и Variable. В UI плагина и копирайте используется Token.

**«Hide» ≠ «Skip».** Skip отменяет одно нарушение в текущей сессии (одна нода). Hide отключает целый тип нарушений до конца сессии (все ноды этого типа). При Rescan оба сбрасываются.

**«Skip» ≠ «Ignore» ≠ «Fix».** Skip помещает нарушение в ignored set, но не применяет токен. После Skip нода остаётся «грязной» в Figma — Fix не выполнен. В UI используется только термин Skip.

**`commitUndo` ДО мутации, не после.** API `figma.commitUndo()` означает «закрой предыдущую undo-группу и начни новую», а не «зафиксируй последнее действие». Вызов после мутации помещает Fix в старую группу — Cmd+Z откатывает пустую текущую. Закреплено в шаге 11.9.1.

**Тоггл AI не удаляет ключ.** Выключение AI через AI toggle оставляет `google-api-key` в clientStorage. Это сделано намеренно: пользователь может включить AI обратно без повторного ввода ключа.

**`filteredViolations` — derived, не state.** Хранение отфильтрованного списка в useState с синхронизацией через useEffect — типичный источник рассинхронизации между чекбоксами и Review. Решение зафиксировано в шаге BUG-2: производное значение на каждый рендер, единый источник правды.

**Health Score удалён намеренно.** Метрика «было N → стало M» убрана в Ф.14, потому что на малых ДС давала неинтерпретируемый результат (0→0). Не возвращать без сценария на средних/больших ДС.

**Bound variable ≠ Violation.** Нода со ссылкой на Variable через `boundVariables` использует токен корректно и нарушением не является. Детектор пропускает такие ноды.

# История изменений терминологии

Старое имя ⚫ устаревшее. ⠀ **v0.11.1 (Ф.11)** — введён термин **Candidates** (массив топ-N кандидатов в Violation).

# Как использовать этот глоссарий

**Как дополнять термины.** Новый термин добавляется в подходящий раздел в момент, когда он впервые появляется в коде, UI или обсуждении и используется хотя бы дважды. Маркер при добавлении — 🟡 (уточняется), переводится в 🟢 после первого QA-цикла.

**Кому показывать на ревью.** Глоссарий продукта — для ревью спецификации с продакт-менеджером и онбординга нового дизайнера. Глоссарий реализации — для code review и обсуждений архитектуры. Антипаттерны — для каждого нового участника команды в первый день.

**Как поддерживать актуальность.** Изменение определения термина приравнивается к изменению API: упоминается в отчёте сессии и в разделе «История изменений терминологии». Удаление термина допустимо только после удаления соответствующей сущности из кода и UI; до удаления — маркер ⚫ устаревший.

**Когда пересматривать определения.** При закрытии каждой фазы дорожной карты, перед публикацией версии (v1.0, v1.1) и при появлении нового слоя архитектуры (DTCG-импорт, мульти-ключи AI). Пересмотр включает проверку на дубли, устаревшие термины, расхождения между определением и фактической реализацией, актуальность маркеров стабильности.

# Инструкция 1. Как создать глоссарий с нуля

## Когда использовать эту инструкцию

Создаёшь новый продукт или подключился к существующему, где нет единого языка. Признаки нужды в глоссарии: участники называют одну сущность разными словами (Skip / Ignore / Pass), копирайт в UI расходится с обсуждением в чате, новый человек на онбординге переспрашивает термины.

Не создавай глоссарий на старте проекта — там ещё нет устоявшегося языка. Делай это, когда накопилось 15–20 терминов, которые уже используются в коде, UI или отчётах сессий.

---

## Шаг 1. Собери исходный материал

Перед написанием глоссария собери три источника:

**Код продукта.** Имена типов, полей, констант, протоколов сообщений. Это база технических терминов (`Violation`, `PluginMessage`, `candidates`).

**UI-копирайт.** Все строки, видимые пользователю: кнопки, лейблы, тосты, ошибки. Это база продуктовых терминов (Skip, Hide, Fix).

**Отчёты сессий и обсуждения.** Термины, возникающие в разговоре, но ещё не попавшие ни в код, ни в UI. Это база развивающихся терминов (Two-tier design system, AI suggestion).

Выгружай в один черновик без структуры — фильтровать будем дальше.

---

## Шаг 2. Раздели на две аудитории

У глоссария всегда две аудитории, которые не пересекаются:

**Продуктовая.** Видит пользователь, продакт-менеджер, маркетолог. Знает Token, не знает PluginMessage.

**Реализационная.** Видит разработчик и архитектор. Знает Sandbox, не интересуется UI-копирайтом.

Если в начале глоссарий получается на 30+ терминов, разделение обязательно. Спорные термины (которые принадлежат обеим — `Token`, `Variable`) клади в продуктовую часть, в реализационной оставляй короткую ссылку.

Если глоссарий ≤ 20 терминов — можно одной частью.

---

## Шаг 3. Сгруппируй термины по смыслу

Не алфавитный порядок и не порядок появления в коде. Группируй по тому, как термины связаны в голове у читателя.

Стандартные группы для продуктов с настройками и действиями:

```
Дизайн-система и токены      ← статика, объекты данных
Источники и политики          ← пользовательские настройки
Нарушения и фильтрация        ← результат работы продукта
Действия пользователя         ← что пользователь может сделать
AI-рекомендации               ← внешние интеграции (если есть)
Технические состояния         ← язык реализации
```

Если у тебя другой домен — придумай свои группы по тому же принципу: статика → настройки → результаты → действия → реализация.

В каждой группе должно быть 3–8 терминов. Если меньше 3 — объедини с соседней группой. Если больше 8 — раздели на подгруппы.

---

## Шаг 4. Зафиксируй стиль формулировок

До написания первого определения выбери и запиши шаблоны:

**Существительные:** «X — это Y, который…» Пример: «Token — это переиспользуемое значение из дизайн-системы».

**Действия:** «X — это операция, при которой…» Пример: «Fix — это операция применения выбранного токена-кандидата к ноде».

**Состояния:** «X — это состояние, в котором…» Пример: «Active pool — это подмножество всех найденных нарушений…».

Запиши эти шаблоны в раздел «Правила оформления» в начале глоссария. Это страховка от расползания стиля при пополнении в будущем.

---

## Шаг 5. Напиши определения

**Длина — одно предложение, максимум два.** Если не помещается — термин слишком общий, разбивай на два.

**Без bullet-точек внутри определения.** Только сплошной текст.

**Английский в скобках,** если термин используется в API или UI на английском: «Bound variable — это нода, у которой…».

**Различай похожие явно.** В определении Skip упомяни Hide. В определении Variable упомяни Style. Это страхует от ложных синонимов.

---

## Шаг 6. Добавь обвязку

Готовый список определений — это ещё не глоссарий, а словарь. Чтобы стал глоссарием, нужны:

**Связанные термины.** Под каждым определением — `См. также:` со списком 1–3 связанных. Это превращает плоский список в навигационную сеть.

**Привязка к коду.** Для технических терминов — курсивом `Реализация: <файл/модуль>`. Не указывай строки, они устаревают. Указывай только модуль или компонент.

**Маркеры стабильности.** 🟢 стабильный / 🟡 уточняется / 🔵 запланирован / ⚫ устаревший. Без них через 3 месяца неясно, где фундамент, а где эксперимент.

**Антипаттерны.** Отдельный раздел в конце с записями вида «X ≠ Y» — где зафиксированы выученные уроки. Это самая ценная часть глоссария после года использования.

**Жизненный цикл (если применимо).** Если в продукте есть последовательность действий (Detection → Violation → Fix → Undo) — нарисуй ASCII-диаграмму перед списком терминов. Это снимает 80% когнитивной нагрузки при чтении.

---

## Шаг 7. Добавь служебные разделы

**В начале:**

- Назначение глоссария (1 абзац: для кого и зачем)
- Структура документа (если 2 части — объясни разделение)
- Маркеры стабильности (легенда)
- Правила оформления (шаблоны из шага 4)

**В конце:**

- Антипаттерны и ложные синонимы
- История изменений терминологии (на старте — пустая, заполняется со временем)
- EN↔RU индекс (таблица для быстрого поиска)
- Как использовать этот глоссарий (правила пополнения, ревью, актуализации)

---

## Шаг 8. Прогон через ревью

Перед фиксацией версии 1.0 глоссария прогони по чек-листу:

|Проверка|Критерий|
|---|---|
|Каждый термин используется минимум 2 раза в коде/UI/отчётах|Если 1 раз — кандидат на удаление|
|Нет дубликатов смысла под разными именами|Skip и Pass = выбрать одно|
|Определение можно прочитать вслух за 10 секунд|Если дольше — режь|
|Связанные термины ведут на существующие записи|Битых ссылок не должно быть|
|Реализация курсивом указывает на актуальный модуль|Не на удалённые файлы|
|Антипаттерны включают минимум 3–5 записей|Иначе раздел не стоит делать|
|Стиль формулировок единообразен|Все существительные по одному шаблону|

После ревью — закрепляй версию, фиксируй файл в проекте, начинай пополнять по второй инструкции.

---

## Сколько времени это занимает

При 30–40 терминах — одна сессия 2–3 часа на черновик и ещё час на обвязку. При 60–80 терминах — две сессии: первая на сбор и группировку, вторая на определения и обвязку.

Не делай больше 80 терминов за раз — устанешь, начнёшь халтурить, последняя четверть будет хуже первой. Лучше выпустить v1.0 на 40 терминах и пополнить по второй инструкции.

# Инструкция 2. Как пополнять существующий глоссарий

## Принцип

Глоссарий — живой документ. Без дисциплины пополнения он за 3 месяца превращается в кладбище устаревших определений. Дисциплина простая: каждое изменение языка продукта проходит через глоссарий в момент изменения, а не «потом».

---

## Когда добавлять новый термин

Термин добавляется, когда выполнены все три условия:

1. **Использовался минимум дважды.** Один раз — это случайное слово в обсуждении. Два раза — уже паттерн.
2. **Имеет потенциал для путаницы.** Новый термин рядом с существующим, который легко спутать (новое `Pin` рядом с существующим `Hide`).
3. **Появился в коде, UI или официальном отчёте.** Не в чате на лету.

Если хотя бы одно условие не выполнено — подожди. Преждевременное добавление засоряет глоссарий и приучает не доверять ему.

---

## Процедура добавления

**1. Определи раздел.** Существующая группа или новая. Если для термина нет подходящей группы — это сигнал, что глоссарий перерос текущую структуру, нужен пересмотр (см. ниже).

**2. Маркер 🟡 при добавлении.** Любой новый термин получает «уточняется». Перевод в 🟢 — только после первого QA-цикла или явной фиксации в коде/UI.

**3. Напиши определение по шаблону.** Те самые шаблоны из шага 4 первой инструкции. Не изобретай новый стиль для одного термина.

**4. Добавь обвязку:**

- `См. также:` с минимум одной ссылкой на существующий термин
- `Реализация:` курсивом, если технический
- Антипаттерн в конце документа, если новый термин легко спутать с существующим

**5. Зафиксируй в «Истории изменений терминологии».** Одна строка: версия + что добавлено.

---

## Процедура изменения определения

Изменение определения существующего термина — это изменение API.

**1. Зафиксируй причину.** Что заставило переписать. Новый сценарий? Расхождение с кодом? Уточнение по результатам QA?

**2. Проверь связанные термины.** Если меняешь определение `Skip`, проверь, что определения `Hide`, `Ignored set`, `Fix` всё ещё корректны относительно нового определения.

**3. Обнови раздел «История изменений терминологии».** Одна строка: версия + что изменилось + почему.

**4. Если изменение фундаментальное** (поменяли смысл, а не уточнили формулировку) — пройди по коду и UI поиском по термину, проверь, что нигде не используется в старом смысле.

---

## Процедура удаления термина

Удалять можно только в два захода.

**Заход 1.** Меняешь маркер на ⚫ устаревший, добавляешь в определение строку «_Удалить в версии vX.Y. Заменён на: <новый термин>_». Оставляешь термин в файле для совместимости с прошлыми отчётами.

**Заход 2.** Через одну-две версии после удаления соответствующей сущности из кода и UI — удаляешь термин полностью. Запись в «Истории изменений» обязательна.

Никогда не удаляй термин в один проход. Старые отчёты сессий ссылаются на него — без переходного маркера читатель решит, что отчёт устарел или содержит ошибку.

---

## Когда пересматривать структуру

Раз в фазу дорожной карты, перед публикацией мажорной версии (v1.0, v2.0) и при появлении нового архитектурного слоя.

**Чек-лист пересмотра:**

|Проверка|Что делать при провале|
|---|---|
|Каждый термин 🟢 встречается в текущем коде/UI|Перевести в ⚫, спланировать удаление|
|Нет терминов 🟡 старше двух версий|Перевести в 🟢 или удалить — «уточнения» не должны висеть вечно|
|Нет терминов 🔵, которых так и не реализовали|Удалить или перенести в backlog продукта|
|В каждой группе 3–8 терминов|Объединить или разбить группы|
|EN↔RU индекс совпадает с актуальным списком|Регенерировать|
|Антипаттерны актуальны|Удалить устаревшие, добавить новые из последних сессий|

Пересмотр занимает 30–60 минут и должен быть отдельным шагом в дорожной карте, не «фоном».

---

## Что писать в раздел «Антипаттерны»

Антипаттерн добавляется по результатам реальной путаницы или бага. Не превентивно.

Хорошие триггеры:

- Тестировщик или новый участник перепутал два термина
- В code review всплыл вопрос «а это то же, что и…»
- Возник баг из-за неверного понимания семантики (как с `commitUndo` до/после мутации)

Формат записи:

**«Term A» ≠ «Term B».** Term A делает X. Term B делает Y. Различие в том-то.

Если объяснение длиннее двух предложений — это уже не антипаттерн, а отдельная заметка. Перенеси в архитектурную документацию.

---

## Что не делать никогда

**Не добавлять термины «на всякий случай».** Если термин не используется дважды — он мусор.

**Не дублировать определение в разных группах.** Один термин — одно место. Если кажется, что нужен в двух — выбери основное, во второе клади ссылку «См. <раздел>».

**Не оставлять незаполненные обвязки.** Определение без `См. также:` — это сигнал, что термин изолирован, и стоит подумать, нужен ли он вообще.

**Не пересматривать структуру вне ритуала.** Большие переборы посреди фазы ломают концентрацию. Дождись закрытия фазы.

**Не делать пересмотр в одиночку для команды больше 3 человек.** Глоссарий — общий язык, ревью пересмотра обязательно.

---

## Признаки, что глоссарий деградирует

Если хоть один из признаков появился — пора делать внеплановый пересмотр:

- В отчётах сессий или обсуждениях встречаются термины, которых нет в глоссарии (не успеваете пополнять).
- Определения противоречат коду (изменили реализацию, не обновили глоссарий).
- Связанные термины ведут на удалённые записи.
- В команде снова появились синонимы (Skip / Pass / Ignore используются вперемешку).
- Маркеры 🟡 не двигаются в 🟢 месяцами.
- Антипаттерны не пополняются — значит, либо команда не натыкается на путаницу (хорошо), либо натыкается, но не фиксирует (плохо).

Первый признак — нормальный, лечится одной сессией пополнения. Все остальные — серьёзный сигнал, что глоссарий потерял доверие команды и не используется как источник правды.

Исходные не полные данные:

- **Design system** — источник дизайн-токенов и компонентов. Бывает **локальная** (в текущем файле) и **подключённая** (из библиотеки через team library).
- **Token** — переиспользуемое значение из дизайн-системы. Делится по способу хранения (Style / Variable) и по уровню абстракции (Primitive / Semantic).
- **Style** — Figma PaintStyle/TextStyle, исторический способ хранения. Всегда «семантичен» по природе (имеет имя).
- **Variable** — Figma Variable, новый способ. Может быть **primitive** (raw-значение `#36499A`) или **semantic** (алиас на другую переменную через `VARIABLE_ALIAS`).
- **Token source** — выбор пользователя: что детектор использует как пул кандидатов (Variables / Styles / Both).
- **Token policy** — выбор пользователя для two-tier ДС: рекомендовать только семантику (Semantic only) или всё (All tokens).
- **Violation** — нарушение, найденное детектором. Имеет тип (`hardcoded_color`, `detached_style`, `missing_text_style` и т.д.) и категорию (Colors / Typography / Layout).
- **Category** — группа типов нарушений для UI-фильтрации на Dashboard.
- **Active pool** (активный пул) — подмножество `detection.violations`, попадающее под текущий `selectedCategories`.
- **Fix** — применение токена-кандидата к ноде через sandbox. После Fix violation удаляется из `detection.violations`.
- **Skip** — пропуск нарушения без применения. Не удаляет из списка, но добавляет в `ignoredIds`.
- **Hide** — скрытие типа нарушения на сессию (например, «не показывать `similar_to_token`»).
- **AI suggestion** — рекомендация конкретного токена-кандидата детектором (топ-3 ближайших по hex или fontSize).
- **AI explanation** — текстовое объяснение от Gemini, почему выбранный токен подходит.
- **Bound variable** — нода, у которой `fills[i].boundVariables.color` указывает на Variable. Не нарушение.
