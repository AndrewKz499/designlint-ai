# Тест-матрицы DesignLint AI

## Назначение

Документ фиксирует покрытие пересечений входных условий продукта DesignLint AI с явными ожидаемыми результатами. Используется QA для прогона перед релизом v1.0, разработчиком — как контракт на корректность, продакт-менеджером — как карта известных ограничений и запланированных доработок. Документ дополняет глоссарий (термины), жизненные циклы (динамика данных) и user flows (линейные сценарии): тест-матрицы покрывают то, что flows не покрывают по своей природе — комбинаторику.

## Условные обозначения

```
✅  Работает корректно
⚠   Работает с предупреждением (известное ограничение, есть пояснение)
❌  Не работает (баг, есть привязка к тикету или backlog)
🚫  Невозможная комбинация (UI блокирует или валидация исключает)
—   Не применимо (комбинация не имеет смысла)
🔵  Запланировано в v1.1
```

В ячейках — короткое описание ожидаемого результата (1–2 фразы) + маркер. Без маркера ячейка не считается заполненной.

## Маркеры стабильности матриц

🟢 **Стабильная** — матрица заполнена, прогнана QA, ячейки актуальны. ⠀ 🟡 **Уточняется** — заполнена, но часть ячеек требует допроверки. ⠀ 🔵 **Запланирована** — оси определены, ячейки не заполнены. ⠀ ⚫ **Устаревшая** — заменена другой матрицей, оставлена для совместимости отчётов.

# Матрица 1. Типы нарушений × действия

**Назначение:** проверить, что все 6 типов нарушений корректно детектируются и обрабатываются всеми пользовательскими действиями.
**Связанные flows:** Flow 1, Flow 3, Flow 4.
**Связанные термины:** Violation type, Detection, Fix, Skip, Hide, Bound variable.
**Маркер:** 🟢

## Оси

- **Строки:** 6 типов нарушений (`hardcoded_color`, `detached_style`, `missing_text_style`, `similar_to_token`, `hardcoded_spacing`, `hardcoded_radius`).
- **Колонки:** Detect, Fix, Skip, Hide.

## Матрица

| Тип нарушения ↓ \ Действие → | Detect | Fix | Skip | Hide |
|---|---|---|---|---|
| `hardcoded_color` | ✅ Кандидаты топ-3 по RGB-дистанции | ✅ Применяет fillStyle / Variable, нода становится Bound variable | ✅ В ignored set, активный пул −1 | ✅ Тип в hiddenTypes, все нарушения этого типа из активного пула |
| `detached_style` | ✅ Кандидат — исходный отвязанный стиль (топ-1 по имени) | ✅ Привязывает обратно через `setStyleId` | ✅ В ignored set | ✅ Тип в hiddenTypes |
| `missing_text_style` | ✅ Кандидаты топ-3 по fontSize / fontFamily | ✅ Применяет TextStyle через `setTextStyleId` | ✅ В ignored set | ✅ Тип в hiddenTypes |
| `similar_to_token` | ✅ Кандидат — ближайший токен по дистанции | ⚠ Применяет, но без явного предупреждения о замене (UX-долг Ф.13) | ✅ В ignored set | 🔵 v1.1 — UI-тоггл «не показывать этот тип впредь» |
| `hardcoded_spacing` | 🔵 v1.1 — детектор для Auto Layout gap / padding | — | — | — |
| `hardcoded_radius` | 🔵 v1.1 — детектор для cornerRadius | — | — | — |

## Известные пробелы

- `hardcoded_spacing` и `hardcoded_radius` запланированы в v1.1 — на синтетической ДС соответствующие ноды детектор пропускает, регрессия не проверяется.
- Hide для `similar_to_token` запланирован в v1.1 — пользователь может Skip-нуть конкретное нарушение, но не отключить тип целиком.
- Не покрыт случай `Bound variable` со сломанным алиасом (Variable удалена в библиотеке) — детектор сейчас считает такую ноду корректной, баг BUG-47.

## Тестовые данные

- `test-fixtures/all-violation-types.fig` — синтетическая ДС, по 5 нод на каждый тип = 30 нарушений. Пути нод задокументированы в комментариях слоёв.
- Для `similar_to_token` — отдельная подсекция с парами «нода — близкий, но не идентичный токен».

# Матрица 2. Token source × Token policy

**Назначение:** проверить корректность candidate pool при всех комбинациях настроек.
**Связанные flows:** Flow 5, Flow 8.
**Связанные термины:** Token source, Token policy, Candidate pool, Primitive token, Semantic token, Two-tier design system.
**Маркер:** 🟢

## Оси

- **Строки:** Token source (`Variables`, `Styles`, `Both`).
- **Колонки:** Token policy (`All tokens`, `Semantic only`).

## Матрица

| Token source ↓ \ Token policy → | All tokens | Semantic only |
|---|---|---|
| Variables | ✅ Все Variables (primitive + semantic) в кандидатах | ✅ Только semantic Variables (определяются по `VARIABLE_ALIAS`) |
| Styles | ✅ Все Styles в кандидатах (Styles всегда семантичны по природе) | ✅ Все Styles (semantic-only фактически = all для Styles) |
| Both | ✅ Variables (все) + Styles (все) | ✅ Semantic Variables + Styles (все) |

## Известные пробелы

- Если в файле нет Variables — UI блокирует выбор `Token source: Variables` (комбинация 🚫 на уровне Scope selector, в матрицу не попадает).
- Если в файле нет Styles — аналогично, UI блокирует `Token source: Styles`.
- Two-tier классификация Variables по `VARIABLE_ALIAS` проверяется только на синтетической two-tier ДС — на реальных проектных ДС возможны нестандартные паттерны алиасов (например, цепочки длиннее одного звена), не покрыты QA.

## Тестовые данные

- `test-fixtures/ds-two-tier.fig` — содержит ~100 primitive Variables + ~30 semantic Variables через `VARIABLE_ALIAS` + набор Styles. Покрывает все 6 ячеек.
- `test-fixtures/ds-styles-only.fig` — только Styles, для проверки строки `Styles`.
- `test-fixtures/ds-vars-only.fig` — только Variables, для строки `Variables`.

**Связанные flows:** Flow 7C (восстановление через ErrorCard для отсутствующего ключа).
**Связанные термины:** AI toggle, AI key, AI suggestion, AI explanation, Candidates.
**Маркер:** 🟢

- **Колонки:** состояние ключа (`отсутствует`, `валидный`, `невалидный`).

|---|---|---|---|

- Диагностический вызов для проверки валидности ключа (кнопка «Проверить» в Settings) запланирован, в v1.0 отсутствует — пользователь узнаёт о невалидности только при первом реальном запросе.

- Для «невалидный ключ» — ввести в Settings строку из случайных символов длиной как реальный ключ.
- Для «отсутствует» — `figma.clientStorage.deleteAsync('google-api-key')` в консоли sandbox или чистая инсталляция плагина.

# Известные пробелы покрытия (cross-matrix)

Эти пробелы не привязаны к одной матрице, а возникают на пересечениях двух и более матриц. Фиксируются здесь, чтобы не множить колонки / строки в каждой матрице.

- **AI explanation × Bulk Fix.** При Bulk Fix AI explanation не запрашивается (по дизайну — Bulk не открывает карточки). Запросы AI explanation возможны только для нарушений, оставшихся в активном пуле после Bulk. Пересечение Матрицы 1 (Fix), Матрицы 4 (Bulk Fix) и Матрицы 5 (AI).
- **Token policy × тип нарушения.** Для `detached_style` policy `semantic-only` не имеет эффекта (Styles всегда семантичны). Это корректно, но избыточно фиксировать в Матрице 1 и Матрице 2 — оставлено как нетривиальная сноска.
- **Размер ДС × Snapshot lifecycle.** На L первый Snapshot build занимает 10–20 с, у пользователя нет визуальной обратной связи кроме общего Spinner. UX-долг BUG-29.
- **Системное событие × AI key.** Cmd+Z во время загрузки AI explanation не имеет эффекта, но при последующем нажатии Fix на той же карточке кэш может оказаться неактуальным. Не воспроизводилось стабильно, требует дополнительного исследования.

# Связь с глоссарием, циклами и flows

Четыре документа работают вместе как единый контракт:

```
Глоссарий       ←─── что значит каждый термин (статика)
Жизненные циклы ←─── как термины движутся во времени (динамика данных)
User flows      ←─── как пользователь проходит через продукт (линейные сценарии)
Тест-матрицы    ←─── как термины пересекаются в комбинациях (комбинаторика)
```

**Правила синхронизации:**

- Все термины в осях матриц — должны быть в глоссарии. Если нет — сначала глоссарий, потом матрица.
- В шапке каждой матрицы — `Связанные flows`. Если flow ещё нет — это сигнал, что не хватает linear-описания и матрица описывает «голую» комбинаторику без сценария.
- Если матрица фиксирует ⚠ или ❌ — этот случай должен быть упомянут в edge-cases соответствующего flow.
