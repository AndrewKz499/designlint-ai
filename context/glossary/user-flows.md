# User flows DesignLint AI

## Назначение

Документ описывает поведение плагина DesignLint AI как последовательности действий пользователя с фиксацией состояния продукта на каждом шаге. Используется QA для прогона релизов, разработчиком и дизайнером — как единая точка истины при разногласиях «так и должно работать или это баг», продакт-менеджером — для проверки покрытия функциональности перед релизом v1.0. Документ дополняет глоссарий (термины) и раздел жизненных циклов (динамика данных): flows показывают, как термины и циклы складываются в реальный пользовательский опыт.

## Условные обозначения

```
[State]   — состояние продукта (Dashboard, Review, Settings, ErrorCard)
{Data}    — состояние данных (active pool: 12, ignored: 0, fixedCount: 3)
→         — переход (нажатие, выбор, событие)
↩         — возврат к предыдущему flow или шагу
⚙         — системное событие без действия пользователя
```

## Маркеры стабильности

Используются те же обозначения, что в глоссарии и в разделе жизненных циклов:

🟢 **Стабильный** — flow реализован и проверен. ⠀ 🟡 **Уточняется** — реализован, но граничные случаи в QA не закрыты. ⠀ 🔵 **Запланирован** — в дорожной карте, в коде ещё нет. ⠀ ⚫ **Устаревший** — оставлен для совместимости отчётов.

# Flow 1. Полный аудит без фильтров

**Цель пользователя:** проверить весь выбранный фрейм на нарушения и исправить всё подряд, не разбираясь по категориям.
**Тип:** happy path.
**Маркер:** 🟢
**Связанные термины глоссария:** Scope, Scan, Active pool, Violation, Candidates, Fix, Rescan, Report metrics.

## Предусловия

- Плагин открыт, инициализация прошла без ошибок.
- В Figma выделен один фрейм с ~50 нодами.
- В файле есть локальная ДС с variables (≥ 10 цветов, ≥ 5 шрифтов).
- AI toggle: выключен (фокус на эвристических кандидатах, без сетевых вызовов).

## Шаги

| # | Действие пользователя | Состояние UI | Состояние данных |
|---|----------------------|--------------|------------------|
| 1 | Открывает плагин из меню Figma | [Scope selector] | {tokenSource: 'both', tokenPolicy: 'all-tokens', aiEnabled: false} |
| 2 | Оставляет настройки по умолчанию, нажимает Scan | [Loading] | {scope: 'selection'} |
| 3 | Ждёт завершения сканирования (~2 сек) | [Dashboard] | {active pool: 47, selectedCategories: all, ignoredIds: ∅, hiddenTypes: ∅, fixedCount: 0} |
| 4 | Нажимает «Review» на категории Colors | [Review: Colors] | {filteredViolations: 31} |
| 5 | На карточке первого нарушения выбирает top-1 кандидат и нажимает Fix | [Review: Colors] | {active pool: 46, fixedCount: 1} |
| 6 | Повторяет шаг 5 для оставшихся 30 нарушений Colors | [Review: Colors] | {active pool: 16, fixedCount: 31} |
| 7 | Возвращается на Dashboard через Back | [Dashboard] | {active pool: 16, selectedCategories: all (сохранены)} |
| 8 | Нажимает «Review» на Typography, повторяет Fix для всех 10 нарушений | [Review: Typography] → [Dashboard] | {active pool: 6, fixedCount: 41} |
| 9 | Нажимает «Review» на Layout, повторяет Fix для всех 6 | [Review: Layout] → [Dashboard] | {active pool: 0, fixedCount: 47} |
| 10 | Нажимает Done | [ReportView] | {fixedCount: 47, totalFound: 47, durationMs: ~120000, scope: 'selection'} |
| 11 | Нажимает Rescan | [Loading] → [Dashboard] | {active pool: 0 или малое число, fixedCount: 0, ignoredIds: ∅, hiddenTypes: ∅} |

## Постусловие

- Все 47 нарушений исправлены в документе Figma (применены токены).
- ReportView показал «47 из 47 за ~2 минуты».
- После Rescan активный пул пуст или содержит несколько новых нарушений (если применение Fix внесло побочные).

## Связанные flows

- При появлении ошибки на любом шаге → **Восстановление через ErrorCard**.
- При желании отменить последний Fix → **Cmd+Z после Fix**.
- При желании работать только по одной категории → **Отфильтрованный аудит по категории**.

## Edge-cases

- **На шаге 5 пользователь меняет кандидата на top-2 или top-3.** Поведение Fix идентично, меняется только `tokenId` в протоколе. Активный пул уменьшается так же.
- **На шаге 6 одно из нарушений падает с `fix-complete error` (нода удалена в Figma параллельно).** Тост с ошибкой, нарушение остаётся в активном пуле, `fixedCount` не инкрементируется.
- **На шаге 11 после Rescan появляется больше нарушений, чем было.** Возможно, применение токенов через `setBoundVariable` вскрыло вторичные нарушения. Это допустимое поведение, не баг.

# Flow 2. Отфильтрованный аудит по категории

**Цель пользователя:** исправить только Typography, остальное оставить как есть для другого спринта.
**Тип:** альтернативный.
**Маркер:** 🟢
**Связанные термины глоссария:** Category, Active pool, Filtered violations, selectedCategories, Fix.

## Предусловия

- Завершён Scan (см. Flow 1, шаги 1–3).
- На Dashboard `{active pool: 47, selectedCategories: all}`.

## Шаги

| # | Действие пользователя | Состояние UI | Состояние данных |
|---|----------------------|--------------|------------------|
| 1 | На Dashboard снимает чекбоксы Colors и Layout | [Dashboard] | {selectedCategories: {Typography}, filteredViolations: 10} |
| 2 | Нажимает Review | [Review: Typography] | {filteredViolations: 10, отображаемых карточек: 10} |
| 3 | Применяет Fix к 8 из 10 нарушений | [Review: Typography] | {active pool: 39, filteredViolations: 2, fixedCount: 8} |
| 4 | Нажимает Back | [Dashboard] | {active pool: 39, selectedCategories: {Typography} (сохранён выбор)} |
| 5 | Включает обратно Colors и Layout | [Dashboard] | {selectedCategories: all, filteredViolations: 39} |
| 6 | Закрывает плагин | — | {state потерян, в Figma остались 39 нарушений Colors+Layout исправлены 8 Typography} |

## Постусловие

- В Figma исправлены 8 Typography-нарушений.
- 39 нарушений Colors и Layout остались нетронутыми.
- При повторном открытии плагина состояние UI начинается с нуля, но изменения в документе сохранены.

## Связанные flows

- Если на шаге 4 пользователь нажимает Done вместо Back → **Полный аудит без фильтров** (часть с ReportView).
- Если на шаге 1 хочется скрыть конкретный тип, а не категорию → **Skip + Hide во время Review**.

## Edge-cases

- **На шаге 1 пользователь снимает все три чекбокса.** `filteredViolations: 0`, кнопка Review дизейблится. Подсказка «Выберите хотя бы одну категорию».
- **На шаге 4 пользователь нажимает Rescan вместо Back.** `selectedCategories` сбрасывается до defaults (см. Rescan cycle). Это известное поведение — Rescan возвращает чистое состояние UI-фильтров.
- **На шаге 2 в категории 0 нарушений** (например, выбрали Layout в файле без layout-нарушений). Review показывает empty state «Всё чисто в этой категории» с кнопкой Back.

# Flow 3. Skip + Hide во время Review

**Цель пользователя:** пройти Review, отложить два конкретных нарушения и скрыть целый тип, который сейчас не интересен.
**Тип:** альтернативный.
**Маркер:** 🟢
**Связанные термины глоссария:** Skip, Hide, Ignored set, Hidden types, Active pool, Filtered violations.

## Предусловия

- Завершён Scan, на Dashboard `{active pool: 47}`.
- Пользователь зашёл в Review категории Colors с `filteredViolations: 31`.

## Шаги

| # | Действие пользователя | Состояние UI | Состояние данных |
|---|----------------------|--------------|------------------|
| 1 | На карточке нарушения типа `hardcoded_color` нажимает Skip | [Review: Colors] | {ignoredIds: {v17}, отображаемых карточек: 30, active pool: 47 (не изменился)} |
| 2 | На следующей карточке того же типа нажимает Skip ещё раз | [Review: Colors] | {ignoredIds: {v17, v23}, отображаемых карточек: 29} |
| 3 | На карточке нарушения типа `similar_to_token` нажимает Hide на тип | [Review: Colors] | {hiddenTypes: {similar_to_token}, отображаемых карточек: 23 (скрыто 6 нарушений этого типа)} |
| 4 | Применяет Fix к 20 оставшимся нарушениям | [Review: Colors] | {active pool: 27, fixedCount: 20, ignoredIds: {v17, v23}, hiddenTypes: {similar_to_token}} |
| 5 | Возвращается на Dashboard через Back | [Dashboard] | {счётчик Colors: 11 (= 47 − 31 + 20 − 5… по факту: исходно 31, минус 20 fix, остаются 11; ignored 2 + hidden 6 + 3 нетронутых)} |
| 6 | Смотрит на счётчик Colors: видит «11», в подсказке «(2 пропущено, 6 скрыто)» | [Dashboard] | без изменений |
| 7 | Нажимает Rescan | [Loading] → [Dashboard] | {ignoredIds: ∅, hiddenTypes: ∅, fixedCount: 0, active pool: пересчитан} |

## Постусловие

- Документ Figma: 20 нарушений исправлены, 27 остались (включая 2 Skip-нутых и 6 Hide-нутых).
- После Rescan ignoredIds и hiddenTypes сброшены, ранее Skip/Hide-нутые нарушения снова видны.

## Связанные flows

- Если пользователь хочет скрыть категорию целиком, а не тип → **Отфильтрованный аудит по категории**.
- При попытке Fix Skip-нутого нарушения через возврат — карточка не показывается до Rescan, доступа к Fix нет.

## Edge-cases

- **На шаге 3 в категории остался один тип нарушений, и его Hide-нули.** `filteredViolations: 0`, Review показывает empty state.
- **На шаге 6 пользователь хочет вернуть Skip-нутое нарушение без Rescan.** В v1.0 это невозможно: единственный способ — Rescan. Для v1.1 запланирована кнопка «Показать пропущенные».
- **Между шагами 1 и 2 пользователь меняет фильтр категорий.** ignoredIds сохраняются (привязаны к `violationId`, не к категории), при возврате в Colors будут учтены.
- **Skip и Hide не пишут в Figma.** Закрытие плагина без Fix оставит ноды в исходном состоянии — это намеренное поведение.

# Flow 4. Bulk Fix по отфильтрованному пулу

**Цель пользователя:** одним действием применить top-1 кандидата ко всем нарушениям активного пула.
**Тип:** happy path.
**Маркер:** 🔵 (запланирован, шаг 10.C.2 дорожной карты)
**Связанные термины глоссария:** Bulk Fix, Active pool, Candidates, Fix.

## Предусловия

- Завершён Scan, на Dashboard `{active pool: 47}`.
- Пользователь снял чекбокс Layout: `{selectedCategories: {Colors, Typography}, filteredViolations: 41}`.
- У всех 41 нарушений непустой массив candidates (top-1 определён).

## Шаги

| # | Действие пользователя | Состояние UI | Состояние данных |
|---|----------------------|--------------|------------------|
| 1 | На Dashboard нажимает Bulk Fix | [Confirmation modal] | {batchSize: 41} |
| 2 | В модалке «Применить top-1 ко всем 41 нарушениям?» нажимает Apply | [Loading с прогресс-баром] | {batchProgress: 0/41} |
| 3 | Ждёт завершения, прогресс-бар обновляется по `fix-batch-progress` | [Loading: 12/41, 24/41, 36/41] | {batchProgress растёт} |
| 4 | Получает результат | [Dashboard] | {active pool: 6 (Layout) + 0 ошибок = 6, fixedCount: 41} |
| 5 | Опционально нажимает Done | [ReportView] | {fixedCount: 41 из 47, batchSummary: «41 успешно, 0 ошибок»} |

## Постусловие

- В Figma применены 41 токен-кандидат top-1.
- Layout-нарушения остались нетронутыми (не входили в активный пул из-за фильтра).

## Связанные flows

- Если в активном пуле есть нарушения с пустыми candidates → они пропускаются Bulk Fix, остаются в активном пуле.
- Если пользователь хочет выбрать кандидаты вручную → **Полный аудит без фильтров** (одиночные Fix).

## Edge-cases

- **На шаге 3 часть Fix падает (например, 5 из 41).** Прогресс доходит до 41/41, но `fix-batch-complete` сообщает `{success: 36, errors: 5}`. UI показывает список ошибок, упавшие нарушения остаются в активном пуле.
- **Пользователь прерывает Bulk Fix на шаге 3.** Уже применённые Fix остаются в Figma. Откат — серия Cmd+Z. UI обновляется по факту полученных `fix-batch-progress`.
- **Bulk Fix запущен на пустом активном пуле.** Кнопка должна быть дизейблена. Если каким-то образом нажата — модалка не открывается.
- **В активном пуле есть нарушения нескольких типов с одинаковым top-1 кандидатом, но разной семантикой** — Bulk Fix не разбирается, применяет top-1 механически. Это сознательная цена пакетной операции.

# Flow 5. Смена token source / token policy после Scan

**Цель пользователя:** после первого скана понять, что хотел искать только в Variables, а не в обоих источниках; пересмотреть результаты.
**Тип:** альтернативный.
**Маркер:** 🟡 (UX подсказки уточняется в QA)
**Связанные термины глоссария:** Token source, Token policy, Candidate pool, Rescan.

## Предусловия

- Завершён Scan с `{tokenSource: 'both', tokenPolicy: 'all-tokens'}`.
- На Dashboard `{active pool: 47}`.

## Шаги

| # | Действие пользователя | Состояние UI | Состояние данных |
|---|----------------------|--------------|------------------|
| 1 | Нажимает шестерёнку → Settings | [Settings] | без изменений |
| 2 | Меняет tokenSource на 'variables' | [Settings] | {tokenSource: 'variables', баннер «Настройка применится при следующем Rescan»} |
| 3 | Нажимает Back на Dashboard | [Dashboard] | {active pool: 47 (не пересчитан), баннер «Настройки изменились — нужен Rescan»} |
| 4 | Нажимает Rescan | [Loading] → [Dashboard] | {active pool: пересчитан с новым Candidate pool, ignoredIds: ∅, fixedCount: 0} |

## Постусловие

- Активный пул пересчитан: candidates содержат только Variables, Styles исключены.
- Старые UI-фильтры сброшены, метрики обнулены.

## Связанные flows

- Если пользователь меняет настройку и не делает Rescan → активный пул остаётся прежним, новые настройки повлияют только на следующий Scan.
- Аналогичный сценарий для tokenPolicy → **Two-tier ДС с tokenPolicy: semantic-only**.

## Edge-cases

- **Пользователь меняет настройку, Fix-ит ещё несколько нарушений и закрывает плагин.** В v1.0 Fix работает по старому Candidate pool до Rescan — это сознательная цена отсутствия live-пересчёта.
- **На шаге 2 пользователь выбирает tokenSource: 'styles', но в файле нет ни одного style.** Баннер дополняется предупреждением «В файле нет Styles, активный пул будет пуст после Rescan».
- **Пользователь меняет настройку дважды до Rescan.** Применяется последняя, баннер не дублируется.

# Flow 6. Cmd+Z после Fix

**Цель пользователя:** откатить последний применённый Fix, увидев его в Figma.
**Тип:** системный (без действия пользователя в плагине).
**Маркер:** 🟢
**Связанные термины глоссария:** Undo, Fix, Active pool.

## Предусловия

- Пользователь только что применил Fix к нарушению `v42`.
- На Dashboard или в Review: `{active pool: 46, fixedCount: 1, последний Fix: v42 → token T7}`.

## Шаги

| # | Триггер | Состояние UI плагина | Состояние Figma и данных |
|---|---------|----------------------|--------------------------|
| 1 | ⚙ Пользователь нажимает Cmd+Z в окне Figma | [Dashboard] (не меняется) | Figma: нода вернулась к hardcoded-значению. Плагин: `{active pool: 46, fixedCount: 1}` (не изменилось) |
| 2 | Пользователь возвращается в плагин, видит счётчики из шага 1 | [Dashboard] | расхождение: в Figma нарушение есть снова, в плагине его нет в списке |
| 3 | Пользователь нажимает Rescan | [Loading] → [Dashboard] | {active pool: 47, fixedCount: 0, нарушение v42 снова в активном пуле} |

## Постусловие

- В Figma нода в исходном состоянии.
- В плагине после Rescan состояние согласовано с Figma.
- Без Rescan: рассинхронизация (известное ограничение v1.0).

## Связанные flows

- Если пользователь делает Cmd+Shift+Z (Redo) → симметричное поведение, плагин также не узнаёт.
- Чтобы привести плагин в согласованное состояние → **Полный аудит без фильтров** (часть с Rescan).

## Edge-cases

- **Cmd+Z нажат несколько раз подряд.** Откатывается несколько Fix последовательно. UI плагина рассинхронизируется кратно.
- **Cmd+Z нажат после операций в Figma вне плагина** (например, пользователь между Fix передвинул фрейм). Откатится передвижение, не Fix. Это корректное поведение Figma.
- **Пользователь ожидает, что счётчик `fixedCount` уменьшится автоматически.** Это явно описано как ограничение v1.0: автоматической синхронизации с Cmd+Z нет.

# Flow 7. Восстановление через ErrorCard

**Цель пользователя:** разобраться, почему Scan не запустился, и продолжить работу.
**Тип:** восстановление.
**Маркер:** 🟢
**Связанные термины глоссария:** Scan error code, ErrorCard, Scope, AI key.

## Подвариант 7A. No selection

### Предусловия
- Плагин открыт.
- В Figma ничего не выделено.
- На Scope selector выбран scope: 'selection'.

### Шаги

| # | Действие пользователя | Состояние UI | Состояние данных |
|---|----------------------|--------------|------------------|
| 1 | Нажимает Scan | [ErrorCard: «Нет выделения»] | {scanErrorCode: 'NO_SELECTION'} |
| 2 | Возвращается в Figma, выделяет фрейм | [ErrorCard] (не меняется) | без изменений |
| 3 | В плагине нажимает Try again | [Loading] → [Dashboard] | {scanErrorCode: null, active pool: рассчитан} |

### Постусловие
- Скан выполнен, пользователь на Dashboard.

## Подвариант 7B. No tokens in file

### Предусловия
- Плагин открыт, в Figma выделен фрейм.
- В файле нет ни одного variable и ни одного style.

### Шаги

| # | Действие пользователя | Состояние UI | Состояние данных |
|---|----------------------|--------------|------------------|
| 1 | Нажимает Scan | [Loading] → [ErrorCard: «В файле нет токенов. Подключите library или создайте variables»] | {scanErrorCode: 'NO_TOKENS'} |

### Постусловие
- Снапшот ДС включает токены подключённой библиотеки.
- Дальнейшая работа как в Flow 1.

## Подвариант 7C. No AI key (при включённом AI toggle)

### Предусловия
- Плагин открыт впервые.
- AI toggle включён по умолчанию.
- `google-api-key` отсутствует в clientStorage.

### Шаги

## Связанные flows

- После успешного восстановления → **Полный аудит без фильтров**.
- Если пользователь хочет позже вернуть AI → Settings → AI toggle → ввод ключа.

## Edge-cases

- **На 7A пользователь нажимает Try again без выделения.** Снова ErrorCard с тем же кодом. Ключ-сценарий: пользователь забыл переключиться в Figma.
- **На 7B нет токенов и нет подключённых библиотек.** Try again даёт тот же ErrorCard. Подсказка: ссылка на документацию по созданию variables.
- **На 7C пользователь вводит невалидный ключ.** При первом AI Explanation cycle (Flow за пределами Scan) появится ошибка «Invalid API key», но Scan и Fix продолжат работать.

# Flow 8. Two-tier ДС с tokenPolicy: semantic-only

**Цель пользователя:** в файле с разделением primitive / semantic токенов получить рекомендации только семантических.
**Тип:** альтернативный.
**Маркер:** 🟢
**Связанные термины глоссария:** Two-tier design system, Token policy, Primitive token, Semantic token, Candidate pool, Candidates.

## Предусловия

- В файле подключена ДС с явным разделением: primitive (например, `colors/blue/500: #36499A`) и semantic (например, `color/brand/primary` → алиас на `colors/blue/500`).
- Всего токенов цвета: 12 primitive + 8 semantic.
- В выделенном фрейме ~30 нарушений типа `hardcoded_color`.

## Шаги

| # | Действие пользователя | Состояние UI | Состояние данных |
|---|----------------------|--------------|------------------|
| 1 | На Scope selector меняет tokenPolicy на 'semantic-only' | [Scope selector] | {tokenPolicy: 'semantic-only'} |
| 2 | Нажимает Scan | [Loading] → [Dashboard] | {Candidate pool: 8 semantic токенов, active pool: 30, candidates каждого нарушения: top-3 из semantic} |
| 3 | Открывает Review: Colors, разворачивает первое нарушение | [Review: Colors] | candidates карточки: `[color/brand/primary, color/surface/accent, color/text/link]` (всё семантические) |
| 4 | Применяет Fix с top-1 | [Review: Colors] | {active pool: 29, нода теперь связана с semantic-токеном} |
| 5 | Повторяет Fix для остальных | [Review → Dashboard] | {active pool: 0, fixedCount: 30} |

## Постусловие

- Все нарушения исправлены применением semantic-токенов.
- Primitive-токены не предлагались как кандидаты ни на одном шаге.

## Связанные flows

- Если пользователь хочет видеть и primitive — меняет policy → **Смена token source / token policy после Scan**.
- Если ДС не two-tier — policy 'semantic-only' даст пустые candidates у части нарушений → см. edge-case ниже.

## Edge-cases

- **Для нарушения нет семантического токена, близкого по значению.** Карточка показывает `candidates: []` и сообщение «Нет подходящего semantic-токена. Расширьте policy до all-tokens или добавьте токен в ДС». Кнопка Fix дизейблится.
- **Файл не two-tier** (есть только primitive, нет алиасов). Candidate pool пуст, активный пул показывается, но Fix недоступен ни для одной карточки. Подсказка предлагает переключить policy.
- **Semantic-токен ссылается на удалённый primitive** (битый алиас). Кандидат всё равно показывается (имя видно), Fix применяется к ноде, но визуально может сломаться. Это ответственность ДС, не плагина.

# Связь с глоссарием и циклами

Документ опирается на два соседних:

- **Глоссарий** — источник терминов. Каждый flow ссылается на используемые термины в секции «Связанные термины глоссария». Если в flow появляется термин, которого нет в глоссарии, — сначала добавляется термин.
- **Жизненные циклы работ плагина** — источник динамики данных. Flows показывают пользовательский путь, циклы показывают, что внутри происходит на каждом шаге. Например, шаг «нажимает Fix» в Flow 1 разворачивается в полный Fix cycle в документе циклов.

При изменении определения термина — пересматриваются все flows с этим термином. При изменении этапов цикла — пересматриваются flows, где этот цикл триггерится действием пользователя.
