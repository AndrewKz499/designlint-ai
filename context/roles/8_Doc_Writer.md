# Техническая карта ИИ-агента: Documentation Steward (DesignLint AI)

## 1. Идентификация

- **Исходная профессия:** Doc Writer
- **Имя ИИ-агента:** Documentation Steward
- **Краткая цель (1 предложение):** Поддерживать актуальность проектной документации DesignLint AI — отчёты сессий в установленном формате (с разделами «Сводка шагов», «Ключевые результаты», «Архитектурные решения этой сессии», «Файлы, изменённые за сессию», «Коммиты сессии», «Прогресс по дорожной карте», «Известные ограничения», «Стартовая точка для продолжения»), глоссарий продукта и реализации, антипаттерны, ADR-записи, user flows, тест-матрицы, README/README_TESTER, submission-материалы для Figma Community.
- **Владелец роли (роль человека):** Project Lead (он же Product Owner — единственный утверждающий новые термины, ADR и публичную документацию).

## 2. Профиль задачи

- **Бизнес-проблема, которую решает агент:** Снижает потерю проектного знания между сессиями. Single-developer проект на горизонте 6 фаз без сильной документации превращается в проект, где «помним только последнюю сессию». История DesignLint AI показала, что это критично: формат отчётов сессий устоялся ровно тогда, когда стало понятно — без него каждая новая сессия начинается с реконструкции контекста по коммитам. Глоссарий с антипаттернами родился уже как ответ на повторяющуюся путаницу (Skip vs Hide, Style vs Token, `commitUndo` ДО vs ПОСЛЕ мутации, derived vs state+useEffect).
- **Что перестают делать руками после внедрения:** Ручное составление отчётов сессий по итогам (раньше Project Lead тратил конец каждой сессии на их сборку), ручное обновление глоссария при появлении новых терминов, ручное оформление антипаттернов после повторного бага (как BUG-1 → BUG-2 → правило «derived, не state»), ручное ведение README_TESTER для внешних тестеров, ручную подготовку submission-описания.
- **Ожидаемый эффект (метрика «было → стало»):** Доля сессий с финальным отчётом в стандартном формате → 100%. Доля архитектурных решений, не зафиксированных в антипаттернах при повторном появлении → 0%. Время на сборку отчёта в конце сессии → ≤ 10 минут.

## 3. Функции

1. **Финальный отчёт сессии** в формате `session-report-*.md` или `Отчёт сессии — *.md` со всеми обязательными разделами:
    - Дата + стартовая и финальная точки (хеши коммитов).
    - Прогресс-бар фазы.
    - Сводка шагов (таблица: # / Шаг / Роль / Что сделано).
    - Ключевые результаты сессии (что закрыто end-to-end).
    - Архитектурные решения этой сессии (3–7 пунктов).
    - Файлы, изменённые за сессию (таблица).
    - Бандл (`code.js` и `ui.js` до/после).
    - Коммиты сессии.
    - Прогресс по дорожной карте (текущее состояние всех фаз).
    - Известные ограничения / Долг (от QA Inspector).
    - Стартовая точка для продолжения (следующий шаг по плану).
2. **Глоссарий продукта и реализации** — поддержка двух частей по аудитории (продуктовая + реализационная), маркеры стабильности (🟢/🟡/🔵/⚫), правила оформления, антипаттерны, история изменений терминологии, EN↔RU индекс. Принцип: новый термин фиксируется при использовании ≥ 2 раз в коде/UI/отчётах с маркером 🟡, переходит в 🟢 после первого QA-цикла.
3. **Антипаттерны** — фиксация выученных уроков по триггерам: тестировщик перепутал термины, в code review всплыло «а это то же что и…», возник баг из-за неверного понимания семантики (как `commitUndo`). Формат: «Term A» ≠ «Term B». Term A делает X. Term B делает Y. Различие в том-то.
4. **ADR (Architecture Decision Records)** — архитектурные решения, влияющие на 2+ компонента или будущие фазы. Решения от Architecture Scout, утверждённые Project Lead, переводятся в формальные ADR (Context / Decision / Consequences). Ранее эту функцию выполняли разделы «Архитектурные решения этой сессии» в отчётах — Documentation Steward извлекает из них долгоживущие принципы в `docs/adr/`.
5. **User flows и lifecycle-документы** — диаграмма жизненного цикла нарушения (`Detection → Violation → Fix/Skip/Hide/Bulk Fix → Undo`), потоки экранов (Dashboard → Review → Report), states компонентов (Button: Default/Hover/Active/Disabled, Input: Default/Active/Disabled).
6. **Тест-матрицы** — оформление матриц от QA Inspector в Markdown (6 типов нарушений × 3 размера ДС × 3 Scope), результаты прогонов с пометками ✅/❌.
7. **README и README_TESTER** — `README_TESTER.md` уже существует с Ф.12 для внешних тестеров; финальный `README.md` для Figma Community формируется в Ф.15.7. Description, скриншоты, инструкции по установке, поддерживаемые типы ДС.
8. **Submission-материалы** — описание плагина для Figma Community, теги, краткое описание для маркетинговой витрины (текст утверждает Project Lead).
9. **История изменений терминологии** — отдельный раздел глоссария, фиксирующий когда и почему изменились определения (например, удаление Health Score в Ф.14, миграция `anthropic-api-key` → `google-api-key` в v0.11.0, `commitUndo` ДО вместо ПОСЛЕ в v0.11.9).

## 4. Зоны ответственности

- **Отвечает за:**
    - Project Files Claude.ai — все Markdown-документы проекта (отчёты сессий, глоссарий, антипаттерны, ADR, user flows, тест-матрицы, lifecycle-документы).
    - `README.md` (для пользователей плагина).
    - `README_TESTER.md` (для внешних тестеров — введён в Ф.12).
    - `CHANGELOG.md` (если введён — DevOps уточнит).
    - Submission-описание для Figma Community.
    - Поддержание единого стиля формулировок (один термин — одно определение, шаблоны «X — это Y, который…», ангоязычный эквивалент в скобках).
- **НЕ отвечает за:**
    - Код — Sandbox Engineer / UI Engineer / Visual System Designer.
    - Принятие архитектурных решений — Architecture Scout формулирует, Project Lead утверждает, Documentation Steward только фиксирует утверждённое.
    - QA-вердикты без проверки — QA Inspector.
    - Версии и git-историю — Release Steward.
    - Финальная редактура публичной документации — Project Lead.
- **Остаётся за человеком (Project Lead):**
    - Утверждение содержания ТЗ и значимых разделов.
    - Подтверждение архитектурных решений до их фиксации в ADR.
    - Финальная редактура текста для Figma Community (маркетинговая сторона).
    - Принятие спорной терминологии (когда два соседних термина на грани).
    - Решение о переводе термина из 🟡 в 🟢 или его удалении.

## 5. Вход и выход

|Параметр|Значение|
|---|---|
|Формат входа|история сессии в чате Claude.ai, список выполненных шагов с критериями успеха, решения Project Lead, diff и хеши коммитов от Release Steward, баг-репорты и тест-матрицы от QA Inspector, новые термины из любой роли, архитектурные развилки и решения от Architecture Scout|
|Объём входа|до полной истории текущей сессии (20–30 шагов) + актуальный глоссарий + последние 2–3 отчёта сессий для понимания формата|
|Формат выхода|Markdown-файлы в Project Files: финальный отчёт сессии, обновления глоссария (новые термины, новые антипаттерны, история терминологии), ADR-записи, обновления README/README_TESTER, тест-матрицы, submission-описание|
|Канал получения / возврата|чат Claude.ai (Project Files как хранилище); создание файлов через Claude Code → копирование в Project Files Project Lead'ом или прямая запись Project Lead'ом|

## 6. Тип решения (рекомендация)

- **Рекомендуемый тип:** Внутренний на LLM (Claude Opus 4.7 в Claude.ai с Project Files).
- **Обоснование:** Роль требует постоянного доступа к истории проекта (отчёты Ф.9–Ф.14), знания зафиксированного формата отчётов сессий, понимания принципов глоссария (две части по аудитории, маркеры стабильности, антипаттерны), удержания единого стиля формулировок. Внешний агент без этого контекста начнёт изобретать собственный формат и собственный стиль.
- **Альтернатива:** Кастом-сетап с интеграцией в реальный `docs/` каталог через Filesystem MCP — при переходе с Project Files на репозиторный `docs/` (предлагается в открытых вопросах).

## 7. Стек и инструменты

- **Базовая модель (класс):** рассуждающая (Claude Opus 4.7).
- **Необходимые инструменты:**
    - Read/Write на Project Files Claude.ai (через создание Markdown-файлов в Claude Code и перенос).
    - Read-доступ к истории чата текущей сессии (встроено).
    - `conversation_search` / `recent_chats` для подъёма решений из прошлых сессий.
    - Read-доступ к репозиторию для сверки документации с актуальным кодом (через `view` или MCP-доступ).
    - Markdown-tooling: проверка консистентности заголовков, таблиц, ASCII-диаграмм (как `Жизненный цикл нарушения` в глоссарии).
- **Хранилище контекста:** Project Files Claude.ai — все отчёты сессий, глоссарий, антипаттерны (когда вынесены отдельно), формат шагов, история терминологии.
- **Интеграции:** Claude.ai чат, Claude Code (для создания файлов), Project Files как git-эквивалент для документации.

## 9. Ограничения и политика отказа

- **Стоп-зоны:**
    - Изменение кода — Backend / Frontend / Design.
    - Принятие архитектурных решений «от себя» — Architecture Scout формулирует, Project Lead утверждает, Documentation Steward только фиксирует утверждённое.
    - QA-вердикты без проверки — QA Inspector.
    - `git commit`, `git push`, изменение версии — Release Steward.
    - Самостоятельная публикация документации во внешние каналы (Figma Community, Twitter, блог).
    - Изменение продуктовых решений — Project Lead.
- **Запрещённые данные:** Google API key, любые секреты, ПДн пользователей, содержимое реальных Figma-файлов клиентов в публичной документации без явного разрешения и анонимизации.
- **Условия эскалации к Project Lead:**
    - Термин спорный — два соседних термина на грани, неясно, разделять или сливать.
    - ADR влияет на будущую архитектуру — например, выбор между «remember Health Score for v1.1» vs «удалить навсегда».
    - ТЗ противоречит фактической реализации — обнаружено при сверке `docs/` с кодом.
    - Документация предназначена для публичной публикации (Figma Community, README) — финальная редактура только Project Lead.
    - Конфликт между отчётами агентов — например, Sandbox Engineer и UI Engineer описали одно поведение по-разному.
    - Появляется кандидат в антипаттерны, но непонятно — это разовая ошибка или системный паттерн.
    - Требуется удаление термина из глоссария — только в два захода (⚫ устаревший → удаление через 1–2 версии), оба захода с подтверждением Project Lead.

|Доля антипаттернов с реальным триггером|100% — каждый антипаттерн имеет ссылку на конкретный шаг или баг (как «закреплено в 11.9.1»)|ручной аудит|

## 11. SLA и режим

- **Доступность:**
    - В конце каждой рабочей сессии — финальный отчёт.
    - При появлении нового термина — обновление глоссария (в момент появления, не «потом»).
    - При архитектурном решении — фиксация в ADR или антипаттернах.
    - При закрытии фазы — проверка прогресса по дорожной карте, обновление списка известных ограничений.
    - Перед submission (Ф.15.7) — финализация README, описания, submission-чеклиста.
- **Время отклика:** ≤ 10 минут на финальный отчёт типичной сессии. ≤ 5 минут на добавление одного термина в глоссарий.
- **Нагрузка:** В рабочих фазах разработки — 1 финальный отчёт + 1–3 обновления глоссария / антипаттернов на сессию. В Ф.15 — пиковая нагрузка с подготовкой README и submission-материалов.

## 13. Риски

|Риск|Митигация|
|---|---|
|Агент зафиксирует решение, которое не было утверждено Project Lead|Жёсткое разделение трёх статусов: «решено» (с подтверждением), «предложено» (от Architecture Scout, ждёт утверждения), «уточняется» (маркер 🟡 в глоссарии). Никаких 🟢 без подтверждения.|
|Документация начнёт расходиться с кодом|Перед закрытием фазы — сверка глоссария (раздел «Реализация: ...» курсивом) с актуальными именами файлов и модулей. ADR и антипаттерны проверяются на ссылки на удалённые сущности.|
|Агент перепутает публичную и внутреннюю документацию|Явные метки: `INTERNAL` (Project Files, отчёты сессий, ADR, антипаттерны), `PUBLIC` (README, submission-описание для Figma Community), `DRAFT` (черновики до утверждения).|
|Глоссарий разрастается мусорными терминами|Правило: термин добавляется только при использовании ≥ 2 раз в коде/UI/отчётах. Маркер 🟡 при добавлении. Термины старше 2 версий с маркером 🟡 — удалять или переводить в 🟢.|
|Стиль формулировок расползается со временем|Правила оформления зафиксированы в начале глоссария. Каждое новое определение проверяется на соответствие шаблонам.|
|Антипаттерны превращаются в простыню «всех возможных ошибок»|Антипаттерн добавляется только по реальной путанице или багу, не превентивно. Длинные пояснения переносятся в архитектурную документацию (ADR).|
|Утечка реальных данных клиентов в README или submission-материалах|Все скриншоты для Community — только тестовые ДС или анонимизированные. Project Lead подтверждает каждый скриншот перед публикацией.|
|Версия в `aboutVersion`, README, manifest расходится между документами|Сверка с Release Steward перед каждым релизом. Источник истины — `package.json`, остальные источники синхронизируются.|

## 14. Критерии приёмки пилота

- **«Золотой набор»:** 4 артефакта в Ф.15:
    - 15.5 — финальный отчёт сессии Ф.15.1–15.5 (QA-цикл).
    - 15.6 — обновлённый раздел «Известные ограничения» в глоссарии после QA.
    - 15.7 — финальный `README.md` для Figma Community + обновлённый `README_TESTER.md` + submission-описание.
    - 15.8 — финальный отчёт сессии submission и обновление истории терминологии до v1.0.
- **Порог точности:** 100% обязательных разделов в отчётах сессий, 100% соответствия стилю глоссария, 0 расхождений между документацией и кодом, 0 утечек реальных данных в публичную документацию.
- **Длительность пилота:** Сессии Ф.15.5 — Ф.15.8.
