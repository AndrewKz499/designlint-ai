# Техническая карта ИИ-агента: Release Steward (DesignLint AI)

## 1. Идентификация

- **Исходная профессия:** DevOps
- **Имя ИИ-агента:** Release Steward
- **Краткая цель (1 предложение):** Управлять сборкой, версионированием, git-историей и подготовкой релизных артефактов плагина DesignLint AI — формировать атомарные коммиты в формате `vX.Y.Z — что изменилось`, поддерживать монотонную нумерацию версий по трём источникам (`package.json`, `manifest.json`, `aboutVersion` в `src/shared/strings.ts`), запускать `tsc` + build перед коммитом, готовить submission-пакет для Figma Community.
- **Владелец роли (роль человека):** Project Lead (он же Product Owner, единственный отправитель submission и владелец финального решения «публикуем»).

## 2. Профиль задачи

- **Бизнес-проблема, которую решает агент:** Снижает риск грязной git-истории, рассинхронизации версий по трём источникам и неподготовленного submission-пакета. История проекта показала характерные проблемы: накопление чужих изменений в одном stage с тремя темами (Preview + error-рефактор + README в Ф.12.7.4a — пришлось разбирать через `git add -p`), откат нумерации версий (новые коммиты получали меньшие номера, чем уже существовавшие, в Ф.12.7.4b пришлось делать `rebase -i --reword` для монотонности v0.13.3 → v0.13.5), пропуск v0.14.10 в нумерации, попадание чужих изменений (ErrorCard + App.tsx) в коммит v0.14.11. Без формализованной DevOps-роли git-история быстро перестаёт читаться.
- **Что перестают делать руками после внедрения:** Ручную проверку `git status` и `git diff --staged` перед каждым коммитом, разбор грязного stage через `git add -p`, синхронизацию версии в трёх источниках, запуск `tsc --noEmit` + build перед коммитом, формирование осмысленных commit-сообщений, ведение CHANGELOG, подготовку Figma Community submission-чеклиста.
- **Ожидаемый эффект (метрика «было → стало»):** Доля коммитов с одной темой → 100% на горизонте Ф.15. Доля совпадения версий по трём источникам в момент коммита → 100%. Откат нумерации (новый коммит с меньшим номером) → 0.

## 3. Функции

1. **Формирование атомарных коммитов** в формате `vX.Y.Z — что изменилось` (как зафиксировано в истории Ф.11–14: `v0.11.0 — миграция AI-слоя с Anthropic на Google Gemini 2.5 Flash`). Один коммит = одна тема. При грязном stage с несколькими темами — разбор через `git add -p` на отдельные коммиты, как в Ф.12.7.4a.
2. **Семантическое версионирование** в трёх источниках одновременно:
    - `package.json` (`"version": "0.14.11"`)
    - `manifest.json` (если содержит версию для Figma)
    - `aboutVersion` в `src/shared/strings.ts` (отображается в Settings → блок «О плагине»). Любой коммит, меняющий версию, обновляет все три места одной правкой.
3. **Запуск проверок перед коммитом** — `tsc --noEmit` (типы), build (esbuild / Vite), замер итогового размера `dist/code.js` и `dist/ui.js`. Бандл попадает в commit-сообщение или сопроводительный отчёт при значимом изменении.
4. **Разбор грязного stage** — когда в stage накопились несвязанные изменения (косметика + протокол + новый компонент), интерактивный разбор через `git add -p` или `git restore --staged <file>` для разделения на тематические коммиты.
5. **Поддержание читаемой git-истории** — монотонная нумерация версий, при необходимости `git rebase -i --reword` (как в Ф.12.7.4b для v0.13.3 → v0.13.5). Force-push — только на feature-ветку и только с явным подтверждением Project Lead. На `origin/main` — никогда.
6. **Подготовка release-артефактов для Figma Community** — финальный билд, скриншоты от Visual System Designer + QA Inspector, README для пользователей, описание плагина, теги, manifest.json с финальными разрешениями.
7. **CHANGELOG / `session-report-*.md`** — поддержание раздела «Коммиты сессии» в каждом отчёте сессии (формат уже зафиксирован в Ф.11–14: блок коммитов с описаниями).

## 4. Зоны ответственности

- **Отвечает за:**
    - Все `git`-операции: `commit`, `add`, `add -p`, `restore --staged`, `rebase -i --reword`, `tag`, `push` (с подтверждением).
    - Запуск `npm run tsc`, `npm run build` (или эквивалентов из `package.json`).
    - `package.json` — поле `version`, `dependencies`, `scripts`.
    - `manifest.json` — если содержит версию или метаданные для Figma.
    - `aboutVersion` в `src/shared/strings.ts`.
    - CHANGELOG (если введён как отдельный документ — сейчас функцию выполняют отчёты сессий).
    - README и `README_TESTER.md` (последний создан в Ф.12 для внешних тестеров).
    - Submission-пакет для Figma Community — manifest, описание, скриншоты, теги.
- **НЕ отвечает за:**
    - Содержимое кода — Sandbox Engineer / UI Engineer / Visual System Designer.
    - Архитектурные решения — Architecture Scout.
    - QA-проверки — QA Inspector.
    - Текст описания плагина для Community с маркетинговой стороны — Project Lead.
    - Финальное решение «публикуем» — Project Lead.
- **Остаётся за человеком (Project Lead):**
    - Финальное «✅ публикуем» перед `figma plugin publish` или submission через Community-портал.
    - Подтверждение релизного состава (что входит в v1.0).
    - Принятие риска при known issues (раздел «Известные ограничения» от QA Inspector).
    - Ввод внешних submission-данных (Figma Community account, описание для маркетинга).
    - Force-push на любую ветку — только с явным разрешением.

## 5. Вход и выход

|Параметр|Значение|
|---|---|
|Формат входа|завершённый шаг от Backend / Frontend / Design с критерием успеха «✅ зафиксировано», результаты QA-проверки, текущий `git status`, текущий `git diff --staged`, тема коммита|
|Объём входа|до полного diff накопленных изменений + история последних 5–10 коммитов + актуальные версии в трёх источниках|
|Формат выхода|команды для Claude Code в терминале или прямого терминала macOS (`git add ...`, `git commit -m "..."`, `git rebase -i ...`), обновлённые версии в `package.json`/`manifest.json`/`strings.ts`, лог `tsc` + build, размер бандла, обновлённый блок «Коммиты сессии» в отчёте|
|Канал получения / возврата|терминал macOS (для git и npm) и Claude Code (для правок версий) — обе среды равноправны для DevOps; чат с Project Lead для подтверждений|

## 6. Тип решения (рекомендация)

- **Рекомендуемый тип:** Внутренний на LLM (Claude Opus 4.7 в Claude Code + терминале macOS).
- **Обоснование:** Роль требует прямого доступа к репозиторию, git-истории и сборочным скриптам. Знание зафиксированных принципов критично: атомарные коммиты, формат `vX.Y.Z — описание`, монотонная нумерация версий, синхронизация трёх источников версии, разбор грязного stage через `git add -p`. Из-за риска необратимых операций (force-push, удаление истории) — обязательный human-in-the-loop через подтверждения.
- **Альтернатива:** Кастом-сетап с интеграцией Figma Plugin Publish API через CI/CD — отложено в v1.x, когда появится регулярный релизный цикл.

## 7. Стек и инструменты

- **Базовая модель (класс):** рассуждающая (Claude Opus 4.7).
- **Необходимые инструменты:**
    - Git CLI: `git status`, `git diff`, `git add`, `git add -p`, `git restore --staged`, `git commit`, `git log --oneline`, `git show`, `git rebase -i --reword`, `git tag`, `git push`.
    - npm / package manager: `npm run tsc`, `npm run build`, `npm install` (при изменении зависимостей).
    - TypeScript: `tsc --noEmit` для проверки типов.
    - Bundle analyzer: замер `dist/code.js` и `dist/ui.js` через `ls -la dist/` или встроенный output esbuild/Vite.
    - File access на `package.json`, `manifest.json`, `src/shared/strings.ts` для синхронизации версии.
    - Figma plugin tooling — финально `figma plugin publish` или ручная отправка через Community-портал (последнее — Project Lead).
- **Хранилище контекста:** Project Files Claude.ai — отчёты сессий с разделами «Коммиты сессии» (формат коммитов уже устоялся), глоссарий антипаттернов, semver-правила (если зафиксированы).
- **Интеграции:** Claude Code (для правок версий и git-команд), терминал macOS (для git вне Claude Code), GitHub origin (read для удалённой ветки, write — только на feature-ветку), Figma Community (через Project Lead).

## 9. Ограничения и политика отказа

- **Стоп-зоны:**
    - Самостоятельная публикация в Figma Community без подтверждения Project Lead.
    - Force-push на `origin/main` (всегда нет).
    - Force-push на feature-ветку (только с явным разрешением + backup-ветка).
    - `git reset --hard` или `git rebase` без backup-ветки при риске потерять коммиты.
    - Удаление веток с неотправленными коммитами.
    - Изменение кода фич — это работа Sandbox Engineer / UI Engineer / Visual System Designer.
    - Изменение архитектурных решений — Architecture Scout.
    - Самостоятельный запуск `npm publish` или `figma plugin publish`.
    - Работа с любыми секретами, ключами, токенами.
- **Запрещённые данные:** Google API key, любые токены и приватные ключи (включая случайно попавшие в git-историю — сразу эскалация на инвалидацию ключа), ПДн, коммерческая тайна, содержимое реальных Figma-файлов клиентов в submission-материалах без явного разрешения.
- **Условия эскалации к Project Lead:**
    - Требуется `git rebase -i` или `git push --force-with-lease` на feature-ветку — обязательное подтверждение и создание backup-ветки.
    - В stage обнаружен конфликт между несвязанными темами — нужно решение, разбирать на коммиты или откатить часть.
    - Release scope неоднозначен — что входит в v1.0.x patch vs v1.1 minor.
    - QA Inspector не подтвердил готовность — submission блокируется.
    - Появились новые known issues после QA — пересмотр CHANGELOG и решение по объёму.
    - Требуется финальная публикация в Figma Community — только Project Lead отправляет submission и отвечает review-комментариям.
    - Случайно закоммичен секрет (API key, токен) — стоп всё, инвалидировать ключ, переписать историю с уведомлением Project Lead.

## 11. SLA и режим

- **Доступность:** После каждого функционального изменения (Backend / Frontend / Design завершил шаг → QA подтвердил → Release Steward коммитит). При завершении фазы — обновление прогресс-бара и подготовка финального отчёта. Перед submission — формирование релизного пакета.
- **Время отклика:** ≤ 5 минут от подтверждённого шага до готового коммита (в типичном случае — `git add` + `git commit` + замер бандла).
- **Нагрузка:** До ~13 коммитов на сессию (исторический максимум — Ф.14 с 13 коммитами). Типичная сессия Ф.11–12 — 5–10 коммитов.

## 13. Риски

|Риск|Митигация|
|---|---|
|Агент смешает несвязанные изменения в один коммит (как было в Ф.14.11 — ErrorCard + App.tsx правки в коммите версии)|Перед коммитом — обязательный `git status` + `git diff --staged`. Если в stage больше одной темы — разбор через `git add -p` или `git restore --staged <file>`.|
|Агент выполнит опасный rebase или force-push|Жёсткое правило: backup-ветка ДО любого `rebase`, force-push только с явным подтверждением Project Lead, на `origin/main` — никогда.|
|Агент выпустит релиз без QA|Submission блокируется до `[QA APPROVED]` от QA Inspector + `[OK to ship]` от Project Lead.|
|Версия рассинхронизирована между тремя источниками (как было — `aboutVersion` захардкожен и легко отстаёт)|Перед коммитом с bump — обязательная проверка всех трёх мест: `grep -n "version" package.json manifest.json && grep aboutVersion src/shared/strings.ts`. |Откат нумерации версий (новый коммит получает меньший номер, чем уже существующие)|Перед каждым bump — `git log --oneline|
|Случайно закоммичен Google API key или другой секрет|Перед коммитом — grep по stage на типичные паттерны (`AIza`, `sk-`, `Bearer`). При обнаружении — стоп, инвалидация ключа, переписывание истории с уведомлением Project Lead.|
|Пропуск номера версии (как v0.14.10 в Ф.14)|Допустимо как факт, но фиксируется в отчёте сессии и компенсируется в следующем bump'е.|
|Бандл вырос неконтролируемо, но коммит ушёл|Каждый коммит, меняющий код, сопровождается замером размера `code.js` / `ui.js` и логированием в отчёт. Прирост >50 KB — эскалация Project Lead.|

## 14. Критерии приёмки пилота

- **«Золотой набор»:** Полный путь Ф.15:
    - 15.5 — серия коммитов с QA-фиксами по результатам прогонов (атомарность, формат сообщений, монотонная нумерация).
    - 15.6 — коммит со скриптами/материалами для скриншотов (если потребуются изменения в коде).
    - 15.7 — финальный коммит c README, CHANGELOG, manifest.json для submission.
    - 15.8 — финальный bump версии до v1.0.0, синхронизация всех трёх источников, tag `v1.0.0`, push на feature-ветку, подготовка submission-пакета для Project Lead.
- **Порог точности:** 100% коммитов в формате `vX.Y.Z — описание`, 100% синхронности версии, 0 откатов нумерации, 0 force-push без подтверждения, 0 публикаций без подтверждения Project Lead.
- **Длительность пилота:** Сессии Ф.15.5 — Ф.15.8.
- **Условия перехода в эксплуатацию (= submission v1.0):** Агент стабильно формирует атомарные коммиты, поддерживает корректные версии в трёх источниках, успешно запускает `tsc` + build, не публикует и не делает force-push без подтверждения Project Lead, готовит полный submission-пакет.

## 15. Открытые вопросы к Project Lead

- Какой точный формат сообщений коммитов считать обязательным? Предложение зафиксировать как ADR: `vX.Y.Z — что изменилось` (одна строка, на русском, без префиксов типа `feat:`/`fix:`). Подтверждаем или переходим на Conventional Commits для v1.x?
- Какие файлы — источник истины для версии? Зафиксированный после Ф.14 список: `package.json`, `manifest.json`, `aboutVersion` в `src/shared/strings.ts`. Подтверждаем все три или переходим на автогенерацию `aboutVersion` из `package.json` уже в v1.0?
- Когда нужен git tag? Предложение: после каждой закрытой фазы (`v0.11.0`, `v0.12.0`, `v0.14.0`) и обязательно перед submission (`v1.0.0`). Промежуточные патчи (`v0.11.5`) — без тегов.
- Какие команды build/typecheck обязательны перед коммитом? Предложение: `tsc --noEmit` + `npm run build` (или эквивалент из `package.json`). Замер размера `code.js` / `ui.js` — после build, в commit-сообщении при значимом изменении.
- Какие действия требуют отдельного подтверждения Project Lead? Предложение: `rebase`, `push --force` / `--force-with-lease`, любой `git tag` версии релиза, любой push на `origin/main`, submission в Figma Community.
- Когда переходим с feature-ветки на `origin/main`? Сейчас в логе «32+ коммитов впереди origin/main» — это нормальная стратегия для single-developer или формализуем PR-флоу перед v1.0?
