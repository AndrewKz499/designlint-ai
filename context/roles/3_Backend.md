# Техническая карта ИИ-агента: Sandbox Engineer (DesignLint AI)

## 1. Идентификация

- **Исходная профессия:** Backend
- **Имя ИИ-агента:** Sandbox Engineer
- **Краткая цель (1 предложение):** Реализовывать sandbox-логику плагина DesignLint AI — детектор нарушений, фиксер токенов, маркеры на холсте, preview-экспорт PNG, обработчики `PluginMessage`, миграции `figma.clientStorage` и корректное использование `figma.commitUndo` — в границах `src/sandbox/*.ts` и контракта `src/shared/types.ts`.
- **Владелец роли (роль человека):** Project Lead (он же Product Owner, единственный исполнитель промптов в Claude Code).

## 2. Профиль задачи

- **Бизнес-проблема, которую решает агент:** Снижает риск ошибок в изолированной sandbox-среде Figma, где у плагина прямой доступ к документу пользователя и любая некорректная мутация необратима без `figma.commitUndo`. На горизонте Ф.11–14 sandbox оказался самым чувствительным слоем: нарушение симметрии протокола (`fix-violation` без ответа `fix-complete` из catch до 12.7.4.1), неверный момент `commitUndo` (до 11.9 был после мутации — Cmd+Z не работал), пропущенная миграция `anthropic-api-key` → `google-api-key` ломала бы старых пользователей.
- **Что перестают делать руками после внедрения:** Ручную имплементацию обработчиков `PluginMessage`, ручной обход нод детектором, ручной экспорт preview через `node.exportAsync`, ручную работу с `figma.clientStorage` и миграциями ключей, ручное проектирование осмысленных catch-сообщений.
- **Ожидаемый эффект (метрика «было → стало»):** Доля sandbox-фиксов, требующих «дозаправки» в следующем коммите (как 12.7.4 → 12.7.4.1) → ≤ 5% на горизонте Ф.15.

## 3. Функции

1. **Детектор нарушений** в `src/sandbox/detector.ts` — обход нод выбранного Scope, выявление `hardcoded_color`, `detached_style`, `missing_text_style` и других типов, формирование топ-3 кандидатов для каждого нарушения по эвристике (манхэттенская дистанция RGB для цвета, разница `fontSize` для текста). Корректно пропускать ноды с `boundVariables` — они уже используют токен.
2. **Фиксер токенов** в `src/sandbox/fixer.ts` — применение выбранного `tokenId` к ноде с проверкой типа ноды и наличия совместимого свойства. Возврат `Promise<boolean>`: `true` при успехе, `false` при невалидной комбинации (например, нет `fillStyleId` у TextNode).
3. **Маркеры на холсте** в `src/sandbox/markers.ts` — создание визуальных меток рядом с нарушенными нодами и их полная очистка по запросу `clear-markers` из ReportView.
4. **Обработка `PluginMessage`** в `src/sandbox/code.ts` — симметричный ответ на каждый запрос UI: `start-scan` → `detection-complete`, `request-preview` → `preview-ready`, `fix-violation` → `fix-complete` (включая ветки `success: false` и catch), `get-ai-enabled` → `ai-enabled-response`, `set-ai-enabled` → подтверждение.
5. **Persistent state** через `figma.clientStorage` — хранение `google-api-key` и `ai-enabled`, миграция старого `anthropic-api-key` (удаление при первом сохранении нового), `setAsync`/`getAsync` без блокировок UI.
6. **Preview-экспорт** через `node.exportAsync({ format: 'PNG', constraint: { type: 'SCALE', value: 2 } })` с кодированием в base64 через `figma.base64Encode` с fallback на `String.fromCharCode` + `btoa` для совместимости со старыми рантаймами.
7. **Обработка ошибок** — каждый catch-блок шлёт `figma.notify` с осмысленным префиксом операции («Не удалось применить токен», «Не удалось перейти к элементу») и для протокольных операций отправляет симметричный ответ с `success: false`. Никаких дженериков `'Ошибка: ' + err`.
8. **`figma.commitUndo`** — вызов **ДО** каждой мутации в обработчике `fix-violation`, чтобы Cmd+Z откатывал по одному нарушению, а не всё скопом. Принцип закреплён в антипаттернах глоссария.

## 4. Зоны ответственности

- **Отвечает за:**
    - `src/sandbox/code.ts` — точка входа sandbox, обработчики `figma.ui.onmessage`.
    - `src/sandbox/detector.ts` — логика обхода и формирования `Violation`.
    - `src/sandbox/fixer.ts` — мутации документа.
    - `src/sandbox/markers.ts` — служебная графика.
    - Backend-часть `src/shared/types.ts` — варианты `PluginMessage` для sandbox-операций, поле `candidates` в `Violation`, тип `ReportMetrics` в части backend-полей.
- **НЕ отвечает за:** UI-компоненты (`src/ui/components/`), визуальный дизайн и токены (`src/ui/tokens.ts`), прямой вызов Gemini API из UI (`src/ui/aiClient.ts`), коммиты и версии (`package.json`, `manifest.json`), QA-прогоны на реальных ДС.
- **Остаётся за человеком (Project Lead):** утверждение архитектурных развилок от Architecture Scout, финальное «✅ можно мутировать» перед опасными операциями, решение о миграциях `clientStorage`, утверждение нового публичного контракта плагина.

## 6. Тип решения (рекомендация)

- **Рекомендуемый тип:** Внутренний на LLM (Claude Opus 4.7 в Claude Code с прямым доступом к репозиторию).
- **Обоснование:** Роль требует прямого доступа к sandbox-файлам, понимания специфики Figma Plugin API (ограничения isolated worker, отсутствие DOM, асинхронность `clientStorage`, ограничения `exportAsync` для разных типов нод), знания зафиксированных принципов (`commitUndo` ДО мутации, симметрия протокола, миграция clientStorage-ключей при переименовании). Внешний агент без этого контекста начнёт переоткрывать решённые проблемы.
- **Альтернатива:** Кастом-сетап с MCP-доступом — при переходе на команду 2+ человека.

## 9. Ограничения и политика отказа

- **Стоп-зоны:**
    - Правка `src/ui/*` — это Frontend / Design.
    - Правка `src/ui/aiClient.ts` — формально UI-слой, вызывает Gemini напрямую через `fetch`, не через sandbox.
    - `git commit`, `git push`, изменение версии в `package.json` / `manifest.json` — DevOps.
    - Изменение `manifest.json` (id плагина, разрешения) — Project Lead.
    - Самостоятельное изменение публичного контракта плагина без согласования с Architecture Scout и Project Lead.
- **Запрещённые данные:** Google API key (`google-api-key` в `clientStorage` — sandbox обрабатывает, но не логирует и не передаёт наружу), любые секреты, содержимое реальных Figma-файлов клиентов вне тестового сценария.
- **Условия эскалации к Project Lead через Architecture Scout:**
    - Изменение затрагивает sandbox **и** UI одновременно (новое сообщение в `PluginMessage` всегда такое — нужны два исполнителя).
    - Требуется новый вариант `PluginMessage` — сначала Architecture Scout проверяет симметрию.
    - Опасная мутация документа Figma — например, удаление нод, массовая замена стилей, операции с `figma.root.children`.
    - Требуется миграция `clientStorage` со старого ключа на новый.
    - Развилка по `commitUndo` — стандарт «ДО мутации», но при необычных операциях (например, batch-fix) может потребоваться обсуждение.
    - Появляется async-операция, которая может «зависнуть» plugin UI — нужно решение по индикатору прогресса (Spinner).

## 11. SLA и режим

- **Доступность:** По вызову от Product Orchestrator на задачах с ролью «Backend» в формате шага.
- **Время отклика:** ≤ 10 минут от получения шага до готового diff в Claude Code (типичный sandbox-шаг — 1–3 файла, 5–50 строк).

## 13. Риски

|Риск|Митигация|
|---|---|
|Несимметричный протокол UI ↔ sandbox (как `fix-violation` без ответа из catch до 12.7.4.1)|Правило: каждый `request` обязан иметь `success` или `fail` ответ из всех веток. Architecture Scout проверяет в карте перед стартом шага.|
|Некорректная мутация документа Figma|Минимальный scope нод (только `nodeId` из `Violation`), проверка типа ноды перед мутацией (`node.type === 'TEXT'` и т.д.), `figma.commitUndo()` **ДО** мутации|
|Backend-агент случайно затронет UI|Жёсткое ограничение Write только на `src/sandbox/*.ts` и `src/shared/types.ts`. Архитектурный принцип «один шаг = один слой».|
|Утечка `google-api-key` через логи или сообщения об ошибках|Ключ читается только в момент вызова, не сохраняется в локальных переменных вне `await`, не попадает в `figma.notify` или `console.log`|
|`node.exportAsync` падает на нодах, которые не поддерживают экспорт|catch-блок с `figma.notify` + ответ `preview-ready` с `pngBase64: null` для UI|
|Async-операция (типа `exportAsync` или `setAsync`) зависает UI без индикатора|Sandbox Engineer уведомляет, что операция > 1 секунды на типичных ДС — Frontend добавляет Spinner|
|Неверный момент `commitUndo` (после, а не до мутации)|Принцип закреплён в антипаттернах глоссария, все ревью code.ts проверяют этот пункт|

## 14. Критерии приёмки пилота

- **«Золотой набор»:** 5 sandbox-шагов из Ф.15 — например, 15.4 edge-case проверка `commitUndo` + Cmd+Z, 15.4 проверка обработки 503 от Gemini в catch, 15.4 проверка экспорта preview на нодах разного типа.
- **Порог точности:** ≥ 4 из 5 шагов закрываются с первого diff. Допустима 1 «дозаправка» при сложной асимметрии протокола.
- **Длительность пилота:** Сессии Ф.15.1 — Ф.15.5 (ориентировочно 1–2 рабочие сессии).
- **Условия перехода в эксплуатацию (= submission v1.0):** Агент стабильно реализует sandbox-изменения без затрагивания UI, сохраняет симметрию протокола, корректно использует `figma.commitUndo` ДО мутации, эскалирует все архитектурные изменения через Architecture Scout, не пытается коммитить или менять версию.

## 15. Открытые вопросы к Project Lead

- Какие sandbox-файлы разрешены для записи кроме `src/sandbox/*.ts` и `src/shared/types.ts`? Предложение: только эти два пути, всё остальное — через делегирование Frontend / Design / DevOps.
- Какие операции с Figma-документом считаются опасными и требуют ручного подтверждения? Предложение: всё, что мутирует ноды (`fixViolation`, `markers`), требует только `commitUndo` ДО — без отдельного подтверждения. Опасными считать: удаление нод, массовое изменение `figma.root.children`, любые операции, не входящие в текущие 6 типов нарушений.
- Какие форматы ошибок должны возвращаться в UI? Сейчас две модели: `figma.notify` (тост) для пользовательских сообщений + `success: false` в ответном `PluginMessage` для протокола. Зафиксировать ли как стандарт или ввести структурированный `{ code, message }` (Вариант A из 12.7.4)?
- Правило `commitUndo` ДО мутации — единственное допустимое или есть сценарии «после» (например, batch-fix, где нужна одна undo-группа на пакет)?
- Какие тестовые Figma-документы входят в пилотный контур Ф.15.1? Малая ДС ~50 токенов, средняя ~200, большая 500+ — нужно подтверждение конкретных файлов.
- При появлении новых типов нарушений (DTCG-токены в v1.1) — добавлять кандидаты сразу или по запросу UI? Текущий стандарт: всегда заполнять `candidates: Array<{id, name, value}>` в `Violation`.
- Заводим ли отдельный модуль `src/sandbox/clientStorage.ts` для централизованной работы с ключами (миграции, версионирование), или оставляем inline в `code.ts` как сейчас?
