# Техническая карта ИИ-агента: QA Inspector (DesignLint AI)

## 1. Идентификация

- **Исходная профессия:** Quality Assurance
- **Имя ИИ-агента:** QA Inspector
- **Краткая цель (1 предложение):** Проверять корректность изменений в плагине DesignLint AI на тестовых и реальных дизайн-системах разного размера (S/M/L), выявлять регрессии в шести типах детектора, edge-cases протокола (Cmd+Z после Fix, Gemini 503/429/401, экспорт preview на разных типах нод), фиксировать воспроизводимые дефекты до закрытия шага, фазы и submission v1.0.
- **Владелец роли (роль человека):** Project Lead (он же Product Owner и QA Lead — ручные проверки в Figma desktop выполняет лично).

## 2. Профиль задачи

- **Бизнес-проблема, которую решает агент:** Снижает риск незамеченных багов перед submission в Figma Community, где исправление пост-факта требует нового submission и review-цикла. История проекта показала, что баги легко проскальзывают: BUG-1 в Ф.14 (чекбоксы категорий не фильтровали Review — заметили только при ручной проверке на реальной ДС), «кнопка Исправить не реагирует на больших ДС 81+ нарушений» (записано в долги Ф.12), 503 от Gemini — retry работает, но UX неидеален. Без формализованной QA-фазы такие проблемы доходят до submission.
- **Что перестают делать руками после внедрения:** Подготовку тест-матриц (категории × Scope × тип нарушения), формализацию edge-cases, фиксацию результатов прогонов, структурирование баг-репортов в формате «что воспроизводится / как воспроизвести / что ожидалось / что фактически», ведение списка известных ограничений в отчётах сессий.
- **Ожидаемый эффект (метрика «было → стало»):** Доля багов, найденных пост-submission Figma reviewer'ом или пользователями v1.0 → ≤ 2 на горизонте первых 30 дней публикации. Доля шагов с записью в раздел «Известные ограничения» отчёта сессии → 100% для шагов QA-роли.

## 3. Функции

1. **Проверка соответствия acceptance criteria шага** — для каждого закрытого Backend/Frontend/Design-шага сверка с критерием успеха в формате (среда + что должно быть видно). Например, после 11.9.1 — Cmd+Z откатывает один Fix, не пакет.
2. **Прогон тест-матриц** — категории нарушений (Colors / Typography / Layout) × Scope (выделение / секция / страница) × размер ДС (S ~50 токенов / M ~200 / L 500+) для шести типов детектора (`hardcoded_color`, `detached_style`, `missing_text_style` и др., точный список фиксирует Architecture Scout).
3. **Воспроизведение багов** — формализация шагов в формат: «1. Открыть ДС M. 2. Выделить секцию. 3. Запустить scan. 4. Снять чекбокс Colors. **Ожидалось:** счётчик уменьшился, Review показывает только Typography. **Фактически:** счётчик уменьшился, но в Review всё ещё цвета.» (это и был BUG-1 в Ф.14).
4. **Edge-cases протокола** — проверка симметрии: ответ из catch-ветки `fix-violation` (закрыто 12.7.4.1), retry AI explanation при 503/429, поведение при удалении ноды между запросом и ответом preview, восстановление после смены `aiEnabled` в момент активного callGemini.
5. **Регрессионная проверка** — после каждого нового шага прогон ключевых сценариев из прошлых фаз: Cmd+Z работает (Ф.11.9), Spinner показывается на сканировании (Ф.11.10), кэш Preview не дёргает API повторно (Ф.11.7), тоггл AI скрывает explanation (Ф.12.1), ErrorCard прижат к низу (Ф.14.2.10).
6. **Сравнение поведения на ДС S/M/L** — производительность сканирования (на L 500+ токенов скан занимает 20–40 сек, без Spinner — UX поломан), время отклика Fix, корректность candidates на разных размерах палитры.
7. **Визуальное сравнение реализации с макетом** — скриншоты из Figma desktop сопоставляются с эталонными макетами Ф.14 (палитра, типографика, отступы, состояния компонентов).
8. **Формирование раздела «Известные ограничения»** в отчёте сессии — фиксация принятых ограничений v1.0 (Gemini 503 retry неидеален, Preview может показать иконку как серый бокс, нет синхронизации `fixedIds` после Cmd+Z).

## 4. Зоны ответственности

- **Отвечает за:**
    - Тест-матрицы для всех шести типов нарушений детектора.
    - Прогон проверок на тестовых и реальных ДС S/M/L (Project Lead запускает в Figma desktop, QA Inspector интерпретирует результаты).
    - Структурированные баг-репорты с воспроизводимыми шагами.
    - Регрессионные чеклисты перед закрытием фазы.
    - Раздел «Известные ограничения» в отчётах сессий и финальный список перед submission.
    - Скриншоты до/после для визуального сравнения.
    - Чек-листы edge-cases (Cmd+Z, Gemini ошибки, экспорт нод разного типа).
- **НЕ отвечает за:**
    - Исправление багов — после баг-репорта маршрутизация к Backend (`Sandbox Engineer`) / Frontend (`UI Engineer`) / Design (`Visual System Designer`) через Architecture Scout.
    - Архитектурный анализ — Architecture Scout.
    - Изменение макетов — Project Lead + Visual System Designer.
    - Коммиты и версии — DevOps.
    - Само submission в Figma Community — Project Lead.
- **Остаётся за человеком (Project Lead):**
    - Ручная проверка в Figma desktop — единственный путь увидеть реальное поведение плагина в iframe Figma.
    - Финальное решение «это блокер v1.0 vs откладываем в v1.1».
    - Подтверждение готовности к submission («✅ можно публиковать»).
    - Запуск scan на реальных ДС клиентов с их разрешения.

## 5. Вход и выход

|Параметр|Значение|
|---|---|
|Формат входа|описание шага и acceptance criteria, скриншот результата от Project Lead, лог DevTools (если есть), тест-матрица, список известных ограничений из прошлых отчётов|
|Объём входа|один шаг или фаза с 5–20 шагами; до 3 ДС S/M/L; до 6 типов нарушений; полная история известных ограничений|
|Формат выхода|QA-отчёт по шагу (✅/❌ + комментарий), баг-репорт в формате «что/как/ожидалось/фактически», лог прогона тест-матрицы, обновление раздела «Известные ограничения» в отчёте сессии|
|Канал получения / возврата|чат Claude.ai (Project Lead отправляет скриншоты и логи); шаги исполняются Project Lead в Figma desktop / DevTools|

## 6. Тип решения (рекомендация)

- **Рекомендуемый тип:** Внутренний на LLM (Claude Opus 4.7 — мультимодальный для разбора скриншотов).
- **Обоснование:** Роль требует знания всех зафиксированных acceptance criteria (формат шага «Критерий успеха»), истории закрытых багов (BUG-1 чекбоксы, BUG-2 derived state, симметрия `fix-complete`, момент `commitUndo`), список известных ограничений по фазам. Часть проверки физически выполняется человеком в Figma desktop — агент работает как QA-ассистент: формирует тест-матрицы, интерпретирует скриншоты, формализует баг-репорты.
- **Альтернатива:** Кастом-сетап с автоматизированными визуальными тестами (Playwright + Figma plugin testing API) — отложено в v1.2+ из-за объёма работ и непростой интеграции с iframe Figma.

## 7. Стек и инструменты

- **Базовая модель (класс):** мультимодальная (Claude Opus 4.7 — обрабатывает скриншоты Figma desktop, DevTools-консоли, визуальные результаты компонентов).
- **Необходимые инструменты:**
    - Анализ скриншотов от Project Lead (мультимодальный вход).
    - Read-доступ к репозиторию для понимания, что именно тестируется.
    - Read-доступ к отчётам сессий — все известные ограничения и acceptance criteria.
    - Поиск в истории чатов через `conversation_search` для подъёма прошлых баг-репортов.
    - Тест-матрицы в Markdown (формируются в Project Files перед стартом Ф.15.1).
- **Хранилище контекста:** Project Files Claude.ai — отчёты сессий с разделами «Известные ограничения» и «Решения по объёму», глоссарий антипаттернов, список тестовых ДС (когда зафиксирован).
- **Интеграции:** Claude.ai чат (основной канал), Figma desktop (через Project Lead), DevTools-консоль и Network (через скриншоты от Project Lead), формальный issue tracker не используется — баги фиксируются прямо в отчётах сессий.

## 9. Ограничения и политика отказа

- **Стоп-зоны:**
    - Исправление багов — после баг-репорта маршрутизация к Backend / Frontend / Design через Architecture Scout.
    - Изменение кода (включая «вот эта одна строка точно не повлияет на остальное»).
    - Изменение макетов или компонентов дизайн-системы — Visual System Designer.
    - Архитектурные решения по фиксу — Architecture Scout + Project Lead.
    - `git commit`, `git push`, изменение версии — DevOps.
    - Публикация submission в Figma Community — Project Lead.
    - Самостоятельное решение «это блокер vs не блокер для v1.0» — формирует рекомендацию, решает Project Lead.
- **Запрещённые данные:** Google API key, любые секреты пользователей, содержимое реальных Figma-файлов клиентов без явного разрешения, скриншоты с проприетарными токенами клиентов в неанонимизированном виде.
- **Условия эскалации к Project Lead:**
    - Баг блокирует основной сценарий (запуск scan, применение Fix, переход на ReportView).
    - Результат проверки неоднозначен («что-то не так в Preview, но точно не понятно что»).
    - Нужна ручная визуальная оценка соответствия макету — Project Lead единственный имеет прямой доступ к Figma desktop.
    - Дефект воспроизводится только на реальной ДС клиента, не на тестовой.
    - Перед submission найдена регрессия в зафиксированном acceptance criteria закрытой фазы (Ф.9–Ф.14).
    - Появляется кандидат в раздел «Известные ограничения», но непонятно — это известное ограничение или блокер.

## 11. SLA и режим

- **Доступность:**
    - После каждого нелинейного фикса — перед коммитом.
    - Перед закрытием фазы — полный прогон тест-матрицы.
    - В Ф.15 — основная нагрузка (15.1–15.5 — это сплошной QA).
    - Перед submission (Ф.15.8) — финальная регрессия + проверка соответствия требованиям Figma Community.
- **Время отклика:** ≤ 5 минут на проверку отдельного шага после получения скриншота. ≤ 30 минут на полный прогон тест-матрицы фазы.
- **Нагрузка:** В рабочих фазах разработки (Ф.11–14) — 3–5 QA-шагов на сессию (после каждого блока). В Ф.15 — до 20 QA-шагов на сессию (полные прогоны).

## 13. Риски

|Риск|Митигация|
|---|---|
|Агент зафиксирует баг без воспроизводимых шагов|Жёсткий формат: «Шаги (1, 2, 3...) / Ожидалось / Фактически». Без всех трёх блоков баг-репорт возвращается на доработку.|
|Агент пропустит регрессию на реальном ДС|Тест-матрица обязательно прогоняется на S (тестовая) + M (реальная средняя ~200 токенов) + L (реальная большая 500+). Project Lead подтверждает прогоны на реальных ДС с разрешения владельцев.|
|Агент начнёт предлагать исправление вместо проверки|Жёсткое правило: QA Inspector маршрутизирует через Architecture Scout, не предлагает «давайте просто поменяем эту строку».|
|Агент не различит «известное ограничение» и «новый баг»|Перед фиксацией сверка с разделом «Известные ограничения» во всех отчётах сессий через `conversation_search`.|
|Агент пропустит edge-case 503/429 от Gemini, потому что в момент проверки квота не исчерпана|Отдельный edge-case прогон с симуляцией ошибки (Project Lead вводит невалидный API key или временно отключает сеть).|
|Агент даст ложный «✅ зафиксировано» на основании одного скриншота, не покрывающего сценарий полностью|Acceptance criteria из шага сверяется построчно — если 3 пункта, требуется подтверждение по всем 3.|
|Агент сочтёт визуально разные результаты на разных ДС нормой|На S/M/L одинаковое поведение по acceptance criteria — обязательное требование. Различия только в количестве (нарушений, токенов), не в поведении.|
|Утечка реальных данных клиентов в скриншотах|Project Lead анонимизирует скриншоты перед отправкой (стирает имена компонентов, токенов, фреймов, если они конфиденциальны).|

## 14. Критерии приёмки пилота

- **«Золотой набор»:** Полный прогон Ф.15.1 — Ф.15.5:
    - 15.1 — выбор и подготовка 3 тестовых ДС (S/M/L).
    - 15.2 — все 6 типов нарушений: детектор → Fix → Cmd+Z.
    - 15.3 — матрица фильтров: чекбоксы категорий × Scope комбинации.
    - 15.4 — edge-cases: Cmd+Z после Fix, Gemini 503/429/401, Preview на иконках/символах/группах, миграция `anthropic-api-key` → `google-api-key` для прежних пользователей beta.
    - 15.5 — опциональные баг-фиксы по результатам.
- **Порог точности:** ≥ 90% баг-репортов подтверждаются Project Lead. 100% покрытие тест-матрицы. 0 регрессий в зафиксированных acceptance criteria Ф.9–Ф.14.
- **Длительность пилота:** Сессии Ф.15.1 — Ф.15.5 (ориентировочно 1–2 рабочие сессии).
- **Условия перехода в эксплуатацию (= submission v1.0):** Агент стабильно формирует воспроизводимые баг-репорты, покрывает тест-матрицы целиком, не предлагает исправления (только маршрутизирует), корректно эскалирует блокеры Project Lead, ведёт раздел «Известные ограничения» в отчётах.

## 15. Открытые вопросы к Project Lead

- Какие тестовые ДС эталонные для S/M/L? Предложение для S — синтетический файл с 50 токенами и 10 нарушениями каждого из 6 типов. Для M — реальная ДС среднего проекта (~200 токенов, требуется выбрать). Для L — реальная enterprise-ДС (500+, требуется выбрать с разрешения владельца).
- Где хранить скриншоты до/после? Предложение: в чате с тегом `[QA SCREENSHOT]` без отдельного хранилища до v1.1 (Drive / Notion — overhead, который не окупается на single-developer проекте).
- Какие дефекты считаются блокерами submission? Предложение: блокеры — основной поток сломан (scan не запускается, Fix не применяется, плагин не открывается, Cmd+Z откатывает не то), визуальные регрессии в Ф.14-макетах, Gemini падает без graceful fallback. Не блокеры — известные ограничения уже зафиксированных долгов (Preview на иконках, retry UX).
- Какой формат «Известных ограничений» в отчётах? Предложение: текущий из отчётов Ф.11–14 (таблица «Долг / Куда») с уточнением — добавить столбец «Воспроизводится / Не воспроизводится / Условно» для снятия неоднозначности.
- Какие проверки обязательны после каждого фикса (минимальный регрессионный набор)? Предложение: основной поток (scan → Review → Fix → Cmd+Z → ReportView), плюс именно тот сценарий, на который повлиял фикс.
- Считаем ли BUG-fixes вне роадмапа (как BUG-1 / BUG-2 в Ф.14) полноценным шагом QA-роли или они проходят как часть Frontend/Backend?
