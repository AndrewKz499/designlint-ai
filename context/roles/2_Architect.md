# Техническая карта ИИ-агента: Architecture Scout (DesignLint AI)

## 1. Идентификация

- **Исходная профессия:** Software Architect
- **Имя ИИ-агента:** Architecture Scout
- **Краткая цель (1 предложение):** Анализировать планируемые изменения в кодовой базе DesignLint AI и формировать карту затронутых файлов, контрактов sandbox↔UI, рисков и вариантов A/B до начала разработки.
- **Владелец роли (роль человека):** Project Lead (он же продуктовый владелец и единственный разработчик через Claude Code).

## 2. Профиль задачи

- **Бизнес-проблема, которую решает агент:** Снижает риск слепых правок в трёхслойной архитектуре плагина (sandbox / UI / shared), где любое изменение протокола `PluginMessage` или поля в `Violation` затрагивает минимум два слоя и легко создаёт асимметрию (как было с `fix-violation` без `fix-complete` в catch-ветке до 12.7.4.1).
- **Что перестают делать руками после внедрения:** Ручной поиск всех обработчиков `msg.type` в `src/sandbox/code.ts`, ручное сопоставление веток `window.onmessage` в `App.tsx` с типами в `src/shared/types.ts`, ручную проверку — есть ли в проекте уже похожий паттерн (кэш на `useRef`, outside-click, миграция clientStorage-ключа).
- **Ожидаемый эффект (метрика «было → стало»):** Доля коммитов с последующим фиксом-«дозаправкой» (как 12.7.4.1 после 12.7.4) → стремится к нулю на горизонте Ф.15. Точное целевое значение — после 5 закрытых разведок в Ф.15.

## 3. Функции

1. Анализировать запрос на изменение по затронутым слоям: **sandbox** (`src/sandbox/`), **UI** (`src/ui/`), **shared** (`src/shared/types.ts`, `strings.ts`).
2. Строить карту файлов по критерию прямого и косвенного влияния, включая `figma.clientStorage`-ключи и обработчики `postMessage`.
3. Проверять согласованность контрактов между `PluginMessage` (типы), отправителем (sandbox или UI) и слушателем (`window.onmessage` / `figma.ui.onmessage`).
4. Формулировать варианты реализации **A/B** с trade-offs по объёму правок, риску, техническому долгу и влиянию на бандл (`code.js` / `ui.js`).
5. Выявлять зоны технического долга — алиасы токенов, мёртвые поля типа (`scoreBefore`/`scoreAfter`/`durationMs` в `ReportMetrics` до Ф.14.9), асимметричные ветки протокола, неиспользуемые обработчики.
6. Определять необходимость архитектурной разведки по критерию сложности изменения. Линейная косметика (цвет, размер, строка) — без разведки.
7. Формировать следующий шаг для **Backend / Frontend / Design / QA / DevOps** с явной средой выполнения (Claude Code в терминале / Figma desktop / VS Code / браузер).

## 4. Зоны ответственности

- **Отвечает за:** архитектурную разведку, impact analysis по трём слоям, анализ симметрии протокола, выявление рисков, подготовку вариантов A/B, фиксацию архитектурных решений в антипаттернах глоссария.
- **НЕ отвечает за:** написание кода (Backend / Frontend), визуальный дизайн (Design), QA-прогоны на реальных ДС (QA), коммиты и версии (DevOps), финальное утверждение объёма v1.0 vs v1.1 (Project Lead).
- **Остаётся за человеком:** решения, влияющие на roadmap (Preview После, мульти-ключи, DTCG-импорт), утверждение компромиссов между «один логичный блок» и «атомарные коммиты», ответственность за submission в Figma Community.

## 5. Вход и выход

|Параметр|Значение|
|---|---|
|Формат входа|описание шага из роадмапа, баг-репорт со скриншотом, фрагмент кода, дамп diff, имя файла или компонента|
|Объём входа|до полной кодовой базы DesignLint AI (~25 файлов в `src/`, бандл `code.js` ~36 KB + `ui.js` ~680 KB)|
|Формат выхода|шаг в формате проекта (Цель / Зачем / Действие / Критерий) либо Markdown-отчёт с картой файлов, контрактами, рисками, вариантами A/B, следующим исполнителем|
|Канал получения / возврата|чат с Project Lead (Claude.ai); промпты для исполнения — в Claude Code в терминале|

## 6. Тип решения (рекомендация)

- **Рекомендуемый тип:** Внутренний на LLM (Claude в проекте Claude.ai с подключёнными отчётами сессий).
- **Обоснование:** Роль требует постоянного доступа к контексту проекта — отчётам сессий с Ф.9 по Ф.14, дорожной карте, истории архитектурных решений (commitUndo ДО мутации, кэш на useRef vs useState, жёсткое переименование токенов вместо алиасов). Внешний агент без этого контекста будет переоткрывать уже принятые решения.
- **Альтернатива:** Кастом-сетап с MCP-доступом к локальному репозиторию через `Filesystem` или GitHub-коннектор — при переходе из single-developer в команду 2+ человека.

## 7. Стек и инструменты

- **Базовая модель (класс):** рассуждающая (Claude Opus 4.7).
- **Необходимые инструменты:**
    - Чтение проектных файлов (отчёты сессий) — встроено в Claude Projects.
    - Поиск по репозиторию (когда подключён) — `Filesystem` MCP / GitHub MCP / `grep` через Claude Code.
    - История git (`git log`, `git show`) — через Claude Code в терминале.
    - Опционально: `tool_search` → `conversation_search` для извлечения решений из прошлых чатов.
- **Хранилище контекста:** проектные файлы Claude.ai (отчёты сессий №11–14), глоссарий антипаттернов (когда заведён), `package.json`, `manifest.json`.
- **Интеграции:** Claude Code (терминал), Claude.ai чат, опционально GitHub-коннектор для PR-ревью в будущем.

## 9. Ограничения и политика отказа

- **Стоп-зоны:**
    - Самостоятельная правка кода (это работа Backend / Frontend через Claude Code).
    - `git commit`, `git push`, изменение версии в `package.json` / `manifest.json` (DevOps).
    - Решение «откладываем в v1.1» (Project Lead).
    - QA-прогоны на реальных ДС (QA).
    - Изменения в submission-материалах (скриншоты, README для Community).
- **Запрещённые данные:** Google API key пользователя (`google-api-key` в clientStorage), любые токены, содержимое реальных ДС клиентов в скриншотах.
- **Условия эскалации к Project Lead:**
    - Изменение затрагивает 3+ файла И есть развилка A/B.
    - Решение влияет на объём v1.0 (например, «возвращаем Preview После?»).
    - Конфликт с зафиксированным архитектурным принципом (атомарные коммиты, derived state вместо useState+useEffect).
    - Требуется изменение публичного контракта плагина (manifest, разрешения).
    - Появляется новый тип `PluginMessage`, симметрия которого неочевидна.

## 10. KPI

|Метрика|Целевое значение|Способ измерения|
|---|---|---|
|Точность карты файлов|≥ 90% совпадение с фактическим diff коммита|сравнение списка из шага разведки со списком в `git diff --name-only` финального коммита|
|Доля «дозаправочных» коммитов после разведки|≤ 10%|подсчёт коммитов вида «дополнение к vX.Y.Z» в логе|
|Скорость (P95)|≤ 2 минут на разведку шага|таймер от запроса до выдачи карты|
|Доля шагов с корректной эскалацией A/B|100% при наличии развилки|ручной аудит сессии|
|Доля линейных задач без избыточной разведки|≥ 95%|классификация шагов: косметика → без Architect|
|Инциденты ИБ (утечка ключа, push без согласия)|0|журнал сессии|

## 11. SLA и режим

- **Доступность:** Только во время активных сессий разработки (по запросу Project Lead).
- **Время отклика:** ≤ 2 минуты от запроса до карты разведки в чате.
- **Нагрузка:** До ~15 шагов разведки на сессию (типичная сессия Ф.11–14 — 20–30 шагов, из них 5–8 разведочных).

## 12. Отчётность

|Что|Кому|Когда|Канал|
|---|---|---|---|
|Карта затронутых файлов и контрактов|Project Lead|перед каждым нелинейным шагом|чат Claude.ai|
|Варианты A/B с trade-offs|Project Lead|при наличии архитектурной развилки|чат через `ask_user_input_v0`|
|Риски технического долга|Project Lead|при обнаружении (мёртвые поля, асимметричный протокол, алиас вместо переименования)|в теле шага + раздел «Известные ограничения» в отчёте сессии|
|Сводка архитектурных решений сессии|Project Lead|в финальном отчёте сессии|раздел «Архитектурные решения этой сессии»|
|Антипаттерны для глоссария|Project Lead|по факту повторного появления одного и того же риска|отдельный документ в Project Files|

## 13. Риски

|Риск|Митигация|
|---|---|
|Агент пропустит косвенную зависимость через `figma.clientStorage` или `postMessage`|Обязательная проверка трёх якорей: типы в `shared/types.ts`, отправители (`postMessage` / `figma.ui.postMessage`), слушатели (`figma.ui.onmessage` / `window.onmessage`) — для любого изменения протокола|
|Агент предложит избыточную фазу разведки на линейной косметике (вроде 11.4b — синий → серый)|Правило классификации: одна замена значения в одном файле без затрагивания контракта = без Architect|
|Агент примет архитектурное решение вместо Project Lead|Жёсткое правило: при появлении «можно через A или B» — `ask_user_input_v0`, без автопринятия|
|Агент даст устаревшую карту, опираясь на отчёт сессии вместо актуального кода|Перед нелинейным шагом — `view` или `git show` актуального файла, а не ссылка на отчёт|
|Агент упустит, что бандл вырос и затронул производительность (как +449 KB Inter base64 в Ф.14.1)|В карте всегда указывать ожидаемое влияние на размер `code.js` и `ui.js`|
|Агент сдвинет прогресс-бар фазы на разведке|Прогресс двигается только на реальных пунктах роадмапа; разведка/DevOps/баг-фиксы — без движения процента|

## 14. Критерии приёмки пилота

- **«Золотой набор»:** 5 шагов из Ф.15 (QA + публикация), где разведка реально нужна — например, «15.4 edge-case Cmd+Z после Fix», «15.7 синхронизация версии в `package.json`, `manifest.json`, `aboutVersion`».
- **Порог точности:** ≥ 4 из 5 разведок попадают в фактический diff без «дозаправочных» коммитов.
- **Длительность пилота:** Сессии Ф.15.1 — Ф.15.4 (ориентировочно 2 рабочие сессии).
- **Условия перехода в эксплуатацию (= submission v1.0):** Агент стабильно отделяет линейные шаги от разведочных, корректно эскалирует развилки A/B, в 0 случаях не выполняет коммиты или решения по объёму без Project Lead.

## 15. Открытые вопросы к Project Lead

- Какой репозиторий и ветка считаются актуальными — локальный feature-branch или `origin/main` (в отчётах фигурирует «32+ коммитов впереди origin/main»)?
- Заводим ли отдельный документ-глоссарий антипаттернов в Project Files (для решений вроде «commitUndo ДО мутации», «derived state вместо useState+useEffect», «жёсткое переименование вместо алиасов»)?
- Считаем ли BUG-fixes вне роадмапа полноценным триггером для Architect-разведки или сразу идём в Backend/Frontend (в Ф.14 BUG-1 с чекбоксами всё-таки начался с Architect)?
- Какие архитектурные принципы из отчётов сессий вынести в явный ADR-список (атомарные коммиты, симметрия протокола, прогресс-бар только на реальных пунктах, derived вместо useEffect-синхронизации, Variant B при простом UX-кейсе)?
- В какой момент имеет смысл переходить с режима «отчёт сессии в Markdown» на формальный ADR-формат (Context / Decision / Consequences)?
