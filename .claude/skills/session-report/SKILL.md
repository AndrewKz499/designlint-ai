# Skill: session-report

Этот навык формирует **финальный отчёт сессии** в строгом формате проекта. Отчёт — это главный артефакт документирования: он попадает в `context/sessions/`, становится baseline для `@analytics` и историческим контекстом для будущих сессий.

## Когда использовать

Используй этот навык всегда, когда нужно зафиксировать результаты завершённой сессии:

- В конце фазы (Ф.NN) — финальный отчёт со всеми шагами фазы.
- В конце большой рабочей сессии (даже если фаза не закрыта).
- При требовании Project Lead'а «зафиксируй сессию».
- Перед закрытием большого блока работы (например, перед submission в Figma Community).

## Когда НЕ использовать

Не оборачивай в формат отчёта сессии:
- Промежуточные статусы внутри сессии («что сделано на данный момент»).
- Короткие заметки о решениях — для них есть ADR (отдельный skill).
- Технические детали одного шага — это в commit-message и в самом коде.
- Открытые обсуждения, которые не привели к решению — это в `Открытые вопросы` финального отчёта, но не отдельным документом.

## Что НЕ делай этим скиллом

- Не пиши отчёт **до закрытия сессии**. Если сессия в процессе — скажи Project Lead'у, что отчёт будет после закрытия.
- Не дублируй содержимое карт ролей, ADR, глоссария. Отчёт **ссылается** на них, а не копирует.
- Не выдумывай acceptance criteria шагов задним числом. Если критерий не был зафиксирован при формулировке шага — отметь явно «критерий не зафиксирован».
- Не фиксируй архитектурное решение «от себя». Принцип проекта: `@architect` формулирует, `@project-lead` утверждает, `@doc-writer` только записывает утверждённое.
- Не пропускай раздел «Известные ограничения» — даже если ограничений нет, явно пиши «новых известных ограничений нет».

## Семь обязательных секций

Каждый отчёт содержит **все** эти секции в строгом порядке.

| Секция | Что туда писать |
|---|---|
| **Заголовок** | `# Отчёт сессии Ф.<NN> — <тема>` |
| **Контекст** | 1–2 абзаца: с чего начали сессию, что было baseline, какая была главная цель |
| **Выполненные шаги** | Все шаги в формате skill `step-format` (Цель / Зачем / Действие / Критерий / Среда / Исполнитель) с маркером результата ✅/❌ |
| **Архитектурные решения** | Список ADR-ссылок (`ADR-NNN`), которые были приняты в этой сессии. Если новых ADR нет — явно пиши «новых ADR нет» |
| **Известные ограничения** | Кандидаты в раздел «Known issues v1.0» от `@qa`. Таблица: # / Ограничение / Затронуто / Принято потому что / План v1.x |
| **Решения по объёму** | Что ушло в v1.1 в этой сессии и почему. Список с обоснованиями |
| **Коммиты сессии** | Список от `@devops`: vX.Y.Z — описание (`<hash>`). По одной строке на коммит |
| **Открытые вопросы** | Что не решено и должно быть рассмотрено в следующей сессии |

## Формат вывода

Используй ровно этот шаблон:

```markdown
# Отчёт сессии Ф.<NN> — <тема>

## Контекст

<1–2 абзаца: с чего начали, какой был baseline, главная цель сессии.>

## Выполненные шаги

### Ф.<NN.X> — <название шага>
- **Цель:** <из step-format>
- **Действие:** <из step-format>
- **Критерий успеха:** ✅ <как проверили> / ❌ <что не сошлось>
- **Исполнитель:** @<роль>

### Ф.<NN.Y> — <название шага>
- **Цель:** ...
- **Действие:** ...
- **Критерий успеха:** ✅ ...
- **Исполнитель:** @<роль>

<...>

## Архитектурные решения

- ADR-<NNN> — <короткое описание> (см. `context/architecture/adr-NNN-<тема>.md`)

или

«Новых ADR в этой сессии нет.»

## Известные ограничения

| # | Ограничение | Затронуто | Принято в v1.0 потому что | План v1.x |
|---|---|---|---|---|
| 1 | <ограничение> | <модуль/экран> | <причина> | v1.X |

или

«Новых известных ограничений в этой сессии нет.»

## Решения по объёму

В v1.1 ушло:
- <фича X> — потому что <обоснование по фильтрам приоритетов>
- <фича Y> — потому что <обоснование>

или

«Объём v1.0 не пересматривался.»

## Коммиты сессии

- v<X.Y.Z> — <тема коммита> (`<hash>`)
- v<X.Y.Z> — <тема коммита> (`<hash>`)

## Открытые вопросы

1. <вопрос или нерешённое решение>
2. <вопрос или нерешённое решение>

или

«Открытых вопросов нет — фаза закрыта.»
```

## Правила заполнения

### Раздел «Контекст»

Пиши коротко и фактически. Не пересказывай предыдущие отчёты. Достаточно:
- С чего начали (последний коммит сессии до этой / закрытая фаза до этой).
- Какая главная цель сессии («закрыть Ф.15.2 — асимметрии PluginMessage»).
- Что было baseline («v0.14.13, 5 асимметричных handler'ов из аудита Ф.15.1»).

### Раздел «Выполненные шаги»

Один шаг = одна запись. Маркер результата обязателен:

- **✅** — критерий выполнен полностью.
- **❌** — критерий не выполнен. Обязательно объясни, что именно не сошлось.
- **⚠️** — критерий выполнен с оговорками (например, скриншот соответствует, но размер бандла вырос больше ожидаемого). Опиши оговорку.

Если шаг переехал в следующую сессию — отметь явно «отложено в Ф.<NN+1>», не пиши «в процессе».

### Раздел «Архитектурные решения»

Только ADR, **утверждённые** Project Lead'ом в этой сессии. Не включай:
- Обсуждения без решения.
- Архитектурные предположения от `@architect` без выбора Project Lead'ом.
- Ретроспективные «вот теперь понятно как надо было».

Если ADR ещё не оформлены отдельным файлом — это ок, пиши «ADR-<NNN> утверждён, файл будет создан в Ф.<NN+1>».

### Раздел «Известные ограничения»

Источник — `@qa`. Если `@qa` не выдал список — спроси его явно перед формированием отчёта.

Каждое ограничение должно иметь:
- Что именно ограничено.
- Какой модуль/экран затронут.
- Причину принятия (одна из четырёх стандартных: «редкий случай», «не блокирует submission», «не вносит хрупкости», «требует крупной переработки — отложено»).
- Целевую версию для исправления.

### Раздел «Решения по объёму»

Пишется только если в этой сессии произошло перераспределение между v1.0 и v1.1. Источник — решения `@project-lead`. Без источника — не пиши «отложено», даже если кажется очевидным.

### Раздел «Коммиты сессии»

Источник — `@devops`. Запроси у него явно: «Какие коммиты были в этой сессии?» — и получи список с хешами и темами. Не выдумывай хеши.

### Раздел «Открытые вопросы»

Только то, что должно быть рассмотрено в следующей сессии. Не складывай сюда:
- Идеи «было бы неплохо когда-нибудь» — это в общий бэклог v1.1, не в отчёт.
- Архитектурные обсуждения, которые ещё не нашли владельца — эскалируй к `@project-lead` до отчёта.

## Связь с другими документами

Отчёт — это **узловой** документ, который ссылается на:

| Документ | Куда ссылается |
|---|---|
| ADR | в раздел «Архитектурные решения» |
| Глоссарий (`context/glossary/`) | если в сессии появились новые термины — ссылка |
| Антипаттерны (`context/architecture/antipatterns.md`) | если в сессии появился новый антипаттерн — ссылка |
| README / README_TESTER | если в сессии менялась документация для пользователей — ссылка |
| Карты ролей (`context/roles/`) | если уточнялась чья-то зона ответственности — ссылка |

Дублировать содержимое этих документов **не нужно**.

## Связь с архитектурными принципами

Этот skill реализует принципы из CLAUDE.md:

- **Чистая git-история** — раздел «Коммиты сессии» должен соответствовать `git log` для периода сессии.
- **Атомарность шагов** — каждый шаг в отчёте имеет один результат (✅ / ❌ / ⚠️), не «частично закрыто».
- **Документация соответствует коду** — если шаг ✅, в коде это должно быть видно. `@analytics` потом проверит.

## Перед отдачей отчёта проверь

- [ ] Все семь обязательных секций заполнены (или явно «не применимо»).
- [ ] Каждый шаг имеет маркер результата (✅ / ❌ / ⚠️).
- [ ] Архитектурные решения — только утверждённые `@project-lead`.
- [ ] Известные ограничения — получены от `@qa` явным запросом.
- [ ] Коммиты сессии — получены от `@devops` с реальными хешами.
- [ ] Открытые вопросы — только то, что должно быть в следующей сессии.
- [ ] Нет дублирования с ADR / глоссарием / антипаттернами — только ссылки.
- [ ] Файл сохранён в `context/sessions/session-report-<NN>.md` (не в Project Files Claude.ai).
- [ ] Имя файла соответствует номеру фазы (`session-report-15.md` для Ф.15).
