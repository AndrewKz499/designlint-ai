# Skill: adr

Этот навык формирует **Architecture Decision Record** — документ, фиксирующий одно архитектурное решение в контексте, в котором оно было принято. ADR не пересматривается задним числом — если решение меняется, создаётся новый ADR со статусом «Заменяет ADR-NNN».

## Когда использовать

Используй этот навык, когда выполнены **все три условия**:

1. `@architect` сформулировал варианты решения (минимум A/B).
2. `@project-lead` выбрал один из вариантов **явно** в чате (не «вроде ок», а «✅ выбираю вариант A» или эквивалент).
3. Решение влияет на архитектуру (контракт между слоями, паттерн использования API, формат данных, политика версионирования) — а не на одну строчку кода.

## Когда НЕ использовать

Не оборачивай в формат ADR:
- Решение «в процессе обсуждения» — пока `@project-lead` не утвердил, ADR нет.
- Тактические решения, не влияющие на архитектуру (выбор имени переменной, выбор отступа, выбор формулировки строки в UI).
- Гипотезы и предположения — даже если они от `@architect`.
- Изменения в продуктовых решениях (что отображать на экране, какой UX) — это в отчёте сессии, не ADR.

Для не-архитектурных утверждённых решений достаточно записи в отчёте сессии (раздел «Архитектурные решения» с указанием «без отдельного ADR»).

## Что НЕ делай этим скиллом

- Не пиши ADR от своего лица. Ты `@doc-writer`, не `@architect` и не `@project-lead`. Ты только фиксируешь.
- Не дополняй ADR гипотезами или возможными последствиями, которых не обсуждали.
- Не пересматривай существующий ADR. Если решение изменилось — создай новый ADR со статусом «Заменяет ADR-NNN», а старому смени статус на «Отменён».
- Не пропускай раздел «Альтернативы». Если в реальности развилки A/B не было (вариант был один) — явно пиши «развилка отсутствовала», не выдумывай альтернативы.

## Семь обязательных секций

| Секция | Что туда писать |
|---|---|
| **Заголовок** | `# ADR-<NNN>: <короткое название решения>` |
| **Статус** | `Принято` / `На рассмотрении` / `Отменён` / `Заменяет ADR-<NNN>` / `Заменён ADR-<NNN>` |
| **Дата** | YYYY-MM-DD — когда `@project-lead` утвердил |
| **Контекст** | 1–2 абзаца: какая ситуация заставила принимать решение, что было в коде до этого |
| **Решение** | Один абзац: что **конкретно** утверждено. Без «возможно», «лучше», «попробуем» — только утвердительная формулировка |
| **Альтернативы** | Минимум один альтернативный вариант с указанием, почему не выбрали (если развилки не было — явно «развилка отсутствовала, единственный вариант — текущий») |
| **Последствия** | Положительные / Отрицательные / Технический долг (что может вырасти после этого решения) |
| **Прецеденты** | Ссылки на отчёты сессий или коммиты, где это решение было принято и впервые применено |

## Нумерация ADR

Сквозная по проекту, начиная с `ADR-001`. Перед созданием нового — посмотри в `context/architecture/`, какой номер последний. Не используй даты в номере (они уже в поле «Дата»).

Имя файла:

```
context/architecture/adr-<NNN>-<краткая-тема>.md
```

Примеры:
- `adr-001-tokens-without-aliases.md`
- `adr-007-useref-cache-for-preview.md`
- `adr-009-plugin-message-symmetry.md`

Тема в имени файла — на латинице, через дефисы. На русском писать только в заголовке внутри документа.

## Формат вывода

Используй ровно этот шаблон:

```markdown
# ADR-<NNN>: <название решения на русском>

## Статус
Принято

## Дата
YYYY-MM-DD

## Контекст

<1–2 абзаца о ситуации, которая заставила принимать решение. Что было в коде до этого. Какая проблема обнаружилась. Кто её обнаружил (роль, не имя).>

## Решение

<Один абзац, утвердительно. «Используем X», «Запрещаем Y», «Применяем паттерн Z».>

## Альтернативы

**Вариант B (отклонён):** <описание>
- Почему не выбрали: <обоснование>

**Вариант C (отклонён):** <описание, если был>
- Почему не выбрали: <обоснование>

или

**Развилка отсутствовала.** Единственный вариант — текущий, потому что <обоснование>.

## Последствия

**Положительные:**
- <что становится лучше>

**Отрицательные:**
- <что становится хуже>

**Технический долг:**
- <что может вырасти и потребовать пересмотра в будущем>

или

«Технический долг не ожидается.»

## Прецеденты

- Ф.<NN.X> — <где впервые применено>
- Коммит `<hash>` — <короткое описание>
- BUG-<N> — <если решение закрывает конкретный баг>
```

## Примеры

### Хороший ADR

```markdown
# ADR-007: Кэш Preview на useRef вместо useState

## Статус
Принято

## Дата
2024-12-15

## Контекст

В Ф.11.7 обнаружено, что компонент Preview дёргает Gemini API повторно при каждом ре-рендере родительского компонента. Кэш на `useState` вызывал ре-рендер при обновлении, что создавало замкнутый цикл: ре-рендер → проверка кэша → API-запрос → setState → ре-рендер.

## Решение

Кэш Preview хранится в `useRef`. Чтение и запись через `.current`. Ре-рендер на изменение кэша **не** вызывается. Инвалидация кэша явная — через клик «Refresh» или смену violation.

## Альтернативы

**Вариант B (отклонён):** `useState` с `useMemo`-обёрткой. Не выбрали: всё равно вызывает ре-рендер при `setState`, проблема не решается.

**Вариант C (отклонён):** Внешний кэш в singleton-объекте. Не выбрали: усложняет тестирование, ломает изоляцию компонента.

## Последствия

**Положительные:**
- API-вызовы Gemini сокращаются на 60–80% при типичной навигации в Review.
- Уходит замкнутый цикл ре-рендеров.

**Отрицательные:**
- Кэш не инвалидируется автоматически при изменении пропсов — нужна явная логика инвалидации.

**Технический долг:**
- Если в будущем добавится Preview История с несколькими ключами кэша — `useRef` придётся обернуть в Map. Несложно, но не одной строкой.

## Прецеденты

- Ф.11.7.4 — первое применение в `Preview.tsx`.
- Коммит `a3f7e2c` — v0.11.7 — feat кэш Preview на useRef.
```

### Плохой ADR (НЕ делать)

```markdown
# ADR-?: Может быть стоит использовать useRef

## Статус
В процессе обсуждения

## Контекст
В Preview какие-то проблемы с ре-рендерами, кажется.

## Решение
Возможно, лучше использовать useRef.
```

Что не так:
- Статус «В процессе» — ADR создаётся **после** утверждения, не во время обсуждения.
- «Возможно, лучше» — не утвердительная формулировка.
- «Какие-то проблемы, кажется» — не конкретный контекст.
- Нет альтернатив, последствий, прецедентов.
- Нет даты, нет номера.

## Связь с другими документами

ADR — это **источник правды** для архитектурных решений. На него ссылаются:

- **Отчёты сессий** — в разделе «Архитектурные решения» — `ADR-NNN — <короткое описание>`.
- **Антипаттерны** (`context/architecture/antipatterns.md`) — если решение запрещает паттерн, антипаттерн ссылается на ADR.
- **Карты ролей** — если решение меняет зону ответственности роли — ссылка на ADR в карте.
- **CLAUDE.md** — если решение становится принципом проекта — добавляется в раздел «Архитектурные принципы».

ADR **не** дублирует содержимое этих документов — наоборот, он первоисточник.

## Связь с архитектурными принципами

Этот skill реализует принципы из CLAUDE.md:

- **Чистая документация** — каждое решение зафиксировано один раз, в одном месте.
- **Документация соответствует коду** — раздел «Прецеденты» содержит ссылки на коммиты, где решение применено.
- **Решения не пересматриваются «от себя»** — изменение требует нового ADR со ссылкой на отменённый.

## Перед отдачей ADR проверь

- [ ] Все семь обязательных секций заполнены.
- [ ] Статус — `Принято` (не «В процессе», не «Возможно»).
- [ ] Дата — реальная дата утверждения `@project-lead`.
- [ ] Контекст — конкретный, с указанием фазы или коммита.
- [ ] Решение — утвердительное, без «возможно», «лучше», «попробуем».
- [ ] Альтернативы — минимум одна (или явно «развилка отсутствовала»).
- [ ] Последствия — все три подраздела (положительные / отрицательные / технический долг).
- [ ] Прецеденты — реальные ссылки на фазы и коммиты, не выдумка.
- [ ] Имя файла соответствует шаблону `adr-<NNN>-<латиница-через-дефис>.md`.
- [ ] Нумерация сквозная — следующий номер после максимального в `context/architecture/`.
