# Skill: commit-message

Этот навык формирует **атомарный, читаемый коммит** в формате проекта DesignLint AI. Атомарность — главный критерий: один коммит = один логический блок изменений.

## Когда использовать

Используй этот навык всегда перед `git commit`, включая:

- Версионные коммиты (`vX.Y.Z — описание`).
- Фиксы багов (`fix: ...`).
- Новые фичи (`feat: ...`).
- Документационные коммиты (`docs: ...`).
- Рефакторинг (`refactor: ...`).
- Поддержку git-истории (`chore: ...`).

Проверка чужого коммита перед `--amend` или `rebase --reword` — также используй этот навык.

## Что НЕ делай этим скиллом

- Не пиши коммит с **несколькими логическими темами**. Если в stage три темы — три коммита. Разбирай через `git add -p` или `git restore --staged <file>`.
- Не пиши коммит **без проверок** (`tsc --noEmit`, `npm run build`).
- Не пиши коммит, **не проверив stage на секреты** (`git diff --staged | grep -i "AIza\|api[_-]key\|secret"`).
- Не пиши коммит с версией в `package.json`, **если не обновил её** в двух других местах (`manifest.json` если содержит, `aboutVersion` в `src/shared/strings.ts`).
- Не пиши коммит **до получения «✅ зафиксировано»** от агента-исполнителя (`@backend` / `@ui-engineer`).

## Формат темы коммита

### Версионный коммит

```
v<X.Y.Z> — <короткое описание в Past Simple>
```

Примеры:
- `v0.14.13 — fix чекбокс категорий не фильтрует Review`
- `v0.14.20 — feat добавлен Spinner на ds-scan-confirmed`
- `v0.13.6 — fix симметрия fix-violation в catch-ветке`

Правила:
- Длина темы — **до 72 символов** (включая `vX.Y.Z`).
- После версии — длинное тире `—` (не дефис, не двойной дефис).
- Описание — короткое, в прошедшем времени.
- Никаких точек в конце темы.

### Фикс / фича / docs / refactor / chore (без бампа версии)

Используй conventional commits, когда коммит **не меняет версию** (например, поправка README, чистка комментариев, реорганизация без функциональных изменений):

```
<тип>: <короткое описание>
```

Типы:
- `fix` — исправление бага.
- `feat` — новая функциональность.
- `docs` — документация (README, README_TESTER, CHANGELOG, ADR).
- `refactor` — рефакторинг без изменения поведения.
- `chore` — поддержка (git-история, .gitignore, конфиги).
- `style` — только форматирование, не визуальные стили.

Примеры:
- `docs: добавлен ADR-007 по выбору useRef для кэша Preview`
- `chore: добавлен logs/ в .gitignore`
- `refactor: вынесен PluginMessage в src/shared/types.ts`

### Когда что использовать

| Изменение | Формат |
|---|---|
| Меняет поведение плагина → нужен релиз → бамп версии | `vX.Y.Z — описание` |
| Не меняет поведение пользователя (доки, конфиги, чистка) | `<тип>: описание` |
| Внутренний рефакторинг без функциональных изменений | `refactor: описание` |

## Формат тела коммита

Тело **не обязательно** для тривиальных изменений. Но обязательно для:

- Версионных коммитов с >1 затронутым файлом — перечисли файлы и кратко опиши, что в каждом.
- Коммитов, фиксирующих архитектурное решение — ссылка на ADR / отчёт сессии.
- Коммитов с известными ограничениями — явно в теле.

### Шаблон тела

```
<пустая строка после темы>
Изменения:
- src/<file>: <что поменялось>
- src/<file>: <что поменялось>

Проверки:
- tsc --noEmit: ✅
- build: ✅
- Размер dist/<bundle>: <до> → <после> (Δ <значение>)

Связано: ADR-<NNN> / Ф.<NN.X> / BUG-<N>

Известные ограничения: <если есть>
```

## Обязательные проверки перед коммитом

Пройди этот чеклист **в порядке**, прежде чем формировать commit-message:

1. **`git status`** — что в stage, что в working tree. Stage должен содержать **только одну тему**.
2. **`git diff --staged`** — что точно идёт в коммит. Прочитай diff целиком, не пропуская.
3. **Проверка секретов:** `git diff --staged | grep -i "AIza\|api[_-]key\|secret\|token"`. Если найдено что-то похожее на ключ — **отказ от коммита**, эскалация к `@lead-architect`.
4. **`npx tsc --noEmit`** — типы чисты.
5. **`npm run build`** (если есть в `package.json` → `scripts`) — сборка проходит.
6. **`ls -la dist/`** — замерь размер бандла, сравни с предыдущим коммитом (`git show HEAD:package.json` или `git log --shortstat`).
7. **Если меняется версия** — проверь синхронизацию в трёх местах:
   - `package.json` → `version`
   - `manifest.json` → `version` (если содержит это поле)
   - `aboutVersion` в `src/shared/strings.ts`
   
   Если версия только в одном месте — **отказ от коммита**, добавь синхронизацию.

## Примеры

### Хороший версионный коммит

**Тема:**
```
v0.14.20 — fix симметрия set-api-key в catch-ветке
```

**Тело:**
```
Изменения:
- src/sandbox/code.ts: добавлен postMessage('set-api-key-done', {success: false}) в catch
- src/shared/types.ts: расширен SetApiKeyDoneMessage полем error?: string

Проверки:
- tsc --noEmit: ✅
- build: ✅
- Размер dist/code.js: 36.6 KB → 36.7 KB (Δ +0.1 KB)
- Размер dist/ui.js: 681 KB (без изменений)

Связано: BUG-15, ADR-009
```

### Хороший фикс-коммит без бампа

**Тема:**
```
docs: уточнён глоссарий — Active pool vs filteredViolations
```

**Тело (опционально):**
```
Связано: Ф.14.9 — после удаления мёртвых полей ReportMetrics
термины «Active pool» и «filteredViolations» расходились.
Глоссарий уточнён, добавлена перекрёстная ссылка.
```

### Плохой коммит (НЕ делать)

**Тема:**
```
fixes
```

Что не так:
- Ни типа, ни описания — что именно фиксили?
- Не понять, нужно ли смотреть этот коммит при ретроспективе.

**Тема:**
```
v0.14.21 — поправил баг с категориями и заодно подкрутил Spinner и удалил мёртвый код в ReportView
```

Что не так:
- Три темы в одном коммите — нужно три коммита.
- Длина темы > 72 символов.
- При откате одного из изменений — придётся откатывать всё.

## Синхронизация версий — критичный момент

DesignLint AI хранит версию в **трёх местах одновременно**:

| Место | Поле | Как обновлять |
|---|---|---|
| `package.json` | `"version": "0.14.X"` | через `Edit` или `npm version` |
| `manifest.json` | `"version": "0.14.X"` (если есть) | через `Edit` |
| `src/shared/strings.ts` | `aboutVersion: "v0.14.X"` или `"0.14.X"` | через `Edit` |

**Любое расхождение — баг.** Перед коммитом грепни: `grep -rn "0\.14\." package.json manifest.json src/shared/strings.ts`. Все три должны показать **одинаковое** значение.

Если в `manifest.json` нет поля `version` — это нормально, не добавляй его без согласования с `@lead-architect`.

## Связь с архитектурными принципами

Этот skill реализует два зафиксированных принципа проекта (см. CLAUDE.md):

- **Атомарные коммиты** — один логический блок = один коммит.
- **Версия в трёх местах одновременно** — расхождение = баг.

Нарушение любого — эскалация к `@lead-architect`.

## Перед отдачей коммита проверь

- [ ] Stage содержит **только одну** логическую тему.
- [ ] `git diff --staged` прочитан целиком.
- [ ] Нет секретов (grep AIza/api_key/secret/token чист).
- [ ] `tsc --noEmit` прошёл.
- [ ] `npm run build` прошёл (если есть скрипт).
- [ ] Размер бандла замерен и указан в теле (если есть значимое изменение).
- [ ] Если меняется версия — обновлена во всех трёх местах.
- [ ] Тема ≤ 72 символов, в прошедшем времени, без точки.
- [ ] Тип коммита (`fix:` / `feat:` / `docs:` / `refactor:` / `chore:` / `vX.Y.Z`) выбран правильно.
- [ ] Тело заполнено (если применимо).
- [ ] Получено «✅ зафиксировано» от агента-исполнителя (`@backend` / `@ui-engineer`).
