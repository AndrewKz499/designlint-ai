# Skill: step-format

Этот навык формирует **формализованный шаг дорожной карты** в шести обязательных полях. Формат закреплён в проекте по итогам Ф.11–14 и обеспечивает: 1) проверяемость результата, 2) ясную маршрутизацию, 3) единое понимание среды выполнения.

## Когда использовать

Используй этот навык всегда, когда нужно зафиксировать задачу для исполнителя:

- Новый шаг внутри открытой фазы дорожной карты.
- Декомпозиция сложной задачи на атомарные шаги.
- Передача задачи от `@architect` (после разведки) к исполнителю.
- Передача задачи от `@qa` (после баг-репорта) к `@architect` → исполнителю.
- Финальный шаг сессии, который должен попасть в отчёт от `@doc-writer`.

## Когда НЕ использовать

Не оборачивай в формат шага:
- Короткие ответы и реплики в чате («да», «согласен», «давай»).
- Разъяснения и рассуждения вслух (когда `@project-lead` думает, а не ставит задачу).
- Открытые вопросы, на которые нужен ответ от Product Owner — это `ask_user_input_v0`, не шаг.
- Промежуточные комментарии типа «продолжай», «ок, дальше».

Формат шага — **тяжёлая** конструкция. Не используй её там, где достаточно одного предложения.

## Что НЕ делай этим скиллом

- Не пиши шаг с расплывчатой целью («улучшить UX», «причесать код», «посмотреть что не так»). Цель должна быть проверяемой.
- Не пиши шаг без критерия успеха. «Сделать хорошо» — не критерий.
- Не пиши шаг без явной среды выполнения. Без среды исполнитель не понимает, где физически работать (Claude Code в терминале / Figma desktop / VS Code / браузер).
- Не пиши шаг без явного исполнителя (`@<роль>`). «Кто-то должен сделать» — не задача.
- Не объединяй несколько логических задач в один шаг. Если хочется добавить «и заодно...» — это сигнал, что нужны два шага.

## Шесть обязательных полей

Каждое поле имеет свой контракт. Если хоть одно не заполнено — шаг не сформирован.

### 1. Цель

Что именно делаем. **Одна строка.** Существительное + действие в инфинитиве.

✅ «Восстановить симметрию `set-api-key` в catch-ветке.»
✅ «Добавить Spinner на экран ScanDesignSystem при `step='scanning'`.»
❌ «Поправить баг.» — какой именно?
❌ «Улучшить производительность.» — где, как, насколько?

### 2. Зачем

Бизнес или техническая причина. **1–2 предложения.** Должно отвечать на вопрос «почему это важно сейчас, а не в v1.1».

✅ «При exception в sandbox UI остаётся в loading-состоянии без обратной связи. Это блокер сценария Settings → Test API key.»
✅ «На L-палитрах 500+ токенов скан занимает 20–40 сек. Без Spinner UX поломан — пользователь думает, что плагин завис.»
❌ «Чтобы было лучше.»
❌ «Архитектурный принцип требует.»

### 3. Действие

Конкретные правки, кто что делает. Если затронуто несколько ролей — перечисли последовательно. Без указания файлов и строк, но достаточно конкретно, чтобы исполнитель понял зону работы.

✅ «`@backend`: добавить `postMessage('set-api-key-done', {success: false})` в catch-ветке handler'а в `src/sandbox/code.ts`. `@frontend`: убедиться, что обработчик в Settings корректно сбрасывает `loading` при `success: false`.»
❌ «Поправить код.»

### 4. Критерий успеха

**1–2 строки конкретного проверяемого результата.** Должен быть измеримым: скриншот / лог / diff / хеш коммита / output команды.

Шаблоны критериев по типу шага:

| Тип шага | Шаблон критерия |
|---|---|
| Правка кода | «Скриншот `<сценарий>` в Figma desktop соответствует acceptance, `tsc --noEmit` чисто, размер `dist/<bundle>.js` Δ ≤ N KB.» |
| Правка дизайна | «Скриншот компонента `<имя>` соответствует макету Ф.<NN.X>, токены применены без raw-значений.» |
| Документация | «Файл `<путь>` создан/обновлён, в нём заполнены секции <список>.» |
| Коммит | «`git log -1 --oneline` показывает `<hash> v<X.Y.Z> — <тема>`, версия синхронизирована в трёх местах.» |
| QA | «Тест-матрица `<имя>` пройдена, баг-репортов сформировано N, все воспроизводимы.» |

✅ «Кнопка `Test API key` в Settings показывает `Saved ✓` после successful set-api-key-done. Console чисто. Скриншот приложен.»
❌ «Проверить, что работает.»

### 5. Среда

Физическое место, где делается шаг. Без этого исполнитель не понимает, где открывать инструменты.

Список валидных сред:

| Среда | Когда |
|---|---|
| Claude Code в терминале | правки `src/`, `git`-операции, `npm run` |
| VS Code | редактирование документов в `context/`, ручная правка конфигов |
| Figma desktop | визуальная проверка плагина в iframe, прогон scan на тестовых ДС |
| Браузер | submission в Figma Community, чтение Gemini docs, скачивание из Project Files |
| Claude.ai чат | стратегическая работа `@project-lead`, `@doc-writer`, `@analytics` с Project Files |

Можно указать комбинацию: «Claude Code в терминале + Figma desktop для визуальной проверки».

### 6. Исполнитель

Имя субагента в формате `@<роль>`. Если шаг требует двух ролей — укажи последовательность: `@backend → @qa` (сначала backend делает, потом qa проверяет).

Маршрутизация — по правилам из CLAUDE.md, секция «Маршрутизация задач».

## Формат вывода

Используй ровно этот шаблон:

```markdown
### Шаг <X.Y.Z> — <короткое название>

**Цель:** <одна строка>

**Зачем:** <1–2 предложения, бизнес или техническая причина>

**Действие:** <конкретные правки, кто что делает>

**Критерий успеха:** <1–2 строки проверяемого результата>

**Среда:** <Claude Code в терминале / Figma desktop / VS Code / браузер / комбинация>

**Исполнитель:** @<роль> (+ @<следующая роль> для проверки, если применимо)
```

## Примеры

### Хороший шаг (правка кода)

```markdown
### Шаг 15.2.3 — Восстановить симметрию set-api-key в catch-ветке

**Цель:** Добавить ответ из catch-ветки handler'а `set-api-key` в sandbox.

**Зачем:** Сейчас при exception в sandbox UI остаётся в loading-состоянии. Settings → Test API key молча зависает. Это блокер сценария валидации Gemini-ключа, попадает в раздел «Известные ограничения» если не исправить до v1.0.

**Действие:** `@backend`: добавить `figma.ui.postMessage({ type: 'set-api-key-done', success: false, error: <message> })` в catch-ветке `src/sandbox/code.ts:139-153`. Расширить тип `SetApiKeyDoneMessage` в `src/shared/types.ts` полем `error?: string`.

**Критерий успеха:** Кнопка `Test API key` в Settings возвращается из loading в idle с error-message при невалидном ключе. `tsc --noEmit` чисто, размер `dist/code.js` Δ ≤ 0.2 KB. Скриншот error-state приложен.

**Среда:** Claude Code в терминале + Figma desktop для проверки.

**Исполнитель:** @backend → @qa (проверка симметрии и регрессии)
```

### Хороший шаг (документация)

```markdown
### Шаг 15.4.1 — Зафиксировать ADR-009 по симметрии PluginMessage в catch

**Цель:** Создать ADR, фиксирующий принцип «ответ из catch обязателен для всех handler'ов с try/catch».

**Зачем:** В Ф.14 нашли пять асимметричных handler'ов (start-scan, get-snapshot, discover-sources, ds-scan-confirmed, set-api-key). После 15.2.3 паттерн фиксируется на уровне принципа, чтобы будущие handler'ы не повторяли ошибку.

**Действие:** `@doc-writer`: создать `context/architecture/adr-009-plugin-message-symmetry.md` по шаблону ADR (Контекст / Решение / Альтернативы / Последствия / Прецеденты). Включить пять найденных асимметрий как прецеденты.

**Критерий успеха:** Файл `context/architecture/adr-009-plugin-message-symmetry.md` создан, содержит все обязательные секции ADR, прецеденты пронумерованы, ссылки на code.ts актуальны.

**Среда:** Claude Code в терминале.

**Исполнитель:** @doc-writer → @architect (ревью)
```

### Плохой шаг (НЕ делать)

```markdown
### Поправить асимметрии

Нужно поправить асимметричные handler'ы которые мы нашли. Сделать как раньше делали с fix-violation.
```

Что не так:
- Нет всех шести полей.
- Цель размытая — «поправить асимметрии», но какие именно?
- Нет критерия успеха.
- Нет среды.
- Нет исполнителя.
- «Как раньше делали» — не действие, а отсылка.
- Объединено пять разных handler'ов в один шаг — нужно разбить.

## Связь с архитектурными принципами

Этот skill реализует принципы из CLAUDE.md:

- **Атомарность изменений** — один шаг = один логический блок = один (потенциально) коммит.
- **Проверяемые acceptance criteria** — без явного критерия шаг не закрыть.
- **Явная маршрутизация** — без `@<роль>` непонятно, кто работает.

## Перед отдачей шага проверь

- [ ] Все шесть полей заполнены.
- [ ] Цель — одна строка с конкретным результатом.
- [ ] Зачем — 1–2 предложения с **причиной сейчас**, не «вообще полезно».
- [ ] Действие — конкретное, с указанием ролей и зон работы (без файла и строки — это слишком детально).
- [ ] Критерий успеха — измеримый (скриншот / лог / diff / хеш / output команды).
- [ ] Среда указана из валидного списка.
- [ ] Исполнитель — `@<роль>` по маршрутизации из CLAUDE.md.
- [ ] В шаге **одна** логическая задача, а не «и заодно».
- [ ] Если шаг требует разведки `@architect` перед исполнителем — это явно отражено в маршрутизации.
