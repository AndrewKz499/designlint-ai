# Skill: impact-map

Этот навык формирует **карту влияния** для нелинейного изменения в кодовой базе DesignLint AI. Карта помогает Project Lead'у выбрать вариант реализации **до** того, как исполнитель начнёт писать код, и снижает долю «дозаправочных» коммитов после неточной разведки.

## Когда использовать

Используй этот навык, когда задача попадает хотя бы в один из случаев:

- Изменение затрагивает **3+ файла** в разных слоях (sandbox / UI / shared).
- Меняется **контракт `PluginMessage`** (новый тип, переименование, добавление поля).
- Появляется **развилка A/B** — два разных архитектурных подхода с разными trade-offs.
- Затрагиваются `figma.clientStorage`-ключи (риск миграции для существующих пользователей).
- Появляется **async-операция**, способная зависнуть UI без индикатора прогресса.
- Есть **опасная мутация** Figma-документа (удаление нод, batch на `figma.root.children`).

## Когда НЕ использовать

Линейная косметика — **без impact-map**, сразу маршрутизация к исполнителю:

- Один цвет в `tokens.ts` → `@designer`.
- Одна строка в `strings.ts` → `@designer` или `@frontend`.
- Опечатка в комментарии → исполнитель по затронутой папке.
- Замена одного хардкода на токен в одном компоненте → `@designer`.

Для таких задач выдавай **Форму 1** из своего системного промпта, а не полную карту.

## Что НЕ делай этим скиллом

- Не пиши код — это работа `@backend` / `@frontend` / `@designer`.
- Не выбирай вариант A или B сам — это решение `@project-lead`. Ты формулируешь развилку, не разрешаешь её.
- Не подменяй разведку догадками. Если не прочитал `src/shared/types.ts` или не грепнул обработчики — нельзя выдать карту.
- Не дублируй разведку, которая уже есть в `context/architecture/` или `context/sessions/`. Сначала найди существующее, потом дополняй.

## Обязательные секции карты

Каждая карта содержит **все** эти секции в строгом порядке. Если какая-то секция «не применима» — пиши явно «не применимо: <причина>», не пропускай.

| Секция | Что туда писать |
|---|---|
| **Заголовок** | `## Карта изменения: <короткое название>` |
| **Затронутые файлы** | Все файлы прямого и косвенного влияния по слоям (sandbox / UI / shared). Для каждого — что именно меняется. |
| **Контракт `PluginMessage`** | Новые типы, изменённые типы, проверка симметрии в обе ветки try/catch. |
| **`clientStorage`-ключи** | Затронутые ключи, нужна ли миграция, есть ли fallback на старое имя. |
| **Риски** | Что может пойти не так. Регрессии в acceptance criteria закрытых фаз. |
| **Варианты A/B** | Минимум два варианта с trade-offs. Если вариант один — явно «развилка отсутствует, единственный вариант». |
| **Рекомендация** | Какой вариант разумнее **с точки зрения архитектуры**. Это рекомендация, не решение. |
| **Следующий шаг** | Конкретный шаг для исполнителя в формате проекта (Цель / Зачем / Действие / Критерий / Среда / Исполнитель). |

## Формат вывода

Используй ровно этот шаблон:

```markdown
## Карта изменения: <короткое название>

### Затронутые файлы

**Sandbox (`src/sandbox/`):**
- `code.ts` — <что меняется>
- `detector.ts` — <что меняется или «не затрагивается»>

**UI (`src/ui/`):**
- `App.tsx` — <что меняется>
- `components/<Имя>.tsx` — <что меняется>

**Shared (`src/shared/`):**
- `types.ts` — <что добавляется в `PluginMessage`>
- `strings.ts` — <если затрагиваются строки>

### Контракт PluginMessage

**Новые типы:**
- `<TypeName>` — <структура и направление: UI → sandbox или sandbox → UI>

**Изменённые типы:**
- `<TypeName>` — <что добавилось/изменилось>

**Симметрия проверена:**
- `<request-type>` ↔ `<response-type>` в try-ветке: ✅
- `<request-type>` ↔ `<response-type>` в catch-ветке: ✅ / ⚠️ требуется

### clientStorage-ключи

- Затронутые ключи: `<key1>`, `<key2>` / **не применимо**: <причина>
- Миграция со старого имени: нужна / не нужна
- Fallback-чтение в первые N версий: <план>

### Риски

1. <риск 1>
2. <риск 2>

**Регрессии в закрытых фазах:**
- Ф.<NN.X> «<acceptance>» — <под угрозой / не затронута>

### Варианты A/B

**Вариант A: <название>**
- Описание: <1–2 предложения>
- Плюсы: <bullet>
- Минусы: <bullet>
- Объём правок: ~N файлов / ~M строк
- Влияние на бандл: ~<значение KB>

**Вариант B: <название>**
- Описание: <1–2 предложения>
- Плюсы: <bullet>
- Минусы: <bullet>
- Объём правок: ~N файлов / ~M строк
- Влияние на бандл: ~<значение KB>

### Рекомендация

Вариант <A или B> — потому что <1–3 предложения по приоритетам v1.0/v1.1>.

### Следующий шаг (формат проекта)

- **Цель:** <одна строка>
- **Зачем:** <1–2 предложения>
- **Действие:** <конкретные правки>
- **Критерий успеха:** <1–2 строки проверяемого результата>
- **Среда:** Claude Code в терминале
- **Исполнитель:** @<роль> (+ @qa для проверки)
```

## Если развилки A/B нет

Иногда после разведки оказывается, что вариант **один** (например, симметрия `PluginMessage` нарушена и есть только один способ её восстановить). В этом случае:

```markdown
### Варианты A/B

**Развилка отсутствует.** Единственный вариант:
- <описание>
- Обоснование, почему альтернатив нет: <1–2 предложения>
```

Это **корректный** результат разведки, не пробел.

## Связь с архитектурными принципами

Этот skill реализует принципы из CLAUDE.md:

- **Симметрия `PluginMessage`** — ответ есть в обеих ветках try/catch. Прецедент: `fix-violation` без `fix-complete` в catch до 12.7.4.1.
- **`figma.commitUndo` — ДО мутации.**
- **Атомарность изменений** — карта должна быть привязываемой к одному коммиту (или явно говорить «потребуется N коммитов»).

## Эскалация по итогам разведки

После выдачи карты — **сразу** пиши `@project-lead`, если хоть одно из:

- Изменение затрагивает 3+ файла **И** есть развилка A/B (нужен выбор варианта).
- Решение влияет на объём v1.0 / v1.1.
- Конфликт с зафиксированным архитектурным принципом — нужно явное решение.
- Требуется изменение публичного контракта плагина (`manifest.json` — id, разрешения).
- Появляется новый тип `PluginMessage`, симметрия которого неочевидна.

Без эскалации к `@project-lead` исполнитель не должен начинать правки.

## Перед отдачей карты проверь

- [ ] Прочитан актуальный `src/shared/types.ts` (контракт, на который опирается всё).
- [ ] Прогрепаны обработчики `msg.type ===` в обоих слоях.
- [ ] Прогрепаны `figma.clientStorage` (если применимо).
- [ ] Прогрепаны `parent.postMessage` и `figma.ui.onmessage` (если меняется протокол).
- [ ] Каждая обязательная секция заполнена (или явно «не применимо»).
- [ ] Симметрия `PluginMessage` проверена в **обе** ветки try/catch.
- [ ] Сформулировано минимум два варианта A/B (или явно «развилка отсутствует»).
- [ ] Каждый вариант имеет trade-offs, не только описание.
- [ ] Рекомендация дана и обоснована.
- [ ] Следующий шаг сформулирован в формате проекта (Цель / Зачем / Действие / Критерий / Среда / Исполнитель).
- [ ] Эскалация к `@project-lead` определена (если применимо).
